# Расширение STV Market Researcher: программа работ

Дата обновления: 16.10.2026. Версия пакета: 1.2. Все шесть направлений внедрены в Market Researcher в объёме первых рабочих этапов. Фактический объём, проверки и ограничения приведены в начале каждого ТЗ. Расширения, явно перечисленные как отложенные, не считаются выполненными.

## 1. Цель

Связать техническое состояние инструмента с проверяемым информационным контекстом: первоисточник → актив → катализатор → исследовательская идея → технический сценарий → наблюдаемый результат. Пользователь должен видеть основания и неизвестное, сохранять собственные гипотезы и проверять их на воспроизводимых данных.

Пакет описывает шесть направлений из исследования stvterminal. Общая инфраструктура ниже является нулевым этапом первого направления, а не самостоятельным большим продуктом.

## 2. Основания и границы

Источники: [архитектура](https://github.com/seytuev/stvterminal/blob/af1b0b3a74f28b61b8c44b423a895610af92c418/docs/ARCHITECTURE.md), [разделы](https://github.com/seytuev/stvterminal/blob/af1b0b3a74f28b61b8c44b423a895610af92c418/docs/SECTIONS.md), [аудит](https://github.com/seytuev/stvterminal/blob/af1b0b3a74f28b61b8c44b423a895610af92c418/docs/AUDIT.md). В Market Researcher использовать текущие контракты из [индекса](../CONTRACTS_INDEX_RU.md), каноническое состояние app/services/asset_state.py, существующие HTF/H1/ALT lifecycle, quality, data_sync, авторизацию и миграционный механизм SQLite/PostgreSQL. Точки подключения сверять с кодом перед каждым этапом: параллельные изменения проекта не перезаписывать.

Обязательные границы:

- Исследовательские модули не меняют BOS/SMS, зоны, допуск входа, направление рыночной оценки и lifecycle технических идей.
- Прежнее внедрение ИИ-фильтра HTF/LTF отменено; [архивное ТЗ](../AI_HTF_LTF_Notification_Filter_Spec_RU_2026-10-10.md) не становится действующим из-за этого пакета.
- Нет автоторговли, автоматического исполнения, подключения биржевых ордеров и автоматического принятия идей.
- Полный перенос портфельного учёта, legacy Notion и ReelStudio не входит. Корзина исследования не является учётом реального счёта.
- Добавление зависимостей Redis, брокера сообщений, отдельного vector DB, нового frontend framework или перенос всего stvterminal не требуется для MVP.
- Новые API, таблицы, настройки и модули в этих документах — предлагаемые контракты, которых сейчас может не быть.

## 3. Архитектура первого этапа

Основной вариант по уточнению владельца: перенос готовых модулей STVTerminal внутрь Market Researcher, адаптация к общей БД и существующему интерфейсу. Исходные TypeScript-модули сохранены в app/research/terminal с provenance.json и хешами оригиналов. Готовый terminal-runtime.cjs запускается локальным Node.js >=18; отдельные Next/Vite, D1, R2 и второй сервер для этого не нужны. Браузер работает только с API Market Researcher. Открытие графика не обращается к внешней модели или терминалу.

Перенесены Hub merge/consensus/digest schema, mention identity, project signals model, Telegram noise/stories/web reader, events types/time/merge/importance. Чистый Hub core извлечён из исходника без переписывания алгоритмов. Python-адаптеры отвечают за хранение, авторизацию, задания и связи с техническими инструментами. Публичные Telegram-каналы собираются встроенным перенесённым reader; Deribit подключён к календарю отдельным адаптером. Исторические данные импортируются из оригинального transfer-data ZIP. Интеграционный API отдельного терминала сохранён как необязательный путь миграции/обновления.

Фактическое размещение первого этапа:

На старте разрешён отдельный фоновый цикл в существующем процессе; тяжёлые исследования уже исполняются в изолированном subprocess с frozen входами, лимитом 60 секунд/512 МиБ. Исследовательские задания не помещать в очередь calc_task для закрытых свечей. Использовать её проверенные принципы, сохраняя самостоятельные таблицы и ресурсные лимиты.

### Запуск и обновление перенесённых модулей

Настройки приведены в .env.example: RESEARCH_ENABLED=1 включает домен, RESEARCH_DERIBIT_ENABLED=1 — публичные экспирации. RESEARCH_NOTIFICATIONS_ENABLED по умолчанию выключен. URL и токен отдельного терминала можно оставить пустыми. Каналы настраиваются на /research.html. Обычный app.main запускает исследовательские задания вместе с текущим worker. Для локального просмотра без второго worker котировок: `python -m tools.serve_research --port 8086`.

Повторяемый перенос исходников: `python tools/import_terminal_modules.py ../stvterminal`; сборка: `npm ci --prefix tools/research`, затем `npm run build --prefix tools/research`. Исторический ZIP: `python -m tools.import_terminal_snapshot <archive.zip> --database <database-path>`. Повторный импорт не дублирует версии. Перед изменением рабочей БД сохранять согласованную резервную копию.

Проверки: `python -m pytest tests/test_research.py -q`; PostgreSQL — те же тесты через tools.pytest_postgres на отдельной тестовой БД. Браузерные проверки tests/research_ui_check.cjs используют изолированный tests.research_fixture_server. Нагрузочный стенд `python -m tools.check_research_performance` создаёт временную БД, 10 000 материалов / 100 000 версий / 2 000 событий и сохраняет замеры в tmp/research-performance.json; он не измеряет влияние на основной цикл котировок. Полный нагрузочный допуск R1.3 остаётся отдельной проверкой.

## 4. Общая идентичность

### 4.1. Актив и инструмент

research_asset: asset_uid (неизменяемый UUID), asset_class (crypto/equity/index/cash), display_symbol, name, status (active/archived/merged), merged_into_uid, created_at. Символ не является уникальным ключом.

research_asset_external_id: asset_uid, namespace, external_id, chain, address, valid_from, valid_to, revision_id, available_at, verification, origin. Пространства включают stvterminal, coingecko, cmc, contract и другие реально подключённые каталоги. Контракт нормализуется по правилам конкретной сети; универсальное приведение всех адресов к нижнему регистру запрещено.

research_instrument_asset: instrument_id, asset_uid, relation (spot/perpetual/equity/index), valid_from, valid_to, revision_id, available_at, resolution (verified/manual), evidence. Один актив связан с несколькими инструментами. Для отношения «базовый актив» у инструмента допустима одна действующая связь. Проверять биржу, рынок, базу/котировку и период действия. Старый instrument_id не переназначать новому активу без истории. Valid_from/valid_to задают предметный период связи, available_at — когда приложение получило именно эту версию решения; историческое чтение проверяет обе оси.

research_identity_candidate: исходное упоминание, кандидаты, причина неоднозначности, решение владельца, версия и время. Одинаковый символ, похожее название или URL сами по себе не создают подтверждённую связь. Неоднозначный материал виден в проверке, но не попадает в подтверждённый контекст актива.

### 4.2. Общие ссылки

Внешний объект идентифицируется тройкой provider, kind, external_id. Локальный ID не зависит от отображаемого тикера. Ссылки между доменами содержат тип объекта, ID и при необходимости revision_id; не использовать произвольный URL как единственный внешний ключ.

## 5. Время, версии и историческая доступность

Все машинные времена — целые миллисекунды UTC; интервалы полуоткрытые [from, to). В текущем UI используется принятый в проекте показ МСК. Для календарной даты без времени хранить дату и её исходный timezone отдельно; не превращать её в точное время полуночи.

| Поле | Значение |
|---|---|
| published_at | Время публикации оригинала, если известно |
| occurred_at / starts_at | Время факта или ожидаемого события; допускает неизвестность и точность периода |
| source_observed_at | Когда терминал впервые получил конкретную версию |
| available_at | Когда эта версия стала доступна Market Researcher после commit импорта |
| updated_at | Последнее изменение локальной записи |
| analysis_at | Время конкретного разбора |
| revision_id / schema_version | Неизменяемая версия содержания / формат контракта |

Опоздавший импорт не датировать задним числом по published_at. Изменение текста, даты, стадии, привязки или анализа создаёт новую неизменяемую версию с отдельным available_at. Текущая проекция может обновляться; история версий сохраняется. Исторический режим использует только версии с available_at ≤ отсечка. Реконструкция из поздно импортированных данных подписывается отдельно и не считается тем, что приложение знало тогда.

Снимок содержит as_of, generated_at, input_revision_ids, method_version, payload_hash и quality. generated_at не заменяет время доступности данных. Для внешней истории отдельно разрешена отсечка source_observed_at, только если экспортированная история подтверждает это время; режим называется реконструкцией внешнего архива.

## 6. Интеграционный протокол

Необязательный адаптер отдельного stvterminal реализует серверные маршруты ниже. Он нужен только для дальнейшего получения данных из этого экземпляра; встроенный перенос и сбор Market Researcher от него не зависят. Изменения находятся в site/services/research-export, маршруте integration/v1 и локальной миграции 0029; удалённая БД терминала при внедрении не изменялась.

- GET /api/integration/v1/capabilities — версия, поддерживаемые сущности, идентификатор набора данных, срок доступности change log.
- POST /api/integration/v1/snapshots — создание согласованного снимка выбранных сущностей/активов; возвращает snapshot_id и исходный change cursor. Операция создаёт только служебный экспорт, не меняет пользовательские данные.
- GET /api/integration/v1/snapshots/{id}?cursor=... — страницы стабильного снимка.
- GET /api/integration/v1/changes?after=...&limit=... — изменения после снимка, включая исправления и tombstones.

MVP экспортирует assets, materials, analyses и catalyst_candidates для выбранного списка. Экспорт готовых summaries подключается при наличии подтверждённых ссылок на материалы. Возможности объявляются явно; отсутствующая сущность не трактуется пустой.

Envelope: schema_version, dataset_id, batch_id, generated_at, items, next_cursor, has_more. Item: entity_kind, entity_id, revision_id, operation (upsert/tombstone), change_seq, payload, payload_hash. Последовательность change_seq монотонна в одном dataset_id. Курсор непрозрачный, устойчивый к одинаковым timestamp, привязан к фильтру и версии формата. Один updated_at без составного порядка недостаточен.

Импорт страницы и продвижение cursor — одна транзакция. UNIQUE(provider, entity_kind, entity_id, revision_id) обеспечивает повторяемость. Повтор страницы не дублирует записи. Старую версию не применять поверх новой. Неизвестное обязательное поле/сломанная ссылка отправляются в карантин с причиной; для их повторного применения хранить исходную ограниченную запись и позицию. Курсор разрешено продвинуть только после надёжного сохранения всех строк страницы, включая карантин. Зависимости импортируются до публикации готовой проекции.

Согласованность snapshot должна обеспечиваться на стороне терминала: материализация экспортных строк или versioned чтение по зафиксированному watermark. Серия обычных SELECT по изменяемым таблицам с одним generated_at согласованным снимком не считается. Временные экспортные объекты имеют TTL, объявленный capabilities; TTL не применяется к истории пользовательских данных. После завершения snapshot все изменения с большими change_seq должны быть доступны без окна потери между снимком и change log.

Истечение cursor/snapshot возвращает 410 с причиной; импорт начинает новый snapshot, сохраняя прежнюю рабочую проекцию до завершения. Смена dataset_id требует полной сверки. Удаление отсутствующего объекта выводить только из завершённого полного снимка соответствующей области или явного tombstone; отсутствие в ограниченной выдаче не является удалением.

В терминале change log и согласованный экспорт необходимо разработать; существующие UI endpoints с LIMIT и runtime-таблицами не считать готовым протоколом. Если точная история отсутствует, импортировать текущие данные с временем первого получения и явным history_complete=false.

## 7. Доступ, задания и бюджет

Пользовательские API защищаются текущим require_auth; изменяющие запросы наследуют проверку Origin. Токен интеграции отдельный, серверный, с областью экспортируемых данных. Не передавать его в query/browser/localStorage/логи. Новые маршруты терминала сами проверяют токен; наличие защиты Sites и заголовка oai-authenticated-user-id не заменяет проверку на отдельном сервере.

research_job: id, kind, dedup_key, input_version, status, attempts, next_attempt_at, lease_owner, lease_until, progress, last_error_code, created_at, updated_at. Статусы pending/running/succeeded/failed/cancelled. Claim атомарный; просроченный lease допускает восстановление идемпотентного задания. Результат фиксируется только при совпадении входной версии. Сетевые операции выполняются вне транзакций и общих блокировок.

Для одной пары kind/dedup_key допускается одно активное задание; это обеспечивается ограничением/атомарным claim в поддерживаемой БД. Более новая входная версия помечает старое вычисление superseded и ставит новый расчёт. Ошибочное или отменённое задание не удерживает lease бесконечно. При shutdown прекращается выдача новых заданий, завершаются короткие транзакции, сохраняется прогресс; принудительно оборванное задание восстанавливается по lease.

Новые функции по умолчанию выключены. Предлагаемые настройки: RESEARCH_ENABLED=false, RESEARCH_SYNC_INTERVAL_SECONDS=300, RESEARCH_SYNC_PAGE_SIZE=100 (максимум 500), RESEARCH_HTTP_TIMEOUT_SECONDS=15, RESEARCH_SYNC_CONCURRENCY=1. После ошибки — backoff с jitter и верхней границей 30 минут; 429 учитывает Retry-After. 401/403 переводят источник в auth_error без частых повторов. Значения — инженерные начальные настройки, не результаты измерений.

Информационный контекст 01–02 переиспользует готовые разборы. ИИ-задачи 03/05 обращаются к провайдеру через общий журнал model.py и бюджет; расходы отдельного терминала не входят в этот журнал. Перед включением новых собственных LLM-задач требуется настроенный ненулевой бюджет, лимиты запросов/выхода и журнал provider/model/input hash/usage. Отсутствие бюджета означает budget_blocked, а не безлимитную работу. Автоматический повтор платного запроса с неопределённым исходом ограничивается отдельной политикой и отражается в расходах.

## 8. Качество, API и интерфейс

Общий ответ чтения содержит data, meta: as_of, generated_at, data_revision, quality, reasons, last_success_at, history_complete. Quality: ok/partial/stale/unavailable/disabled; auth_error, budget_blocked и schema_error передаются как причины/состояния источника. Пустая успешная выборка отличается от отсутствия подключения и старого кэша.

Локальные списки имеют устойчивый cursor по времени и ID, ограничение limit ≤ 100 и фильтры на сервере. 400 — неверный запрос, 401/403 — доступ, 404 — объект, 409 — конфликт версии, 422 — неверные данные, 429 — лимит запуска, 503 — функция недоступна. Ошибка содержит code, message, request_id и field_errors при наличии; без секретов. Долгая операция возвращает 202 и job_id.

Все изменения пользователя записываются с actor, request_id, before_revision, after_revision и временем. Создание поддерживает Idempotency-Key; редактирование — expected_revision. Повторный запрос не создаёт второй объект. Данные источника и пользовательская редакция хранятся раздельно.

Общие локальные маршруты, необходимые до предметных модулей:

| Метод и путь /api/research/v1 | Контракт |
|---|---|
| GET /assets | Поиск по symbol/name/external ID, cursor, limit; одинаковые символы возвращаются раздельно |
| GET /assets/{uid} | Каталог, внешние ID, действующие инструментальные связи и их история |
| POST /assets | Ручной подтверждённый актив с идентифицирующим основанием; повтор внешнего ID даёт конфликт |
| POST /instruments/{id}/asset-link | Создать/завершить версионную связь; asset_uid, valid_from, expected_revision, reason |
| GET /jobs/{id} | Общий статус, progress, error_code, created/updated_at и ссылки на готовый результат |
| POST /jobs/{id}/cancel | Кооперативная отмена поддерживаемого задания; уже завершённый результат не удаляется |

Idempotency-Key хранится с владельцем, типом операции и hash тела запроса минимум 7 суток; повтор с другим телом возвращает 409. После срока ключа постоянные уникальные доменные ограничения продолжают защищать от дублей. Секреты исключаются из сохраняемого audit payload. Изменение instrument→asset не переписывает прошлые интервалы; при исправлении старой ошибки создаётся отдельная версия решения, доступная с текущего момента.

UI должен сохранять выбранный инструмент, масштаб/позицию графика, сортировку и состояние раскрытия при фоновом обновлении. Поздний ответ для другого инструмента не обновляет текущую карточку. Новые тексты и HTML экранируются; внешние материалы считаются недоверенными данными. Проверять 1440/900/390 px, обе темы, клавиатуру, длинные названия и отсутствие горизонтального переполнения.

Исследовательский журнал отделён от технических market/decisions/delivery. Если позже добавляется вкладка общего журнала, у неё собственный kind=research и серверная пагинация; старые kind и контракты не переименовываются. Push новых модулей изначально выключен и использует отдельные категории существующего outbox. Не отправлять исторический импорт как новые уведомления.

## 9. Хранение и эксплуатация

Новые research_* таблицы создаются версионированными миграциями, а не DDL из GET. Обязательны внешние ключи, уникальные ограничения и индексы для cursor/asset/time/job status. При поддержке обоих backend проекта миграции и смысловые интеграционные проверки выполняются на SQLite и PostgreSQL. Не копировать D1-specific SQL в PostgreSQL без адаптации.

До включения сделать резервную копию и проверить миграцию на копии. Отключение флага прекращает новые задания, сохраняя данные и техническую работу. Rollback приложения не удаляет новые таблицы; разрушительное преобразование заменяется совместимой миграцией. Данные research включаются в существующую процедуру backup/restore.

Диагностика: доступность API источника, время успешной страницы/синхронизации, отставание, pending/running/failed, возраст самого старого задания, карантин, качество привязок, число новых версий, ошибки и расходы модели. Метрики без токенов, исходных текстов и неограниченных label по ID. Очистка заданий/кэша имеет политику; доказательства сохранённых идей и снимки экспериментов не удаляются вместе с временным кэшем.

Начальная эксплуатационная область — список до 10 проверенных активов. Целевой стенд первой приёмки: 10 000 материалов, 100 000 изменений, 2 000 катализаторов; для 04–06 нагрузки определяются в их документах. Цель чтения карточки p95 ≤ 500 мс при 5 параллельных клиентах после прогрева. Исследовательская синхронизация не должна увеличивать p95 обработки котировок/закрытых свечей более чем на 10% относительно того же стенда без неё; до измерения это целевые ограничения, не подтверждённые характеристики.

Замер 15.10.2026 на Windows 10.0.26200, Python 3.11.9, SQLite, 12 логических CPU: указанный временный набор 10 000 / 100 000 / 2 000, 10 прогревов, 100 чтений, concurrency=5, 1,751 с; p50=81,78 мс, p95=90,46 мс, максимальный ответ 4 980 байт. Это чтение репозитория с прогретым кэшем исходных алгоритмов. Отдельный HTTP smoke на рабочем локальном наборе: 30 запросов, concurrency=5, p95=38,91 мс, ответ до 7 843 байт. Эти короткие замеры не заменяют длительный baseline влияния синхронизации на worker котировок.

## 10. Последовательность поставок

| Поставка | Минимальный законченный результат | Условие следующего шага |
|---|---|---|
| R0 | Реестр активов, проверка привязок, экспорт/импорт, диагностика | Повтор, рестарт, исправление и удаление проверены |
| R1 | Информационный блок рабочего места для пилота | Источники прослеживаются, stale честный, график не тормозит |
| R2 | Ручные/импортированные катализаторы и связи с активами | Перенос дат, дубли, конфликты и история приняты |
| R3 | Идеи, ревизии, связи и ручной пересмотр | Не смешиваются с HTF-идеями, результат считается от корректного времени |
| R4 | RS в скринере, затем версионные корзины | Проверены формулы, пропуски, состав и точки старта |
| R5 | Учебник сначала с ручной проверкой, затем теневой поиск | Независимая выборка и ошибки оценки отделены |
| R6 | Описательные эксперименты, затем исполнение стратегий | Историческая доступность и воспроизводимость доказаны |

04 допускает отдельное продвижение после R0; R5/R6 не блокируют полезный выпуск R1. Сроки определяются после R0 и проверки доступности источников. В каждом документе этапы являются отдельными задачами; не объединять весь пакет в один большой релиз.

## 11. Общая приёмка

- G01: флаги выключены — прежние API, графики, движки и уведомления работают с прежней семантикой.
- G02: одинаковый тикер у разных активов не приводит к склейке; несколько рынков одного актива отображают один исследовательский контекст.
- G03: повтор страницы, одинаковые timestamp, падение перед/после commit и исправление старой записи не теряют и не дублируют изменения.
- G04: поздние публикации и новые редакции не появляются в историческом срезе раньше available_at.
- G05: 401, 429, timeout, неверная схема, частичная история и пустой ответ различимы; сохранённые данные доступны с честным качеством.
- G06: в сетевых запросах браузера, HTML, API и логах нет интеграционных секретов; мутации защищены авторизацией/Origin.
- G07: SQLite/PostgreSQL сохраняют эквивалентный смысл; backup/restore восстанавливает связи, версии и курсоры.
- G08: измерены целевые задержки и влияние на технические циклы; выход за пределы устраняется до расширения пилота.

Каждый релиз закрывается изменением кода, миграциями, релевантными тестами, визуальной проверкой изменённого UI и фактическим результатом в ответе задачи. Проверки документации, тестовые источники и текущая работа внешних API не подменяют друг друга.

## 13. Правила изменения пакета

Новые численные значения в документах — стартовые проектные решения. Их изменение оформляется новой method/config version с причинами; результаты старых версий остаются читаемыми. Фактические возможности подключённого API сверяются при реализации, а не предполагаются по документации 2026-10-13.

Для замеров сохранять hardware/runtime/backend, размер данных, concurrency, warmup, длительность, p50/p95 и исходный baseline технических циклов. Сравнение выполняется на одном наборе нагрузки с модулем выключенным и включённым. Не использовать заявленное целевое p95 как уже полученный результат.

При конфликте требований общие идентичность/время/доступ/историческая честность имеют приоритет; предметная численная методика — из соответствующего ТЗ. Изменение текущего технического контракта HTF/H1/ALT/Events требует отдельной задачи, а не скрытого исключения внутри исследования.
