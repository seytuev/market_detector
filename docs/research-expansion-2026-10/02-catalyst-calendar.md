# ТЗ 02. Календарь внешних катализаторов

Дата: 15.10.2026. Версия: research-catalysts-1.0. Статус: первый рабочий этап внедрён. Общие контракты — [README](README.md); материалы и идентичность — [ТЗ 01](01-asset-information-context.md).

Реализованы режим «Катализаторы» в текущем разделе событий, список/неделя/месяц, фильтры, точные и неполные даты, CRUD и история, очередь кандидатов, принятие/отклонение, явное объединение/разделение, конфликты обновлений источника, ближайшие события в карточке актива. Исходные types/time/merge/importance из STVTerminal перенесены; предложения объединения требуют решения владельца. Подписки подключены к существующему outbox, глобальная отправка по умолчанию выключена.

Из живых адаптеров включён Deribit: фактически получены 18 уникальных экспираций BTC/ETH из публичного списка контрактов. Из архива терминала перенесены 6 кандидатов на проверку. Tokenomist/CoinMarketCal/FRED, LLM-извлечение новых кандидатов и полноценное макропокрытие остаются следующими поставками: доступность API не выдаётся за полноту календаря. Реальные уведомления при проверке не отправлялись. Семантика времени, идемпотентность, сохранение данных при отказе источника и смена ревизии напоминания проверены на SQLite/PostgreSQL; интерфейс проверен в двух темах и трёх размерах.

## 1. Цель и отличие от текущего календаря

Добавить проверяемый календарь внешних событий: разлоки, листинги/делистинги, обновления сетей, запуски, governance, токеномика, макропубликации и экспирации. Пользователь видит событие, дату с реальной точностью, стадию, затронутые активы, источники и изменения планов.

Существующие /api/events/calendar, app/events/calendar.py и статистика дней BTC/корзины сохраняют назначение. Они не заменяются внешним календарём. Катализаторы хранятся в research_* и имеют новые API; они не добавляются в events_fact как рыночный направленный факт.

MVP: ручное создание/проверка, импорт кандидатов терминала, список/неделя/месяц, связь с активом и отображение ближайшего в рабочем месте. Автоматический опрос всех провайдеров и push не являются условием первого выпуска.

## 2. Что переиспользовать

stvterminal: src/events/types.ts, time.ts, merge.ts, pipeline.ts и sources; services/calendar/extraction.ts; services/events/server.ts. [Исходный модуль](https://github.com/seytuev/stvterminal/tree/af1b0b3a74f28b61b8c44b423a895610af92c418/site/src/events).

Переиспользовать точность даты, отдельные источники и контекст, извлечение кандидата, историю запусков. Heuristics merge переносить только после проверки: совпадение тикера и kind не всегда означает одно событие; соседние разлоки/релизы могут быть самостоятельными.

Внешние адаптеры Tokenomist/CoinMarketCal/FRED/Deribit и других источников включаются по одному после проверки доступа и семантики. Статический список дат FOMC из исходника не становится автоматически актуальным календарём: хранить период покрытия, источник и время проверки, показывать окончание покрытия.

## 3. Сценарии

1. «Контекст рынка → Катализаторы»: ближайшие события с фильтром «Наблюдаемые активы / Все доступные / Макро».
2. В рабочем месте выбран инструмент: список его событий; глобальное макрособытие показывается с пометкой общего контекста, без утверждения о доказанном влиянии на этот токен.
3. Материал содержит «запуск в IV квартале»: кандидат появляется в «На проверке» с precision=quarter, без выдуманного дня.
4. Официальный источник переносит дату: пользователь видит новую дату, предыдущую и основание переноса.
5. Два источника расходятся: одно подтверждённое событие сохраняет конфликт, либо кандидаты остаются раздельными до проверки.
6. Прошло запланированное время, подтверждения нет: «Дата прошла, исполнение не подтверждено», без автоматического live/completed.

## 4. Модель данных

research_catalyst: id, kind, title, scope (asset/global), created_at, current_revision_id, review_status (pending/accepted/rejected), archived_at. Виды: unlock/listing/delisting/launch/upgrade/governance/tokenomics/security/regulatory/macro/expiry/other. События без будущей даты допустимы.

research_catalyst_revision:

| Группа | Поля |
|---|---|
| Версия | revision_id, catalyst_id, available_at, actor, revision_reason, payload_hash |
| Содержание | title, summary, mechanism_hypothesis, risks, checks |
| Стадия | stage=rumor/proposal/announced/live/denied/cancelled |
| Время | date_label, timezone, precision, starts_at, ends_at, date_status |
| Доказательства | source_revision_ids, evidence_quotes, external_event_ids |
| Качество | verification, conflicts, coverage_note |
| Числа | amount, amount_unit, pct_of_supply, supply_basis, values_as_of; каждое поле nullable |

precision: exact/day/week/month/quarter/unknown. starts_at/ends_at задают точный момент либо границы периода с признаком precision; границы периода не выдаются за точное время события. Для day хранить исходную календарную дату/timezone; при неизвестном поясе не создавать точный UTC timestamp.

date_status: scheduled/postponed/unscheduled/passed_unconfirmed/completed/cancelled. Это отдельная ось от стадии содержания. Completed требует свидетельства исполнения. Denied означает опровержение утверждения, cancelled — отмену плана; оба сохраняют прежние версии.

research_catalyst_asset: catalyst_id, asset_uid, relation (direct/contextual/beneficiary_hypothesis), evidence, available_at. Глобальный макро-контекст не копируется отдельным объектом для каждого актива.

research_catalyst_source: catalyst_id, source_namespace, external_id, material_revision_id, source_url, published_at, asserted_date, asserted_stage, source_observed_at, available_at. Структурированный API — источник конкретного утверждения, а не универсальное доказательство всего текста.

research_catalyst_candidate: исходное извлечение, material_revision_id, parse_version, предлагаемые связи, review_status, rejection_reason, accepted_catalyst_id. Повтор одного извлечения идемпотентен. research_catalyst_transition фиксирует создание, принятие, смену даты/стадии, конфликт, отмену, слияние и разделение.

## 5. Валидация и объединение

Автоматическое принятие в MVP разрешено только для явно настроенного структурного адаптера с проверенным внешним event_id, семантикой дат и подтверждённым активом. Извлечение из текста создаёт pending-кандидат; confidence модели не заменяет review_status.

Порядок дедупликации:

1. Совпадает namespace+external_event_id — новая версия известного события.
2. Известен один первичный анонс/документ — материалы добавляются как свидетельства.
3. Семантическая похожесть/один ticker/kind/близкие даты — только кандидат объединения.

Автоматическое слияние разных событий запрещено при разных версиях релиза, раундах governance, партиях разлока или площадках листинга без доказательства единого события. Два разлока за неделю не объединять по одной только близости дат. Экспирации разных продуктов/бирж не объединять автоматически.

Ручное merge создаёт канонический ID, aliases и историю; ссылки прежних объектов продолжают разрешаться. Split восстанавливает самостоятельные объекты и переносит конкретные свидетельства с журналом решения. Исправление не переписывает прошлые снимки.

Числа выводятся с единицей и знаменателем: «5% supply» требует определения total/circulating/другой базы и времени оценки. Неизвестное значение не заменяется нулём. Ожидаемое направление влияния является гипотезой; листинг/разлок не формирует автоматически LONG/SHORT.

## 6. Состояния и приоритет

Приоритет внимания: critical/high/normal/low с перечислением причин. В MVP код использует вид события, прямую связь с наблюдаемым активом, близость даты и подтверждённость источника. Версия политики фиксируется. Приоритет не равен вероятности движения и не меняет технические strategy gates.

Окончание даты переводит scheduled в passed_unconfirmed фоновым заданием, если нет нового свидетельства. При изменении даты старый reminder аннулируется и создаётся новая версия. Отзыв единственного источника понижает verification, но не уничтожает историю существования плана.

## 7. API

| Метод и путь /api/research/v1 | Вход / результат |
|---|---|
| GET /catalysts | from, to, asset_uid, scope, kind, stage, review_status, cursor, limit |
| GET /catalysts/{id} | Текущая версия, источники, конфликты, связи |
| GET /catalysts/{id}/history | Версии и переходы с пагинацией |
| GET /catalyst-candidates | Очередь проверки, фильтры по причине |
| POST /catalysts | Ручное событие; Idempotency-Key |
| PATCH /catalysts/{id} | Пользовательское исправление; expected_revision, reason |
| POST /catalyst-candidates/{id}/review | accept/reject/link_existing; expected_revision |
| POST /catalysts/merge | IDs, выбранное основание, expected_revisions |
| POST /catalysts/{id}/split | Наборы источников для новых объектов и причина |
| POST /catalysts/collect | 202 job_id для настроенных источников |
| GET /catalysts/source-status | Покрытие дат, курсоры, ошибки и время успеха |

Ограничение календарного запроса: максимум 93 дня; неизвестные даты запрашиваются отдельным фильтром unscheduled=true. Для выбранного диапазона возвращаются пересекающие его периоды, а не только точные starts_at. Входная timezone проверяется; отображение использует правила текущего приложения.

История и права соответствуют README. Ссылка из карточки актива содержит catalyst_id и при необходимости revision_id. Ручная правка конфликтует по версии, не стирает незаметно обновление провайдера.

## 8. Интерфейс

В «Контексте рынка» добавить режим «Катализаторы», сохранив текущие «Ситуация / Лента / Календарь / Правила» и их URL. Для прямого входа предложить events.html?mode=catalysts&catalyst=ID; существующие assessment-ссылки продолжат работать.

Представления: список ближайшего, неделя, месяц; отдельные «На проверке» и «Без точной даты». События месяц/квартал отображаются в полосе периода/списке, а не как точка произвольно выбранного дня. Дневное событие без времени не получает подпись «00:00».

Карточка: название, актив, вид, стадия, дата/период, подтверждение, приоритет и его причина, источники, история изменений. Конфликт даты виден сразу. Формы создания/проверки показывают исходное утверждение рядом с редактируемым значением. Отдельные действия: принять, исправить, отклонить, связать с идеей.

В графике MVP ограничиться списком рядом с ним. Маркеры на временной оси — следующий этап: координата только при известной дате и precision, без растягивания оси/сброса масштаба. Событие без точной даты не рисуется точным маркером.

## 9. Напоминания и отказоустойчивость

В MVP уведомления выключены; календарь и счётчики работают без push. Позже пользователь отдельно включает напоминания по отслеживаемым активам/видам. Начальные варианты: за 24 часа и 1 час только для exact, за день для day; для month/quarter — периодическая сводка без точного countdown.

delivery_key включает catalyst_id, revision_id, reminder_kind и recipient. Перенос даты не приводит к повторной доставке старого reminder. После включения или backfill не отправлять пачку прошлых событий. Использовать существующий outbox с самостоятельной категорией research_catalyst; не смешивать с рыночной сводкой events_bundle.

Поведение при отказе: сохранить календарь и явно показать старое время синхронизации; не объявлять отсутствие событий. Сбой одного адаптера не останавливает другие и не удаляет его записи. Покрытие календаря и будущих дат показывается отдельно от технической доступности API.

## 10. Поставки

1. K1: модель, ручной CRUD, кандидаты, источники и список. Без автоматического принятия и push.
2. K2: импорт терминала, корректные даты/периоды, конфликты, merge/split и история; ближайшее в рабочем месте.
3. K3: один подтверждённый внешний адаптер, затем остальные по отдельности; контроль покрытия и расписание.
4. K4: подписки/напоминания и опциональные маркеры графика после приёмки K1–K3.

## 11. Критерии приёмки

- K01: текущий календарь статистики дней и рыночные оценки возвращают прежние данные; новый календарь имеет отдельный namespace.
- K02: «в IV квартале», «в октябре», day без timezone и exact корректно различаются в БД, API и UI.
- K03: перевод America/New_York → UTC учитывает DST; границы дат в МСК проверены без жёсткого вычитания часов.
- K04: дата публикации не становится датой события; неизвестная дата остаётся неизвестной.
- K05: proposal не становится live, а прошедшая дата не становится completed без свидетельства.
- K06: разные партии разлока, релизы и продукты экспирации не теряются при дедупликации.
- K07: перенос даты/отмена/опровержение/отзыв источника сохраняют версии и корректно отражаются в текущем виде.
- K08: два спорных источника дают конфликт; ручное решение журналируется и не стирается следующим импортом.
- K09: merge/split сохраняют адресуемость ссылок и историю; повтор операции идемпотентен.
- K10: при отключённом источнике и истёкшем периоде покрытия UI показывает ограничение, а не пустой здоровый календарь.
- K11: напоминания проверены через тестовый sender: перенос, повтор, рестарт и backfill не создают повторной/исторической рассылки.
- K12: 2 000 событий и диапазон до 93 дней читаются в целевом p95 README; обе темы и мобильное представление не переполняются.

Fixtures: точная макропубликация в летнее/зимнее время, квартальный анонс, соседние разлоки, перенос, отмена, ложный слух, два расходящихся источника, глобальное событие и два одноимённых токена. Для каждого подключаемого адаптера — контрактный тест реального формата с зафиксированным обезличенным ответом и отдельная проверка актуальности доступа.
