# ТЗ: очистка графика «Альткоины» от старых BOS и лишней разметки

Дата: 7 октября 2026. Статус: готово к декомпозиции на задачи реализации.

Связанный документ: [план редизайна страницы](Altcoins_Redesign_Plan_RU.md).

## 1. Ожидаемый результат

При открытии выбранного сетапа пользователь видит свечи, текущий диапазон, ключевые факты сценария и небольшое число последних структурных событий. Старые BOS/SMS/SSL, обратные сломы и завершённые аналитические эпизоды доступны в журнале и режиме истории.

В этом ТЗ «удалить старые BOS с графика» означает убрать их из обычной визуальной разметки. Рыночные события, опоры, подтверждения и outbox в БД сохраняются. Фильтры отображения не влияют на расчёт сетапов, A/B, целей, отмены, дедупликацию или Telegram.

## 2. Подтверждённые причины перегрузки

- `alt.js::renderChart()` передаёт в `setMarkers()` все строки `d.structure_events`, добавляет выход и входы и вызывает `fitContent()`.
- API возвращает структурные события выбранного `setup_id` без визуального отбора. В `anchors.historical` может быть отметка исторического восстановления.
- `app/alt/engine.py` хранит `BOS_REV` и `SMS_REV` как аналитические факты. Они не являются самостоятельной отменой сетапа, но на графике сейчас выводятся вместе со всеми событиями.
- `drawAltLayers()` выводит все эпизоды манипуляции и область ретеста; управление слоями отсутствует.
- Все TP1–TP4 создаются как ценовые линии, в том числе далёкие и пройденные. Их влияние на масштаб нужно проверить на интеграционном графике.
- Длинная история и накопленные маркеры визуально сжимают свечи. Уже существует проверка `K > 0` перед рисованием линии; её сохранить.

Отметка `historical` обозначает способ первоначальной обработки, а не возраст события и не его ненужность. Не использовать её как единственный критерий скрытия.

## 3. Режимы разметки

| Режим | Содержание | Назначение |
|---|---|---|
| **Сетап** — по умолчанию | Ключевые события выбранного сетапа + последние BOS/SMS/SSL по правилам §4 | Повседневный анализ |
| **История** | Все доступные события выбранного сетапа внутри видимого участка, с группировкой при плотности | Подробный разбор |
| **Без событий** | Свечи и независимо включённые уровни/области; событийных маркеров нет | Изучение цены |

Режим событий и временной охват — разные настройки. Выбор «История» не масштабирует график автоматически; для этого есть «Вся история». Показать пояснение, что история относится к выбранному сетапу, а не к каждому сетапу монеты.

Переключатели слоёв:

- Диапазон L/U/M и область накопления — включены.
- Входы/ретест — включены; событийные точки подчиняются режиму событий.
- Последняя манипуляция — включена; все эпизоды доступны в истории.
- Цели — «Ближайшая» по умолчанию, «Все» или «Скрыть».
- Отмена K — включена при положительном уровне.
- Обратная структура `BOS_REV`/`SMS_REV` — выключена в режиме «Сетап», доступна отдельным переключателем; в «Истории» включена с фильтром типов.

Пользовательский выбор режима и слоёв сохраняется. Для нового пользователя начальные значения соответствуют этой таблице.

## 4. Правила отбора событий

### CH-01. Область и время доступности

Сначала ограничить события точным `setup_id`, инструментом/источником и доступной версией расчёта. Не добавлять события другого сетапа того же актива.

Событие допускается, если его время доступности не позднее `as_of` отображаемого снимка. Для структурного факта это закрытие подтверждающей D1, вычисленное через используемую в проекте границу закрытия. Координата маркера — открытие этой свечи. Для событий жизненного цикла использовать их собственное время рыночного события и связанную свечу.

Не считать время открытия свечи временем подтверждения. При отсутствии корректного `as_of` показать неопределённую свежесть, а не использовать текущее время компьютера как подтверждённую границу данных. ТЗ не добавляет исторический replay; при его дальнейшем появлении фильтр должен принимать отдельный момент просмотра.

### CH-02. События, обязательные для объяснения

В режиме «Сетап» сохранить:

1. Первое подтверждение из `confirmation`, являющееся основанием выбранного сетапа.
2. Зафиксированные входы A/B из `entries`, с исторической датой и фактической ценой/зоной.
3. Подтверждённый выход из диапазона и полученный ретест, если они присутствуют в фактах сценария.
4. Завершение: отмена, истечение срока без ретеста или завершение целей.
5. Достижения целей TP: одна компактная точка на свечу с перечислением достигнутых на ней целей; данные каждой цели сохраняются в деталях.
6. Выбранное пользователем событие из журнала, пока оно выбрано.

Эти факты далее называются ключевыми. Возраст сам по себе их не исключает. Находящиеся вне viewport события показываются в карточке/журнале с действием «К свече»; они не растягивают начальный вид автоматически.

Если одно подтверждение представлено и в `structure_events`, и в `confirmation`/`events`, на графике оно имеет один маркер с перечислением ролей. При отсутствии надёжной связи не угадывать основание по похожей цене: показывать известный факт подтверждения и состояние «Связь со структурной записью не определена» в деталях.

### CH-03. Дополнительная структура в режиме «Сетап»

После выделения ключевых фактов:

- Взять дополнительные структурные события за последние 180 календарных дней до `as_of` снимка.
- Для каждого типа `BOS`, `SMS`, `SSL` оставить только самое позднее событие внутри окна и выбранного сетапа. Сравнивать по времени подтверждения, затем по стабильному идентификатору.
- Событие, уже представленное как ключевое, вторично не рисовать. Поэтому обычный режим содержит не более трёх дополнительных структурных фактов при стандартных настройках.
- При включении обратной структуры аналогично оставить последнее `BOS_REV` и последнее `SMS_REV` за то же окно. Предшествующие обратные сломы остаются в журнале.
- Общий бюджет дополнительных, неключевых маркеров — 8 на видимый участок. Для перечисленных выше типов предел обычно не достигается; резерв нужен для расширений. При превышении выбирать по свежести, с устойчивым порядком по ID.
- Если свежих событий нет, не подставлять старый BOS вместо них. Карточка сообщает «Свежих структурных событий за 180 дней нет» и показывает дату последнего известного отдельно.

180 дней и бюджет 8 — предлагаемые параметры отображения v1. Их изменение не является изменением торговых правил.

Понятие «последний» — визуальное правило, а не признание предыдущего BOS недействительным. Обратный BOS не подписывать как отмену без факта отмены от движка.

### CH-04. История

После правил области/времени показывать все события включённых типов, попадающие в видимый временной участок. Возраст 180 дней и выбор последнего события на тип здесь не применяются.

При плотности дополнительные исторические маркеры объединяются в группы, а не выбрасываются. Бюджет — 24 группы дополнительных маркеров на видимый участок. Ключевые факты учитываются отдельно и тоже могут объединяться по правилам столкновений. В группе доступны все исходные события; лимит ограничивает число визуальных элементов, а не историю.

Список событий показывает всю доступную историю с фильтрами типа/даты. Отфильтрованный график не используется как источник данных этого списка.

### CH-05. Совпадения и столкновения подписей

1. Один фактический источник имеет один визуальный маркер. Идентификаторы событий БД не менять; объединение относится к проекции графика.
2. Если несколько различных событий принадлежат одной свече, группировать отдельно сверху и снизу: например, «BOS +2». Tooltip/панель раскрывают каждый тип, время, уровень и роль. Количество обозначает дополнительные уникальные факты, а не число API-записей одного факта.
3. При столкновении соседних подписей сокращать второстепенную подпись до значка/числа, затем объединять в кластер. Проверять реальные границы текста с отступом минимум 8 CSS px; цветовая стрелка без текста всё равно должна иметь доступные детали.
4. Приоритет видимой подписи: выбранное событие → завершение → вход/ретест/выход → первое подтверждение → цели → дополнительная структура. Остальные элементы представлены в доступной группе или журнале.
5. Если дополнительных исторических кластеров остаётся больше 24, последовательно объединять соседние по времени кластеры одного положения с минимальным расстоянием на экране; при равенстве выбирать более раннюю пару. Повторять до достижения бюджета. В деталях показывать интервал и все события группы.
6. Ключевые факты никогда молча не исчезают из-за бюджета. При столкновениях они входят в группу с явным индикатором ключевого события; выбор из группы выделяет нужную свечу и подпись.
7. При zoom, pan и resize повторно рассчитывать экранные координаты и группировку. Изменение масштаба не меняет исходные факты и список событий.

Плотная история не должна приводить к колонне надписей, которая занимает больше высоты, чем сами свечи. Для v1 потребуется отдельный слой интерактивных маркеров/подписей, если штатный `setMarkers()` не позволяет выполнить правила группировки и раскрытия. Конкретную реализацию выбрать на прототипе; не смешивать два независимых источника маркеров.

## 5. Масштаб, уровни и области

### CH-06. Временной viewport

- Первый выбор объекта: последние 180 доступных закрытых D1; при меньшей истории — доступный фрагмент.
- «Весь диапазон»: от стартовой опоры до последней свечи сценария с полями по 10% временного интервала, минимум 5 D1 с каждой стороны. Если опоры нет, использовать доступные свечи и сообщить об этом.
- «Вся история»: все загруженные свечи; границы доступного фрагмента видны пользователю. `fitContent()` допустим как реализация этой явной команды.
- «К свече»: центрировать выбранное событие, показывая ориентировочно 30 D1 до и после. Если свечи нет в загруженном наборе, показать причину/границу фрагмента, не привязывать событие к соседней свече.
- WS-обновление текущего объекта сохраняет ручной viewport. Если пользователь находился у правого края и следовал за последними свечами, допускается продолжить следование за новой свечой; просмотр старой истории не переключается к настоящему.
- При смене объекта применить его сохранённый viewport в рамках сессии либо начальный вид. Не переносить временное положение другого инструмента автоматически.
- Проверка номера запроса применяется и к обновлениям: поздняя карточка не меняет график, режим или viewport нового выбора.

### CH-07. Ценовая шкала и цели

В режиме «Сетап» автоматическая ценовая шкала строится по high/low видимых свечей с полями 8% диапазона сверху и снизу; нижнюю границу ограничить нулём. При нулевом диапазоне использовать минимальный положительный шаг цены. Далёкие цели и событийные подписи не должны сжимать свечи или расширять шкалу в отрицательные цены.

Линии L/U/M/K и цели в пределах текущей шкалы рисуются на графике. Уровни за пределами шкалы обозначаются компактным индикатором у соответствующего края с названием, ценой и действием «Показать». Это действие явно расширяет шкалу до выбранного уровня; следующий WS-ответ не отменяет ручное решение. Все значения всегда видны в карточке.

«Ближайшая цель» — цель с минимальным положительным расстоянием над последним закрытием D1 среди целей, не отмеченных как достигнутые или пройденные к подтверждению. Если таких нет, сообщить об этом; не подменять цель уже пройденной. Режим «Все» включает все TP, сохраняя правило индикаторов для уровней за пределами шкалы. Достижение цели определяется движком, не положением последней цены.

K ≤ 0: линия и крайний индикатор отсутствуют; цена и объяснение доступны в карточке. Поведение K > 0 подчиняется тому же правилу масштаба. Проверить механизм autoscale на используемой версии Lightweight Charts; при необходимости отрисовать уровни отдельным слоем, который не участвует в автоматическом масштабе.

Подписи близких уровней на оси тоже объединяются: компактная группа цен открывает точные значения. Источник свечей, сетап и версия диапазона используются согласованно во всех слоях.

### CH-08. Области

- Область накопления относится к выбранному диапазону; старые версии показываются в истории по запросу.
- В режиме «Сетап» показывать активный эпизод манипуляции, иначе самый поздний завершённый эпизод, если он пересекает последние 180 дней. Все эпизоды — в режиме истории.
- В режиме «Сетап» незавершённая область ожидания ретеста заканчивается последней доступной свечой или deadline, что наступило раньше. После полученного ретеста область заканчивается фактическим временем первого принятого ретеста. В истории эта завершённая область доступна.
- Текущий код использует `lastOt` при полученном ретесте; заменить это визуальное продление на границу события `retest`. При неизвестной границе не изображать бесконечно действующую область: сообщить о недостатке данных.
- Пустые/невидимые области не создавать. Определять пересечение с viewport явно: `timeToCoordinate() === null` само по себе не означает левый или правый край. Область полностью вне видимого интервала не должна закрашивать весь график из-за fallback-координат.
- Прозрачность и границы областей сохраняют различимость свечей в обеих темах. Приоритет зон и легенда едины для графика и карточки.

## 6. Данные и реализация

### CH-09. Нормализованная проекция

Выделить чистые функции нормализации, отбора и группировки. `renderChart()` получает готовую проекцию, а не объединяет все массивы прямо в `setMarkers()`.

Предлагаемый внутренний контракт:

```text
ChartEvent {
  key, source_ids[], setup_id, source_id,
  type, candle_open_time_ms, available_at_ms,
  level_price?, roles[], importance: key|secondary,
  label, position, details
}

ChartView {
  mode: setup|history|none,
  layers, visible_time_range, price_view,
  as_of_ms, selected_event_key?
}
```

`key` — устойчивый ключ факта; `source_ids` — ссылки на все представления того же факта. Для структуры использовать исходный ID и точную связь с событием жизненного цикла. Если прямой ссылки пока нет, допустимо сопоставление внутри одного сетапа по типу, точной свече и устойчивому `source_event_id` движка; сравнения округлённых цен недостаточно. Не объединять разные типы на одной свече в один факт — только в визуальную группу.

Сегодня detail содержит `structure_events`, `confirmation`, `entries`, `breakout`, `events`, `manipulation_episodes`, свечи и версии. Добавить в read model совместимые поля: `source_event_id` в записи `events`; нормализованную связь подтверждения со структурным событием или явное отсутствие связи; границы/признак усечения загруженной истории. `available_at_ms` можно выводить из существующих фактов и границы закрытия без изменения детектора.

Полную историю оставить в API. Первая версия фильтрует её на клиенте; при дальнейшей серверной пагинации журнал и команды перехода должны уметь догрузить недостающие события/свечи. Нельзя называть загруженный ограниченный фрагмент всей рыночной историей.

### CH-10. Производительность и состояние

- Пересчёт screen layout выполнять максимум один раз на animation frame; кэшировать нормализацию до смены данных/версии.
- Обновлять позиции существующих элементов вместо полной пересборки большого DOM при каждом движении.
- Состояние фильтров событий хранить отдельно от `detail`; новый ответ API не сбрасывает выбор слоёв.
- При отсутствии свечей события остаются в журнале, график показывает понятное пустое состояние.
- После ухода со страницы очищать подписки, observers и обработчики; повторная инициализация не создаёт несколько графиков или обработчиков одной команды.
- Целевой бюджет чистого отбора/группировки — p95 ≤ 16 ms на fixture из 3000 событий и 2000 D1 при ширине графика 1000 CSS px. Измерять на одной зафиксированной машине, записать браузер/CPU; DOM и canvas измерять отдельно. Это критерий будущей реализации, не текущий результат.

## 7. Критерии приёмки и проверки

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| C01 | История HBAR со скриншота или эквивалентная плотная fixture | В обычном режиме нет ковра BOS/BOS_REV/SSL; свечи и диапазон читаются, доступен журнал |
| C02 | 300 старых BOS/SMS/SSL и несколько свежих | Дополнительно показано максимум последнее событие каждого разрешённого типа за 180 дней; ключевые факты сохранены |
| C03 | Первое подтверждение старше 180 дней | Оно остаётся в карточке/журнале и доступно через «К свече»; viewport не расширяется автоматически |
| C04 | Историческое восстановление с `historical=true` содержит основание сетапа | Основание не скрывается только из-за `historical` |
| C05 | BOS_REV/SMS_REV без отмены | По умолчанию скрыты; при включении подписаны как обратная структура, стадия и K не меняются |
| C06 | BOS + SMS + вход на одной свече; дубликат BOS в outbox | Один факт BOS, отдельные реальные SMS/вход в раскрываемой группе; количество не завышено |
| C07 | Zoom-out на нескольких сотнях событий | История группируется до бюджета второстепенных кластеров, все факты доступны из группы/журнала; zoom-in раскрывает детали |
| C08 | WS-обновление при просмотре 2023 года | Выбранный объект и viewport сохраняются; новая свеча не переводит пользователя к последним датам |
| C09 | TP4 далеко над ценой; K ≤ 0 | Свечи не сжаты TP4; цель доступна в карточке/крайнем индикаторе; K не рисуется, шкала не уходит в минус |
| C10 | Получен ретест; затем прошло много дней | Область ожидания заканчивается на принятом ретесте, а не тянется до сегодняшней свечи |
| C11 | Манипуляция полностью вне viewport | Нет ложной заливки всего графика; последний/активный эпизод выбирается по §5 |
| C12 | Событие позже `as_of`; свеча ещё не закрыта на границе снимка | Маркер не появляется до доступности подтверждения |
| C13 | Два сетапа одной монеты; быстрая смена строк | События не смешиваются; поздний ответ первого запроса игнорируется |
| C14 | Нет свечи события из-за лимита истории | Событие есть в журнале, переход сообщает об отсутствии свечи; маркер не смещается на другую дату |
| C15 | Переключения «Сетап / История / Без событий» и слоёв | Меняется только представление; после перезагрузки выбор восстанавливается |
| C16 | Ближайшая цель ранее пройдена или нет ожидающих целей над ценой | Используется правило CH-07, не показывается ложная новая цель |
| C17 | Светлая/тёмная тема, 1440×900, 1366×768, 390×844 | Подписи читаемы; toolbar сверху; уровни и свечи не перекрываются служебными блоками |
| C18 | Смена режимов и последующий ручной/дневной прогон | Число и ID событий, входы, targets, состояние сетапа и отправка уведомлений не изменяются из-за визуальных фильтров |

Для чистых функций добавить тесты отбора, границ 180 дней/as_of, причинных связей и группировки. API-проверки покрывают совместимые новые поля и неизменность полной истории. UI-проверки покрывают фактические столкновения текста, viewport, темы, слои и гонки ответов. Существующие `tests/test_alt_api.py` и `tests/test_alt_engine_events.py` использовать как регрессионную основу; зелёные backend-тесты не заменяют визуальную проверку.

## 8. Порядок внедрения

1. Добавить нормализацию и точные связи фактов, сохранив исходные массивы API.
2. Внедрить режим «Сетап» и доступный журнал одновременно; убрать безусловный вывод всей структуры.
3. Исправить viewport, компоновку графика, ценовой масштаб и управление уровнями.
4. Добавить историю, группы, выбор события и переход к свече; исправить границы областей.
5. Проверить критерии C01–C18 и зафиксировать сравнительные скриншоты для одних и тех же данных/viewport.

Готовность: обычный график читается, исходное объяснение сетапа сохранено, любую скрытую запись можно найти и открыть, обновления не сбрасывают работу пользователя.
