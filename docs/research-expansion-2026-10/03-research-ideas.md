# ТЗ 03. Исследовательские идеи

## Реализованный объём на 16.10.2026

I1–I3 доступны в Market Researcher: отдельный lifecycle, неизменяемые версии тезиса/критериев/источников, снимки HTF/LTF, ручной пересмотр, очередь оснований пересмотра, эпизоды baseline и горизонты 1/3/7/30d. Из STVTerminal перенесены исходные analytics и validation; Python связывает их с текущими котировками и общей БД. Из оригинального ZIP импортированы 13 идей как локальные draft с сохранённым внешним происхождением. В I4 реализован явный AI-черновик по сохранённым источникам: проверяются буквальные цитаты, результат всегда draft. Автоматические push-напоминания для исследовательских идей не включены; пересмотр доступен в UI.

Фактические модули: app/research/ideas.py, records.py, market.py; API — app/web/research_workbench_api.py; UI — research_workbench.js. Дополнительные маршруты: POST /ideas/import, /ideas/prepare-draft, /ideas/{id}/refresh; GET /instruments/{id}/research-links. Список и история используют cursor; outcomes содержат первоначальный и последующие эпизоды. Неизвестная цена не становится нулём, внешний baseline не становится локальным наблюдением.

Проверки: tests/test_research_workbench.py на SQLite/PostgreSQL, tests/research_workbench_ui_check.cjs на изолированной БД. Требования ниже сохраняют целевую постановку; фактические ограничения и общий протокол проверки находятся в README.

Дата: 15.10.2026. Версия: research-ideas-1.0. Статус: запланировано. Общие контракты — [README](README.md), источники — [01](01-asset-information-context.md), катализаторы — [02](02-catalyst-calendar.md).

## 1. Назначение

Сохранять проверяемую исследовательскую гипотезу и основания решения. Идея объясняет механизм влияния на актив, ожидаемые подтверждения, условия опровержения, горизонт и связь с техническим сценарием. Последующий результат привязан к сохранённой версии и времени, а не к отредактированному задним числом тезису.

MVP: ручное создание, источники, критерии, версии, связи с активом/сценарием, ручные пересмотры и описательный результат цены. Модель может подготовить черновик только на следующем этапе; создание подтверждённой идеи всегда является действием пользователя.

## 2. Различие сущностей

| Сущность | Источник и назначение |
|---|---|
| HTF-идея | Существующая htf_idea; происхождение HTF/H1-зон и технический lifecycle |
| LTF-попытка / сценарий | Существующие observations/scenarios/entry zones; структурные условия |
| Исследовательская идея | Новая research_idea; тезис о проекте, событии, нарративе или риске |
| Модельная корзина | Набор активов и весов для проверки гипотезы; ТЗ 04 |
| Торговая стратегия | Исполняемые правила входа/выхода и затрат; ТЗ 06 |

Новая идея ссылается на технические сущности через тип/ID/версию. Отмена H1-попытки не закрывает исследовательский тезис автоматически; фундаментальное опровержение не переписывает BOS и HTF lifecycle. Пользователь видит расхождение и получает задачу пересмотра.

Переиспользовать концепции stvterminal services/investment-ideas: sources, cancel rules, history и asset resolution. [Исходный модуль](https://github.com/seytuev/stvterminal/tree/af1b0b3a74f28b61b8c44b423a895610af92c418/site/services/investment-ideas). Денежный P&L, портфельный ledger и реальные позиции в этот перенос не входят.

## 3. Сценарии пользователя

1. Из информационной карточки или календаря — «Создать идею»: форма получает ссылки на конкретные версии материалов/событий и подтверждённый актив.
2. Из рабочего места — «Сохранить исследовательскую идею»: прикладывается технический снимок текущего инструмента, но тезис заполняется отдельно.
3. Ручное создание без найденного биржевого инструмента допустимо для подтверждённого research_asset; техническая связь и цены остаются отсутствующими.
4. Пользователь формулирует подтверждение и опровержение, выбирает горизонт, сохраняет как draft либо переводит в watching.
5. Поступает новая версия катализатора/отмена технического сценария: появляется запрос пересмотра с новым свидетельством; пользователь отмечает смысл изменения.
6. При завершении пользователь фиксирует заключение и сопоставляет его с первоначальным тезисом и наблюдаемой динамикой.

## 4. Модель данных

research_idea: id (UUID), owner_scope, created_at, current_revision_id, status, archived_at. На первом этапе owner_scope — существующий приватный владелец приложения; это не обещание многопользовательского продукта. Копия идеи создаёт новый ID с copied_from_id и собственным временем.

research_idea_revision:

| Поле | Требование |
|---|---|
| title | 5–200 символов |
| primary_asset_uid | Подтверждённый актив; для draft может отсутствовать |
| related_assets | Связанные активы и тип связи |
| thesis | 20–8 000 символов, собственно гипотеза |
| mechanism | Как наблюдаемый факт может влиять на актив |
| direction | positive/negative/neutral/watch; исследовательская направленность |
| horizon | starts_at, review_due_at, horizon_label; без выдуманной даты |
| status | Состояние на момент версии |
| source_refs | Тип/ID/revision_id источников |
| criteria | Версионные подтверждения и условия опровержения |
| technical_refs | Ссылки и зафиксированные технические снимки |
| author_note | Пояснение пользователя |
| provenance | manual/imported/ai_draft/copy |
| version metadata | revision_id, parent_revision_id, available_at, actor, reason, content_hash |

research_idea_criterion: id, idea_revision_id, type (confirmation/invalidation/review_trigger), description, evaluator (manual/catalyst_stage/technical_transition/date), parameters, required_evidence. Версия критерия неизменяема. Автоматические критерии используют только allowlist событий и серверную валидацию параметров; произвольный Python/SQL/JS из формы запрещён.

research_idea_review: id, idea_id, reviewed_revision_id, trigger_ref, verdict (supports/weakens/refutes/inconclusive), explanation, evidence_refs, actor, available_at, resulting_revision_id. research_idea_transition сохраняет изменения состояния и причины.

research_idea_link: idea_id, linked_kind, linked_id, linked_revision_id, role, created_at. Материал и technical_snapshot сохраняются как свидетельства конкретной версии. Недоступность текущего live-объекта не уничтожает сохранённое основание.

research_idea_price_baseline: id, idea_revision_id, instrument_id, quote_source, quote_kind, price, observed_at, available_at, quality, baseline_policy. research_idea_outcome: baseline_id, method_version, horizon, target_at, observed_at, price, return_pct, benchmark_return_pct, excess_return_pct, quality, computed_at.

## 5. Lifecycle

Состояния: draft → watching → supported/disputed → resolved/invalidated → archived. Supported/disputed могут возвращаться в watching после нового пересмотра. Resolved означает завершение исследования, а не обязательную правоту. Invalidated означает признанное опровержение. Archived сохраняет final_status и закрывает обычное наблюдение.

Допустимые переходы задаются явной таблицей в коде. Любая смена требует reason; для invalidated/resolved — заключение и ссылка на критерий/свидетельство либо явная пометка ручного решения. Восстановление завершённой идеи создаёт новую ревизию и новый эпизод наблюдения, сохраняя прежний результат. При полностью новом тезисе — новая идея с relates_to.

Перевод draft в watching требует актива, thesis, mechanism, хотя бы одного критерия опровержения и даты/условия пересмотра. Отсутствие численной цели допустимо. Недоступная котировка не мешает сохранить тезис, но baseline остаётся unavailable.

Автоматическая задача умеет отметить «условие требует пересмотра» и собрать свидетельства. В MVP она не меняет supported/disputed/invalidated без пользователя. При техническом разрыве данных создаётся data_unavailable, а не refutes.

## 6. Версии и историческая честность

Любое изменение тезиса, направления, критериев, источников или связанного сценария создаёт revision. Редактирование отображаемого заголовка также журналируется. Сравнение версий показывает изменённые поля и время; старый результат не пересчитывается по новой гипотезе.

Из stvterminal импортировать идею как imported draft с внешними created_at и source_observed_at, но local available_at — фактическое получение. Импорт не приписывает нам наблюдение с исторической даты. Для истории результата допускается внешний baseline при известном источнике, времени и методике; он подписан отдельно от локального.

Ручная правка не стирается автоматическим обновлением импортированной записи: сохраняются external_revision и локальная revision; конфликт приходит на пересмотр. Удаление источника в терминале не удаляет идею и её аудит.

## 7. Результат и котировки

По умолчанию baseline фиксируется при первом переходе в watching. Используется первая валидная наблюдаемая котировка выбранного инструмента не раньше времени активации. Максимальное ожидание свежей котировки — 15 минут; при отсутствии baseline=unavailable, без подстановки поздней цены под старую дату. Политика и предел конфигурируются и версионируются.

Изменение тезиса не заменяет исходный baseline. Новый эпизод имеет отдельный baseline; UI позволяет посмотреть первоначальный и текущий эпизоды. Quote source, market type, quote currency и единицы должны совпадать в начале/конце расчёта. Несопоставимые провайдеры не смешиваются без явной методики.

Описательные горизонты первой версии: 1/3/7/30 дней от baseline. Для каждого целевого момента берётся первая закрытая H1 с close boundary не раньше target_at и не позднее target_at + 1 час; сохраняется фактическое observed_at. Если данных нет/свеча не закрыта — pending/missing; не брать ближайшую свечу из будущего без допуска. Доходность = (P1/P0 − 1) × 100%. Методика называется quote_to_h1_close_v1.

Для сравнения с BTC обе доходности считаются на одинаковых фактических временах и в сопоставимой валюте; excess_return_pct — разница процентных доходностей. «Short» не создаёт реализованный результат короткой позиции: отрицательное направление тезиса оценивается отдельно, без выдуманных funding/маржи.

Не показывать P&L сделки, win rate стратегии или успешность тезиса только на основе роста цены. Описательные изменения цены и заключение пользователя — два отдельных блока. Для сценариев входа/выхода используется лаборатория из 06.

## 8. API

| Метод и путь /api/research/v1 | Назначение |
|---|---|
| GET /ideas | status, asset_uid, due_before, text, cursor, limit; поиск серверный |
| POST /ideas | Создание draft/watching, Idempotency-Key |
| GET /ideas/{id} | Текущая ревизия, актив, связи и состояние данных |
| PATCH /ideas/{id} | Новая ревизия, expected_revision и reason |
| POST /ideas/{id}/transition | Разрешённый переход, причина, expected_revision |
| POST /ideas/{id}/reviews | Сохранение пересмотра и свидетельств |
| POST /ideas/{id}/links | Добавление типизированной связи с версией |
| GET /ideas/{id}/history | Ревизии и пересмотры; cursor |
| GET /ideas/{id}/outcomes | Эпизоды, baseline и описательные горизонты |

API проверяет существование объектов и принадлежность правам владельца. Техническая ссылка на другой актив возвращает 422, если не задана explicit contextual relation с пояснением. Просмотр старой версии не подменяется текущей. Конфликт expected_revision — 409 с актуальным ID, без потери черновика формы.

## 9. Интерфейс

Новый раздел «Исследования → Идеи» вводится при готовности списка и редактора; до этого допустима ссылка из рабочего места. Не переименовывать действующие HTF/H1-понятия. Везде полная подпись «Исследовательская идея», если рядом есть техническая идея.

Список: актив, заголовок, статус, горизонт, следующий пересмотр, последнее изменение и качество baseline. Фильтры: мои наблюдаемые, требуют пересмотра, завершённые, актив. Сортировка и поиск серверные; показывать число отобранных, а не только загруженных строк.

Карточка: тезис/механизм; подтверждения/опровержения; источники; технические связи; история; результат. Кнопка «Сохранить» явно показывает draft или watching. Для изменения после старта выводить «Будет создана новая версия». Форму не очищать до успешного ответа.

В рабочем месте компактный список до 3 действующих идей выбранного актива. Несовпадение исследовательской направленности и H1 выводить как различие наблюдений с временами срезов. Не генерировать общий торговый вердикт.

## 10. Фоновые задачи и напоминания

Задания: фиксация baseline, сбор outcomes, проверка due_at, обработка новых версий связанного события/технического перехода. Каждый review-trigger дедуплицируется по idea_id, criterion_version и evidence_revision. Задача не читает произвольную текущую карточку вместо сохранённого снимка.

MVP показывает очередь пересмотра в UI. Push позже, по отдельному включению: одна сводка задач пересмотра, без повторного создания идеи. Просроченный review не означает автоматическую отмену гипотезы. Отложить пересмотр — отдельное действие с due_at и историей.

## 11. Этапы

1. I1: CRUD draft/watching, версии, критерии, источники, ручной review и список.
2. I2: связи с техническими snapshot и катализаторами; очередь пересмотра и диагностика.
3. I3: baseline, горизонты, benchmark и история эпизодов.
4. I4: импорт внешних идей, AI-черновик и опциональные напоминания. AI-черновик показывает модель и исходные материалы; не принимается сам.

## 12. Критерии приёмки

- I01: отмена LTF-попытки не закрывает исследовательскую идею; опровержение идеи не меняет технические таблицы.
- I02: watching нельзя создать без требуемых полей, но неизвестная цена сохраняется отсутствующей.
- I03: новая версия тезиса сохраняет первоначальный текст, критерии, baseline и результат.
- I04: двойное создание/повтор review после timeout не создаёт второй объект; конкурирующее редактирование получает 409.
- I05: импорт старой идеи не становится локально известным историческим сигналом.
- I06: источник и связанный сценарий раскрываются в тех версиях, на которые принято решение.
- I07: baseline получен не раньше активации; опоздавшая котировка не маскируется; разные рынки/валюты не смешаны.
- I08: 1/3/7/30d считаются по зафиксированной методике, с фактическим временем и missing при пробеле.
- I09: хороший ценовой исход не переводит тезис автоматически в supported; ручной вывод и цена разделены.
- I10: после перезапуска задания baseline/outcome/review восстановлены и идемпотентны.
- I11: роли/Origin, длинные тексты, темы и 390 px проверены; UI сохраняет несохранённый draft при ошибке.
- I12: 5 000 идей с версиями и 50 000 пересмотров читаются через индексы/пагинацию в p95 ≤ 500 мс на стенде README.

Проверки: таблица переходов; optimistic concurrency; время baseline; единицы котировок; исторические версии; import conflict; референциальная целостность; сценарий полного жизненного цикла в браузере. Расчёт доходности сравнивается с ручным примером, а не только с повтором формулы в тесте.
