# Запуск и восстановление LevelFrame

Рабочая версия стабилизации требует Python 3.11 или 3.12, установки зависимостей по `requirements.lock` и сборки локального ресурса графика. Приёмка изменений пока частичная; статус находится в [отчёте реализации](LevelFrame_Stabilization_Implementation_RU_2026_10_13.md).

## Подготовка окружения

Использовать исправный обычный CPython. Существующая `.venv` этой рабочей копии ссылается на недоступный в текущей среде Windows Store Python 3.11. Её бинарные зависимости нельзя переносить в Python 3.12 через PYTHONPATH для полного запуска.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --constraint requirements.lock ".[dev]"
.\.venv\Scripts\python.exe tools/build_static.py
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m app.main
```

`build_static.py` получает фиксированный пакет lightweight-charts 4.2.0 из npm, проверяет SHA-512 архива по метаданным пакета и сохраняет standalone JS в `app/web/static/vendor`. HTML использует этот локальный ресурс. До его сборки график не готов к запуску. Docker выполняет сборку автоматически перед установкой приложения; wheel необходимо строить после этой команды.

Настройки процесса и секреты задаются через ENV или локальный `.env`. Для публичного размещения требуются собственный `HTF_AUTH_TOKEN`, `HTF_PUBLIC_BASE_URL` с HTTPS и writable persistent volume. Контейнер запускается от UID 10001; права тома должны разрешать этому UID запись. Постоянный токен вводится только при входе и обменивается на HttpOnly-сессию; ссылки объектов не содержат токена.

## Состояние процесса

`/api/live` — минимальная liveness-проверка. `/api/ready` сообщает готовность расчёта и отвечает 503 при незавершённой подготовке, отсутствии владельца или устаревшем heartbeat. В Railway для проверки процесса используется `/api/live`, чтобы отказ биржи не создавал цикл рестартов.

Защищённые `/api/diagnostics` и `/api/diagnostics/metrics` показывают версии, владельцев, очереди, ошибки и временные показатели. Состояние заданий настроек доступно через `/api/settings/jobs/{job_id}`. Клиент должен отправлять `expected_config_version`, полученный в GET settings; 409 требует повторного чтения профиля.

## Восстановление очереди

Каждый принятый тик имеет durable receipt. Ошибка расчёта оставляет retry; после предела попыток — quarantine. Следующие тики инструмента ждут исправления предыдущего. POST `/api/diagnostics/quotes/{row_id}/retry` возвращает ошибочную запись в pending. Сначала необходимо устранить причину ошибки и проверить состояние инструмента.

Статус processed остаётся как квитанция дедупликации. При выключении инструмента pending/retry получают явный cancelled с причиной `instrument_disabled`; история записи сохраняется. Quarantine остаётся для расследования. Отдельный `market_publication` восстанавливает доставку уже зафиксированных рыночных событий.

Сетевой результат uncertain не повторяется автоматически. Сначала сверяется фактическая доставка: повтор может создать второе сообщение Telegram.

## Резервные копии

При активном calc-владельце maintenance проверяет свободный диск и выполняет ежедневную SQLite backup. Настройки: `HTF_BACKUP_ENABLED=1`, `HTF_BACKUP_INTERVAL_HOURS=24`. Последняя успешная копия отмечается в `maintenance:last_backup_at`; ошибки записываются в журнал. Для внешнего контроля проверять возраст этой метки и `disk_degraded`.

Ручная копия:

```powershell
python tools/maintenance.py backup --db data/htf_zones.db --destination data/backups/manual-2026-10-13
python tools/maintenance.py verify --db data/backups/manual-2026-10-13/htf_zones.db
```

Backup SQLite и профиль согласованы одной read-транзакцией. Копии charts и labels являются дополнительными файлами; при одновременной записи их согласованность с SQLite отдельно не доказана. Для полной эксплуатационной копии на время сбора этих файлов остановить writer и delivery. Источник рыночного состояния, ревью и доставки — SQLite.

Retention удаляет обработанные квитанции, завершённые публикации, истёкшие браузерные сессии и старые завершённые sync jobs. Pending/retry/quarantine, uncertain, рыночные события, ручная разметка и снимки пользовательских решений остаются. Автоматическая ротация каталогов backup пока не реализована; их объём контролируется отдельно.

Для восстановления остановить все экземпляры сервиса, проверить integrity и foreign keys копии, сохранить повреждённую базу отдельно, затем восстановить SQLite и профиль в чистый каталог тома. Запустить один экземпляр и проверить ownership, курсоры, очереди и uncertain. RPO/RTO для потери диска требуют отдельного протокола восстановления на объёме production.

## Обновление схемы

Версия схемы стабилизации — 2. Миграция добавляет receipts, публикации и сессии, сохраняя пользовательские данные. Старые экземпляры с PID-владением необходимо остановить до миграции: они не понимают fencing generation.

Возврат старого приложения поверх новой схемы не принят. Для отката использовать проверенную копию предыдущей схемы; новые pending после её создания требуют отдельного переноса. Этот переход нельзя считать обычным переключением образа без проверки данных.

## Проверки выпуска

CI содержит Linux/Windows pytest, wheel/Docker smoke и браузерные проверки трёх размеров. GitHub-публикация текущей работы заблокирована политикой инструментов, поэтому этот CI пока не запускался. Нагрузочные 100/500 тиков в секунду и 24-часовой soak также ещё необходимы.
