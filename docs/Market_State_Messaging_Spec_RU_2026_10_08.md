# ТЗ: точные сообщения о контексте, структуре и сценарии

Дата: 8 октября 2026. Статус: план реализации, без изменения приложения. Основание: три пользовательских скриншота BTC и проверка текущего кода. Связанный документ: [аудит качества движка](Quality_Audit_and_Radical_Upgrade_Plan_RU_2026_10_08.md).

## 1. Цель и границы

Карточка должна однозначно отвечать: **где цена; какой контекст выбран и почему; что подтверждено на H1; какое следующее условие проверяется; что завершит наблюдение или отменит сценарий**.

Каждое утверждение опирается на факт движка, его время и источник. Краткий заголовок сообщает одну главную стадию. Сведения о других зонах, ликвидности, качестве данных и ручной проверке показываются отдельно.

В работу входят серверное представление состояния, карточки «Сейчас» и рабочего места, подписи графика, связанные Telegram-сообщения, формат цен и времени, согласованность снимка и тесты. Для альткоинов используется тот же словарь фактов; сообщения перечислены отдельно. Перенастройка стратегии, новый поиск зон и изменение правил входа этим ТЗ не предписаны. Несогласованности расчёта исправляются отдельными изменениями с регрессиями; текст не должен их маскировать.

| D04 | _contained_context_note() называет завершённую ручную медвежью зону «закрытой пробоем вверх» по одному display_until | Причина из lifecycle-события/end_reason; без доказательства — «Причина завершения не записана» |

Ожидаемые уровни сейчас вычисляет отдельная эвристика _expected_levels(). Не считать её автоматически эквивалентной BOS/SMS-машине: наличие внутреннего уровня ещё не означает выполнение всех предпосылок SMS. Условия и их готовность должны приходить из той же машины, которая зарегистрирует событие.

## 3. Словарь

| Термин | Значение в интерфейсе |
|---|---|
| Контекст | Старшая зона, в связи с которой ведётся наблюдение; это не прогноз и не готовый вход |
| Бычий / медвежий контекст | Наблюдение за возможной реакцией вверх / вниз; текущая H1-структура может быть противоположной |
| Кандидат OB | Найдена геометрия основания, но условия рыночного подтверждения ещё не выполнены |
| Рыночное подтверждение OB | Подтверждающий FVG вне основания в направлении выхода по действующим правилам; не равно нажатию кнопки review |
| BOS / SMS | «Пробой структуры вверх/вниз (BOS)» / «Изменение внутренней структуры вверх/вниз (SMS)» — разные события движка |
| Сценарий | Состояние после соответствующего подтверждённого события; может ждать диапазон и не иметь пригодных зон |
| Зона наблюдения за входом | Зона, прошедшая текущие фильтры; касание само по себе не подтверждает вход |
| Завершение зоны | Терминальный переход lifecycle с причиной и временем; не равно закрытию реальной позиции |
| Ручная зона | Способ создания; торговой смысл задаётся типом OB/FVG и направлением |
| Проверка пользователем | Отдельная оценка разметки, которая не подменяет рыночную стадию |

Не использовать «лонг готов», «точка входа», «разворот подтверждён» только по касанию, направлению HTF-зоны или произвольному LH/HL. По умолчанию называть подтверждённый факт структуры.

## 4. Устройство карточки

Порядок фиксирован; пустые необязательные блоки скрываются, неизвестное существенное условие объясняется.

1. **Инструмент:** BTC / USDT · Binance Spot. Цена и время котировки. Не показывать один W1 так, будто вся карточка рассчитана только на нём.
2. **Главный статус:** одна фраза, например «Ожидаем подтверждения роста на H1». Цель — до 70 символов для шаблонов, без обрезки важных данных.
3. **Достоверность:** при проблемах — «H1 обработана по 17:00 МСК; закрытая свеча 18:00 ещё не рассчитана».
4. **Выбранный контекст:** тип, ТФ, направление, границы, состояние, причина выбора.
5. **Положение цены:** внутри / выше / ниже / на границе выбранной зоны. Это геометрия, не lifecycle.
6. **H1:** подтверждённый факт или отсутствие подтверждения. Называть структуру восходящей/нисходящей только при наличии серверной классификации.
7. **Следующее условие:** уровень, сторона, ТФ, строгость сравнения, необходимость закрытия и дополнительные предпосылки. Если уровня нет — какая опора отсутствует.
8. **Завершение/отмена:** до сценария — завершение контекста; после — отмена H1-сценария и отдельно правило родителя, если оно влияет на сценарий.
9. **Другие зоны и факты:** до двух зон и трёх событий, остальные — «Ещё N». Блокирующую причину не прятать в свёрнутой части.
10. **Проверка разметки:** «BTC: 12 зон ожидают вашей проверки»; общий счётчик подписан «По всем активам». Ссылка открывает ту же выборку.

Заголовок не повторяется в других блоках. «Что происходит» удалить как дублирующий раздел либо использовать для нового факта. На ширине 360 px нет горизонтального скролла; причины и условия читаются целиком. Направление передаётся текстом и стрелкой, а не только цветом.

## 5. Функциональные требования

### F01. Единый источник смысла

Сервер возвращает коды сообщений и параметры фактов. Веб и Telegram используют общую версионированную систему шаблонов. Не восстанавливают направление, отмену и причину завершения по тексту, цвету, последнему видимому pivot или одному display_until.

### F02. Время и источник

«Сейчас» требует актуальности зависимых данных. Свежая котировка не доказывает свежесть H1; свежая H1 не доказывает свежесть цены. Сопоставлять один инструмент, площадку и тип рынка. Время — МСК, для несегодняшних событий с датой. Для подтверждения указывать время закрытия свечи.

### F03. Нельзя ждать свершившееся событие

Если BOS/SMS зарегистрирован, показать факт и следующую стадию. Если свеча закрылась за уровнем, но предпосылки машины не были выполнены, назвать недостающее условие; не обещать, что одного повторного закрытия достаточно. При отставании расчёта — «Рассчитываем структуру H1» с курсором/статусом задачи, а не «Ждём пробой».

### F04. Точные условия BOS/SMS и отмены

Условие содержит: kind, level, side, timeframe, requires_close, strict, ссылки на опоры, available_at, prerequisites, status. Статусы: unavailable, waiting_prerequisite, ready, occurred, superseded.

Если доступны BOS и SMS, показать их отдельно и указать, какое событие открывает сценарий по профилю. «Любое из двух» разрешено только при соответствии машине. SMS без требуемого отката: «Уровень SMS: {S}. Сначала нужен подтверждённый откат; одного закрытия выше {S} пока недостаточно».

Отсутствующий уровень не заменять нулём, ближайшим LH или голым «Не определено». Пример: «Уровень подтверждения ещё не определён: после минимума нет подтверждённой опоры». Число оставшихся правых свечей брать из движка и обозначать условность: кандидат может исчезнуть при новом экстремуме.

### F05. Геометрия не равна жизненному циклу

- Цена ниже бычьего OB не означает его отмену. По текущим правилам нужно закрытие свечи собственного ТФ за дальней границей. «Закрытия D1 ниже {L} ещё нет» допускается только при проверенных закрытых D1.
- FVG завершается при полном заполнении. Не вводить ожидание закрытия W1 для завершения недельной FVG.
- Для бычьей FVG доказанный тест после подтверждения до нижней границы должен согласованно завершить lifecycle и зависимое наблюдение. Проверить время, источник и наблюдавшееся движение.
- Одна цена за зоной без достаточной истории не позволяет выдумать время/порядок заполнения. При противоречии — «Статус зоны уточняется», сверка и статус queued/running/resolved/error. После ошибки — причина и действие «Повторить расчёт»; не оставлять бесконечное ожидание.
- Глубоко протестированный, но действующий OB может оставаться контекстом и быть непригодным для нового входа. Назвать оба свойства.

### F06. Причина завершения ручной зоны

Явно сопоставить end_reason и lifecycle-события: заполнение FVG, подтверждённый пробой, ручное закрытие, архивация, замена/миграция, неизвестная причина. «Пробой вверх» — только по соответствующему основанию; назвать ТФ, закрытие/пересечение согласно правилу, уровень и время. Legacy без причины: «Ручная зона завершена {T}. Причина завершения не записана». Возврат цены не возобновляет старый объект.

### F07. Несколько контекстов

Существующую политику выбора не менять скрытно. Показать основание: ручной выбор, цена внутри, ближайшая зона, последний действующий сценарий/контакт. Близость — причина навигации, не оценка качества.

При противоположных направлениях — бейдж «Есть контексты вверх и вниз», выбранный и альтернативный с их стадиями. При завершении выбранного — причина смены. Ручной выбор не сохраняет невалидный контекст.

### F08. Приоритет и независимые состояния

Разделить market_stage, context_state, structure_state, data_state, review_state, direction_conflict. Главный статус:

1. Несогласованный снимок/ошибка данных, делающая вывод невозможным — ограничение вывода.
2. Анализ отключён/идёт обязательный расчёт — состояние процесса и время последнего достоверного результата.
3. Подтверждённая отмена/завершение выбранного сценария — факт и следующий шаг выбора.
4. Текущая стадия выбранного действующего контекста.
5. Отсутствие контекста с конкретной причиной.

Проблема только котировки запрещает «цена сейчас внутри», но не скрывает достоверный BOS по свежим закрытым свечам. Ошибка только Telegram не меняет рыночную стадию. Review не заменяет главный статус.

## 8. Цены и время

- Разделять тысячи пробелом: 81 951; десятичный разделитель — запятая. Убирать незначащие нули, сохранять точность малых цен: 0,001678.
- Для биржевых уровней учитывать tick size, а не универсальные 2/8 знаков. Без научной нотации в обычной карточке.
- Произвольные ручные границы хранить без изменения. Компактное округление отмечать ≈; точное значение доступно в деталях и копировании. Условие не округлять до другой цены без обозначения приблизительности.
- Различные уровни не должны выглядеть одинаковыми: при совпадении строк увеличивать точность/раскрывать детали.
- При неизвестном tick size использовать безопасное число значащих цифр, не изображать отсутствующую точность.
- Раздельные отметки: «Котировка на…», «H1 обработана по…», «Событие подтверждено…». Один бейдж «26 с назад» не означает свежесть всех слоёв.

## 9. Контракт данных и согласованность

Добавить совместимый блок presentation, сохранив старые поля на время перехода:

| Поле | Содержание |
|---|---|
| schema_version, snapshot_id, as_of | Версия формы, идентификатор согласованного снимка, время решения |
| instrument_id, source, ruleset_id, data_version | Однозначные инструмент/источник и версии анализа/данных |
| headline | code, params, evidence_refs |
| context | zone_id, состояние, направление, selection_reason |
| location | inside/above/below/boundary/unknown, quote_at, quote_version |
| structure | state, processed_through, факты подтверждения |
| next_conditions, termination_conditions | Условия F04 с предпосылками и статусами |
| other_zones, liquidity_facts | Самостоятельные объекты с причинами и временем |
| data_issues | Канал, причина, влияние на вывод, статус восстановления |
| review | count, scope, фильтр перехода |

Каждое существенное сообщение имеет ссылку на объект/событие, фактическое время и зависимые каналы данных. Exception/traceback остаются в диагностике, не становятся пользовательским текстом.

Цена и положение относительно зоны обновляются согласованно: новый снимок либо серверная дельта с совместимой версией контекста. Запрещено старое «внутри» рядом с новой ценой ниже зоны. Поздний ответ отбрасывается; смена BTC/ETH не смешивает данные. Перезагрузка не меняет смысл при том же snapshot.

Telegram: подтверждённое событие, время, контекст, условие и ссылка на объект. Историческая досылка: «Подтверждено {T}; сообщение доставлено с задержкой». Старое событие не называть новым входом. Повтор доставки того же event ID не создаёт новый факт. Допускается разная длина сообщений, но не разные причины/условия.

## 12. Ближайшая итерация

Сначала исправить ложные причины завершения, ожидание по завершённому родителю и несовпадение отображаемых условий с BOS/SMS-машиной. Затем разделить карточку, убрать повторы, отформатировать цены и показать точное следующее условие. После этого распространить словарь на обзор, график, Telegram и диапазоны альткоинов.

Результат: один выбранный контекст, проверенное состояние H1, точное следующее условие и отдельные объяснения остальных зон.
