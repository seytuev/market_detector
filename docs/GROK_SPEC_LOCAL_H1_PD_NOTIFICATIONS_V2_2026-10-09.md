# ТЗ v2 для Grok: локальный PD текущего движения H1 и содержательные уведомления

Дата: 09.10.2026. Проект: htfdec. Задача: реализовать изменения движка, API, графиков и уведомлений по описанным ниже правилам.

## 1. Приоритет требований

Это новое ТЗ уточняет `GROK_SPEC_HTF_CONTEXT_H1_REVERSAL_2026-10-09.md` и имеет приоритет при конфликте правил PD, выбора текущего движения и уведомлений. Сохранение HTF-контекста после отработки источника, независимый lifecycle зон, отсутствие look-ahead и дедупликация из предыдущего ТЗ сохраняются.

Ключевое уточнение: нельзя бессрочно использовать исходный LL/HH старой идеи как начало текущего H1 PD. Якорь сохраняется в пределах своей причинной ноги; новый самостоятельный импульс с BOS получает собственный локальный диапазон. Старые ноги и зоны доступны в истории, но не выдаются за текущие.

## 2. Проблема по трём скриншотам

1. На первом графике цена около 83 тыс., но показан H1 PD 109 561,59–112 500,00 с EQ 111 030,79. Этот диапазон не описывает текущее движение.
2. На втором — PD 87 895,98–91 442,88 с EQ 89 669,43. Бот показывает другой старый диапазон для другого HTF-родителя, хотя текущие свечи инструмента те же.
3. На третьем диапазон 80 393,56–82 776,01 с EQ 81 584,79 ближе к текущей цене, но одна близость не доказывает корректность. После BOS вверх верхняя граница должна соответствовать наблюдаемому экстремуму текущей восходящей ноги, даже если он ещё не подтверждён как pivot. Следует показать потенциальные OB/FVG именно этой ноги.

Нельзя просто заменить числа на значения со скрина или добавить фильтр расстояния до цены. Нужно восстановить причинную связь `BOS → текущее движение → его якоря → PD → его зоны`.

Скриншоты не позволяют установить точные времена BOS, источники опор и полный состав OB/FVG. Числа выше — наблюдение изображения, не готовая OHLC-фикстура и не доказательство причины в БД.

## 3. Что видно в текущем коде и что проверить

- `app/engine/ltf/ranges.py::current_range` ищет подтверждённую пару LH→LL / HL→HH. Наличие пары само по себе не гарантирует её принадлежность текущему движению.
- `origin_reversal_range` связан с источником движения, но требует подтверждённую конечную опору. Предварительный экстремум не должен оставлять пользователя со старым PD во время нового движения.
- `app/bot/charts.py::render_ltf_chart` выбирает `current` из `info['ranges']`, добавляет границы в `extra_levels` и учитывает их при масштабировании. Проверить происхождение этого `current` по всей цепочке.
- `app/notify/ltf_queue.py::_render_event_chart` передаёт observation_id; период 3/7/14 дней зависит от возраста HTF-наблюдения. Это может делать старый контекст центром графика вместо локального события.
- `app/services/h1_chart.py` содержит выбор активного либо последнего сценария наблюдения. Проверить все аналогичные fallback: отменённый/последний исторический сценарий нельзя использовать для текущего торгового снимка.

Это направления аудита по чтению кода. До изменения воспроизвести цепочку реально отправленного пакета и указать доказанную причину. Не считать проблему только ошибкой рендера.

## 4. Единая модель текущего движения

На инструмент, биржу, рынок и структурный масштаб H1 должен существовать один канонический выбор текущей локальной ноги на заданный `as_of`. HTF-родители прикрепляют основания и ограничения сценария, но не задают отдельные конкурирующие H1 PD для одного текущего движения.

Не смешивать внутреннюю и внешнюю структуру. Использовать существующую машину подтверждённых BOS и её масштаб; не считать каждый пробой микропивота новой рабочей ногой.

Минимальный контракт движения:

```
movement_id, instrument_id, structure_epoch_id, direction
origin_anchor_key, origin_price, origin_at, origin_known_at
trigger_bos_key, bos_at, broken_anchor_key
state: developing | pivot_confirmed | superseded | invalidated
endpoint_price, endpoint_at, endpoint_status
as_of, revision, source_candle_refs, reason
```

Идентичность должна восстанавливаться при replay и не зависеть от scenario_id конкретного HTF-родителя. Существующие движения/таблицы расширять, а не создавать второй параллельный движок.

### Выбор начала ноги

- BOS вверх: начало — структурный минимум, из которого пошёл импульс, сломавший соответствующий high. При развороте это может быть LL, при продолжении — HL.
- BOS вниз: начало — структурный максимум, из которого пошёл импульс, сломавший соответствующий low. При развороте это может быть HH, при продолжении — LH.
- Начало брать из причинной цепочки структурной машины до BOS. Ни произвольный максимум/минимум окна, ни геометрия HTF-зоны, ни ближайший по цене pivot не подходят.
- Начальный экстремум должен уже существовать и быть известен к моменту расчёта. Если он ещё не подтверждён симметричным pivot-детектором, разрешён явный структурный кандидат с происхождением; нельзя задним числом использовать будущий confirmed pivot. Если происхождение не доказано — `origin_unresolved`, без рабочего PD и входового сигнала.
- Новый локальный HL, появившийся внутри той же ноги, не переносит начало автоматически и не удаляет OB/FVG основания.

### Когда менять движение

1. Обратный подтверждённый BOS завершает текущую рабочую направленную ногу и открывает противоположную от её причинной опоры.
2. BOS продолжения после структурно распознанной коррекции открывает новую ногу от нового причинного HL/LH. Предыдущая становится исторической.
3. Несколько сломанных уровней одним импульсом без новой структурной коррекции не создают несколько ног: добавить BOS-факты к той же ноге.
4. Наличие коррекции и новой опоры определяется той же структурной машиной, а не таймером, расстоянием цены или произвольным числом свечей.
5. При новом BOS старый PD перестаёт быть текущим в той же транзакции. Если новый PD нельзя построить, показать `range_pending` с причиной, а не старый диапазон как замену.
6. Отсутствие нового BOS не означает необходимость постоянно переякоривать диапазон. Выход за его границу без завершения структурного перехода требует пересчёта экстремума/проверки валидности, но не выбора случайной близкой пары.

## 5. PD строится сразу после BOS по потенциальному конечному пивоту

Под «потенциальным пивотом» понимается уже наблюдаемый экстремум цены, которому ещё не хватает подтверждения pivot-детектора. Это не прогноз будущего high/low.

Для long:

```
L = origin_price текущей восходящей ноги
H(t) = максимальный high закрытых H1-свечей этой ноги до as_of
EQ(t) = (L + H(t)) / 2
discount = [L, EQ(t)]
```

Для short:

```
H = origin_price текущей нисходящей ноги
L(t) = минимальный low закрытых H1-свечей этой ноги до as_of
EQ(t) = (L(t) + H) / 2
premium = [EQ(t), H]
```

В расчёт конечного экстремума включить доступную часть ноги до BOS, сам бар BOS и последующие закрытые свечи. Оба якоря должны принадлежать этой ноге. До BOS допускается только отдельная аналитическая preview-разметка без рабочего входового допуска.

Сразу при подтверждённом BOS публикуется `range_status=provisional`, если конечная опора ещё не подтверждена. Не ждать три правые свечи для показа зон и потенциальной возможности отката. Подтверждение pivot переводит статус в `confirmed`; не создаёт повторный BOS или новую торговую идею.

До структурного завершения ноги новый направленный экстремум расширяет PD, даже если предыдущий экстремум уже успел получить pivot-подтверждение. Новая конечная опора снова provisional. После смены ноги предыдущие версии не переписывать.

Открытая H1 может менять отдельный live-preview, явно подписанный «текущая свеча». Он не влияет на подтверждённые события, рабочие уведомления и исторические снимки. На одном `as_of` расчёт детерминированный.

Для третьего скрина: если 80 393,56 подтверждается данными как начало текущей восходящей ноги, а её наблюдаемый high уже выше 82 776,01, старую верхнюю границу нельзя сохранять только потому, что новая ещё не стала confirmed pivot. Подставить реальный high из OHLC и пересчитать EQ. Точное новое значение по изображению не угадывать.

## 6. Потенциальные зоны H1 внутри движения

1. Выявлять все OB/FVG текущей причинной ноги, включая базу перед импульсом, если она причинно относится к этой ноге. Включать зоны до BOS и новые зоны развивающегося импульса после BOS.
2. Кандидатов связывать с каноническим `movement_id`; валидная зона из другой старой ноги не становится текущей только потому, что лежит в нужной половине нового PD.
3. Сохранять все зоны в истории. На основном графике выделять текущую ногу; исторические зоны показывать только отдельным слоем и без текущих входовых уведомлений по умолчанию.
4. Отдельно хранить степень формирования зоны и статус PD. Незавершённый FVG/неподтверждённый OB — `forming`, только preview. Уже подтверждённая зона с provisional PD — полноценный кандидат планирования отката, с явной меткой «предварительный PD».
5. После BOS не требовать подтверждения конечного pivot для `eligible_provisional`. Для реального уведомления о касании должны выполниться все остальные условия: актуальный сценарий/HTF-контекст, валидная сформированная зона, нужная половина PD, качество данных.
6. Long: допущенная область = пересечение зоны с discount. Short: с premium. При частичном пересечении рисовать весь объект и выделять допущенную часть; касание недопущенной части не является входовым касанием.
7. Не отменять существующие запреты по инвалидации, fill, глубине тестирования, настройкам типов и неоднозначному происхождению. Позднее обнаружение не обнуляет историю тестов.
8. Для каждого исключения возвращать reason: `other_movement`, `outside_pd`, `forming`, `invalid`, `filled`, `tested_too_deep`, `origin_unresolved`, `range_pending`, `context_missing`, `data_incomplete` либо совместимые существующие коды.
9. Изменение EQ не должно создавать задним числом факт касания. Для касания по закрытой свече использовать область допуска, известную до этой свечи; если зона впервые стала допустимой только на её закрытии, отправить «зона стала доступна», а не утверждать, что допустимый вход уже был внутри бара. Исключение возможно при доказанной последовательности младшими данными.

Наличие HTF-контекста управляет торговым допуском, а не геометрией локальной структуры. Если контекста нет, локальный PD и кандидаты могут быть видны как аналитика, но не как подтверждённый торговый сетап.

## 7. Один источник данных для движка, графика и сообщения

Подготовить общую проекцию:

```
H1SetupSnapshot {
  instrument, as_of, mode, snapshot_id,
  movement_id, direction, trigger_bos,
  origin_anchor, endpoint, range_status, range_revision,
  lower, upper, eq,
  context_sources[], candidates[], eligible_regions[],
  setup_status, exclusion_reasons[], data_quality
}
```

`mode=event` — неизменяемый снимок времени события. `mode=current` — актуальный снимок. У каждой цены, зоны и опоры должно быть происхождение. Ни renderer, ни Telegram-шаблон не подбирают диапазон самостоятельно по observation_id или последнему сценарию.

Текущий снимок одного инструмента/масштаба имеет один рабочий PD, независимо от выбранного HTF-источника. Исторический просмотр старого события сохраняет его тогдашний диапазон и явно помечается как история.

Перед отправкой текущего входового пакета проверять актуальность movement_id. Если он superseded/invalidated — пакет подавить с причиной. Исторический снимок не перерисовывать на новые данные под старым временем события.

## 8. Правила графика

- Основной кадр посвящён текущей ноге: показать начало, BOS, текущий потенциальный экстремум, PD/EQ, OB/FVG и допустимые области отката.
- Горизонтальные границы PD рисовать от начала соответствующей ноги, а не через все 14 дней до её возникновения. Рабочий/доступный после BOS участок можно выделить отдельно.
- Подписи: «PD H1 текущего движения», «50%», «Потенциальный H/L», направление и статус. Provisional — пунктир; confirmed — сплошная линия. Цвет не должен быть единственным различием.
- Выбирать окно по времени начала текущего движения и BOS с небольшим предшествующим контекстом. Возраст HTF-наблюдения не определяет основной масштаб.
- Масштаб Y считать по свечам локального кадра, якорям текущего PD и его зонам. Старые PD не участвуют. Далёкие HTF-источники указывать текстом «вне кадра» без растяжения оси.
- Реально текущий широкий диапазон нельзя скрыть лишь из-за расстояния до цены. Его происхождение должно быть доказано; локальность — структурное свойство, а не процентный фильтр.
- Не обрезать правые подписи, не накладывать их друг на друга; использовать короткие подписи и отдельный список цен при нехватке места. На скринах длинные надписи уходят за правую границу — это отдельный дефект приёмки.
- Показывать все валидные кандидаты текущей ноги; диагностические/исторические объекты — отдельным слоем. Легенда содержит только реально присутствующие слои.

## 9. Уведомления: повод — рыночный переход, а не существование старого PD

### Отправлять

1. Новый подтверждённый BOS / смена направления: одна карточка инструмента с отменой противоположного сценария, новым направлением, локальным PD и зонами, если торговые условия выполнены.
2. Первое появление допущенных зон текущей ноги после подтверждения сценария: один `entries_ready`, если не вошёл в карточку BOS.
3. Фактическое касание допустимой области актуальной зоны: один алерт на визит по правилам предыдущего ТЗ.
4. Инвалидация актуального сценария: один алерт с конкретным основанием.

### Не отправлять отдельный торговый алерт

- Найден старый подтверждённый PD в наблюдении HTF.
- Повторно рассчитан тот же диапазон или изменился только revision/EQ/статус подтверждения pivot.
- Выбран другой HTF-родитель того же движения.
- Новый кандидат пока forming, вне нужной половины либо относится к старой ноге.
- Replay/миграция обнаружили исторические события.

Обновление экстремума и EQ отражать в текущей карточке/интерфейсе; само по себе это не повод нового сообщения. Если изменение создало впервые пригодную область входа, допускается одно агрегированное обновление по смысловому переходу, не на каждую версию диапазона. При снятии допуска подавлять ожидающие входовые пакеты и обновлять UI; сообщение об инвалидации — отдельное событие.

Для нового BOS без HTF-допуска возможна только включённая пользователем структурная категория «BOS подтверждён, торговый контекст отсутствует». Нельзя называть это готовым входом. Отсутствие зон не запрещает содержательное сообщение о реальной отмене сценария.

### Идемпотентность

Ключ рыночного перехода включает инструмент/рынок/биржу, масштаб, каноническую опору, время BOS и направление. Ключ доставки — получателя, канал, переход и вид сообщения. Не включать observation_id, время опроса или range_revision как основание новой отправки.

Сохранить UNIQUE-ограничения, транзакционную постановку outbox, защиту конкурентного claim, историю попыток и обработку неопределённого результата Telegram. Семантическое объединение разных HTF-источников не должно подавлять реально новый BOS новой ноги.

### Пример нового сообщения

> BTCUSDT · BOS H1 вверх подтверждён [время].
> [Если применимо: медвежий сценарий отменён; бычий подтверждён.] 
> Текущее движение: [исходный low] → [наблюдаемый high]. Верхний pivot потенциальный.
> PD H1: [L]–[H], 50%: [EQ].
> Возможные области покупки на откате: [OB/FVG текущей ноги, допустимые интервалы].
> HTF-контекст: [сохранённые источники].
> Отмена: [уровень и правило].

Для short зеркально: high → потенциальный low, зоны продажи в premium. Цены вставлять только из общего snapshot. Не обещать движение к зонам или исполнение входа.

## 10. План реализации

1. Воспроизвести три класса снимков. Для каждого вывести event/packet/observation/scenario/movement/range IDs, as_of, время обеих опор, состояние сценария и причину выбора current.
2. Реализовать каноническую идентичность текущей ноги и правила смены; запретить fallback на произвольный последний исторический сценарий.
3. Добавить рабочий provisional PD и причинные якоря; сохранить версии и as_of. Убрать требование confirmed endpoint как препятствие показу потенциальных зон.
4. Привязать кандидатов и eligibility к текущей ноге и её диапазону; сохранить полную базу ноги и исторический lifecycle.
5. Создать общую проекцию H1SetupSnapshot, подключить API, web, PNG и уведомления.
6. Пересобрать поводы алертов, семантические ключи и проверку актуальности перед отправкой.
7. Миграция без рассылки: доказуемые старые диапазоны пометить historical/superseded; недоказуемые — unresolved. Не удалять журнал, не восстанавливать отменённые сценарии.
8. Прогнать регрессии и сценарные тесты, отрендерить эталонные снимки long/short/provisional/confirmed. Подготовить отчёт до/после и порядок запуска.

Проверяемые модули: `app/engine/ltf/{engine,structure,breaks,entries,ranges,eligibility}.py`, `app/services/{h1_chart,htf_ideas,overview}.py`, `app/bot/charts.py`, `app/notify/{ltf_queue,outbox,ltf_templates,compact}.py`, `app/web/ltf_api.py`, H1-слои фронтенда, модели/БД/конфигурация. Уточнить фактический путь формирования `info['ranges']`.

## 11. Критерии приёмки

| Проверка | Результат |
|---|---|
| Цена около 83 тыс., в БД старые PD 109–112 тыс. и 88–91 тыс. | Они не выбираются текущими при наличии другой текущей ноги; не растягивают её PNG и не вызывают алерт |
| Для одного движения есть несколько HTF-родителей | Один и тот же локальный PD и набор кандидатов, одна карточка перехода |
| BOS вверх, конечный high ещё не confirmed pivot | Сразу видны provisional PD и все валидные кандидаты ноги |
| BOS вниз, конечный low ещё не confirmed pivot | Зеркальный результат для premium |
| Новый фактический high/low текущей ноги | Граница и EQ обновлены; отдельного алерта на каждую версию нет |
| На скрине 3 новая восходящая нога выше старого high 82 776,01 | Диапазон берётся от её причинного начала к реальному текущему экстремуму, если это подтверждено OHLC |
| Потенциальный экстремум ещё не достигнут ценой | В PD не используется |
| Появился локальный HL внутри той же ноги без нового самостоятельного BOS | Начало не переносится, нижние причинные OB/FVG сохраняются |
| Коррекция и новый BOS продолжения | Новая текущая нога от её HL/LH; прежний PD становится историческим |
| Несколько сломов одним непрерывным импульсом | Одна нога, несколько фактов; нет размножения одинаковых PD |
| Обратный BOS | Переключение направления и PD атомарно; старые входовые пакеты не отправляются |
| Новый BOS есть, происхождение якоря не доказано | range_pending/origin_unresolved; старый PD не подставляется |
| Неподтверждённый OB/FVG | forming-preview, без торгового допуска |
| Валидные OB/FVG у основания и выше в текущей ноге | Все показаны и независимо оценены |
| Зона старой ноги попала в новый discount | Не становится текущей только из-за геометрического пересечения |
| EQ изменился на закрытии свечи, впервые допустив зону | Нет ретроспективного ложного алерта касания внутри этой свечи |
| Pivot подтвердился без изменения геометрии | Меняется статус; не появляется новый BOS/entries_ready |
| Далёкий HTF-источник | Текстовая ссылка вне кадра, нормальный масштаб текущей ноги |
| Историческое событие открыто вручную | Старый PD допустим только с пометкой истории и правильным as_of |
| Replay, restart, два воркера, повторный poll | Одинаковый выбор ноги/PD, нет логических дублей |
| Сравнение API, web, PNG и Telegram на одном snapshot | Совпадают направление, якоря, EQ, зоны и статусы |
| Длинные подписи и несколько близких зон | Цены не обрезаны и читаемы |

Дополнительно: синтетический расчёт L=80 400, H=83 400 даёт EQ=81 900; после реально достигнутого H=83 600 — EQ=82 000. Эти значения служат арифметическому тесту, не подменяют реальные котировки скрина.

## 12. Результат, который нужно сдать

- Реализация, миграция, тесты и обновлённые правила.
- Доказанная причина выбора далёких PD, а не предположение по скриншоту.
- Таблица опор до/после: движение, BOS, начало, потенциальный конец, EQ, статус, источники данных.
- Примеры новых уведомлений и проверенные изображения long/short.
- Отчёт по критериям приёмки и регрессиям, ограничения данных отдельно.

Не считать задачу выполненной, если лишь скрыты далёкие линии, изменён масштаб графика, отключены уведомления целиком или взята ближайшая к цене пара пивотов. Должна измениться причинная модель выбора текущего PD и связанного с ним набора зон.
