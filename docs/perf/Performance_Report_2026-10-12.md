  диск NTFS. Платформа в отчётах бенча: `Windows-10-10.0.26200-SP0`
  (так CPython маркирует Windows 11).
- Все числа — **локальные измерения** на детерминированных сценариях
  (`tools/bench_pipeline_baseline.py`, без сети/Telegram/WS). По §6/§17 они

  проверяется только на production-замерах (таблица соответствия ниже).

  и этим отчётом модель хранения была переписана параллельной работой

  репозитория в `app/db.py`). Измерения «сейчас» отражают **совмещённое
  дерево** (этапы 2–7 + storage-перепись), а не только этап 7.
- Baseline: `data/diag/baseline_1791826560.json` (этап 2-го дерева,
  3 инструмента, 1000 тиков, 30000 свечей/инструмент).
- Текущие прогоны: `data/diag/stage7_load_3.json`, `stage7_load_10.json`,
  `stage7_load_30.json` (те же сценарии и параметры; `--candles 30000`).

## Что изменено в этапе 7

### 1. Tail-read pushdown (§12): окно хвоста — в SQL, не в Python-срезе

`Database.get_candles(..., limit=N)` уже реализует DESC LIMIT по PK
`candle(instrument_id, timeframe, open_time)` с возвратом в восходящем
порядке. Конвертированы чтения полной истории:

| Место | Было | Стало | Обоснование границы |
|---|---|---|---|
| `app/services/data_sync.py:285` (`channel_status`) | `get_candles(...)[-200:]` | `limit=200` | скан разрывов — ровно 200 последних закрытых; срез тождественен |
| `app/services/data_sync.py:624` (`_sync_candles`) | полная история | `limit=200` | окно запроса к источнику и прежде ограничивалось сканом разрывов по последним 200 (`start >= rows[-200].open_time+step`); снапшот `before` нужен для классификации только свечей этого окна (доказано покрытием: весь `incoming ⊆ [start, now]`, `start >= rows[0].open_time` ограниченного набора ⇒ классификация new/revised, метрики, H1-rewind `missed`/`previous` и `max(close_time)` идентичны) |
| `app/worker.py:365` (`_backfill_tail`) | полная история | `limit=512` | `before` нужен для: max-агрегатов (последний бар), membership перекрытия резюме (2 бара), детекта recovery по `fresh` (open_time > last) — всё хвостовое; 512 — по образцу уже существующего `_ws_closed_kline` (`worker.py:808`, limit=512) |
| `app/worker.py:1536` (`_process_synced_channel`) | полный скан + фильтр `close_time > cursor` | `start_ms = max(0, cursor − step + 2)` + прежний фильтр-страж | обрабатываются только свечи с `close_time > cursor`; при инварианте `close_time = open_time + step − 1` это `open_time ≥ cursor − step + 2`; фильтр сохранён, порядок/closed_only неизменны |
| `app/services/quality.py:126` (`_continuity_channel`) | `get_candles("H1")[-50:]` | `limit=_CONTINUITY_SCAN` (50) | тот же скан разрывов последних 50 закрытых H1; горячий путь — вызывается из `data_quality` (гейт доставки LTF, overview) |

Замер выигрыша (проба на 30000 закрытых H1, прогретый page cache):
`get_candles(iid,"H1")` полное — **p50 111.8 мс / p95 116.2 мс**;
`limit=200` — **p50 0.65 мс / p95 0.78 мс** (~170×).
В production это чтение выполнялось на каждый accepted-тик котировки на
канал (`mark_instrument_success` → `channel_status` по всем ТФ) и в
`data_quality`; в бенче свечей мало, поэтому выигрыш виден только в пробе.

### 2. Batch-commit на горячем пути синхронизации (§12)

`app/services/data_sync.py` `_sync_candles`: секция записи (инициализация
курсора `data_sync:processed:{iid}:{tf}` → `insert_candles` → rewind курсора
H1 при дыре за курсором → снимок канала) собрана в **одну единицу**
`batch_writes()` на FIFO-писателе `DataSync._write` (`_persist_incoming`).
Было до 4 отдельных COMMIT, стал 1; проверка курсора перенесена внутрь
единицы (check-and-set атомарен на потоке-писателе). Сбой середины откатывает
всё: курсор не уезжает вперёд данных (AC18).

Путь котировки: `_ingest_quote.accept()` уже одна единица (`batch_writes`:
дедуп → `set_quote_if_fresh` → `spool_quote` → формирующиеся бары) — без
изменений. `_poll_quote` пишет мету канала дважды за тик: маркер попытки ДО
сетевого запроса и маркер успеха/ошибки ПОСЛЕ — объединить их нельзя (между
ними await сети; маркер попытки — осознанная семантика диагностики зависшего
источника). `_note_quote_channel_live` — одна запись за цикл опроса, не на
тик. Решение: не трогаем (§12: менять только измеримое; доля COMMIT в
медиане тика — в шуме, см. метрики ниже).

### 3. PRAGMA/конфиг аудит — без снижения durability

Новый инструмент `tools/db_pragma_audit.py` (read-only `mode=ro`; живая
политика busy_timeout по ролям измеряется зондом `app.storage.Connection`
на временной БД). Результат по `data/htf_zones.db`
(`data/diag/pragma_audit_stage7.json`):

| Параметр | Значение | Оценка |
|---|---|---|
| journal_mode | wal | OK (ставится `app/storage.py:32` при открытии) |
| synchronous | 2 (FULL) | OK — durability не снижалась ни в одном этапе |
| busy_timeout цикл событий | 0 мс | **намеренный контракт** storage-воркстрима: async не ждёт писателя в busy-handler; записи — через `DataSync._write` (FIFO-поток) |
| busy_timeout потоков | 15000 мс | OK (ждущий писатель/расчёт) |
| wal_autocheckpoint | 1000 стр. | дефолт SQLite |
| cache_size | -2000 (≈2 МиБ) | дефолт SQLite |
| WAL файл | 7.8 МиБ | некритично |

**Изменено ничего не было.** Поднимать `busy_timeout` на loop-соединении
нельзя — это вернёт фризы цикла под потоковым расчётом (зафиксировано как
finding уровня info). Проблемных pragma-расхождений не найдено.

### 4. Ограничения наблюдаемости (честно)

`sql_duration{op=commit}` после storage-переписи считает только
autocommit-путь (`Database._commit` вне `batch_writes`): реальные COMMIT
единиц уходят через `raw.execute("COMMIT")` без гистограммы. В прогонах
этапа 7 счётчик показывает 5 за весь сценарий (миграции при открытии) —
это артефакт инструментации, а не отсутствие коммитов. Baseline
(count=8924, p99 15 мс, max 63 мс) измерял старый autocommit-путь.
Сравнение «коммитов до/после» по этой метрике некорректно.

## Нагрузочная приёмка: baseline vs этап 7

Сценарии (`--scenario all`): `quote_storm` (1000 тиков, ~5% дублей, ~2% вне
порядка, через текущий `_poll_quote` → spool → `market_queue.wait_idle`),
`startup` (open+schema+миграции на 30000 H1/инструмент), `candle_close`
(локальная часть sync_candles: 5 закрытий H1 на инструмент; в этапе 7 сценарий
обновлён под текущий код — `limit=200` + одна единица записи).

### quote_storm (1000 тиков; p50/p95/p99 мс — `bench_quote_tick`, быстрый путь)

| Профиль | wall, с | accepted | p50 | p95 | p99 | max |
|---|---|---|---|---|---|---|
| baseline (3 инстр., дерево этапа 2) | 4.99 | 944 | 4.93 | 6.29 | 7.08 | 23.3 |
| этап 7, 3 инстр. | 5.08 | 944 | 3.37 | 18.84 | 34.39 | 50.5 |
| этап 7, 10 инстр. | 4.91 | 944 | 3.24 | 18.83 | 33.99 | 48.9 |
| этап 7, 30 инстр. | 5.80 | 944 | 3.70 | 19.24 | 20.43 | 193.8 |

- Медиана быстрого пути **улучшилась** 4.93 → ~3.2–3.7 мс (~30%).
- Хвост p95/p99 **вырос** (6.3/7.1 → ~19/34 мс). Вклад совмещённого дерева:
  каждый тик — durable spool-строка + 2 меты канала (3 единицы записи с
  COMMIT при `synchronous=FULL` на NTFS) плюс конкурентная дочитка очереди
  потребителем. Хвост остаётся на порядок ниже цели §17 (250 мс, см. ниже).
  `accepted=944` идентично baseline — семантика дедупа/монотонности не
  изменилась.
- Гистограммы `quote_receive_to_persist`/`quote_receive_to_broadcast` в бенче
  искажены артефактом: `received_at` тиков генерируется заранее, а цикл
  replay занимает секунды (p50 ~32 с в обоих деревьях — одинаковый артефакт).
  Валидный локальный прокси пути receive→persist — `bench_quote_tick`
  (полный `_poll_quote` включая канал-мету, т.е. больше, чем persist).

## Соответствие целям §17

| Цель §17 | Локальная проверка | Статус |
|---|---|---|
| Receive → durable quote p95 ≤ 250 мс | `bench_quote_tick` p95 ≈ 19 мс (быстрый путь целиком, включая persist) | **достигнуто локально**; production-замер обязателен |
| Receive → server broadcast p95 ≤ 500 мс | в бенче нет WS-рассылки; метрика `quote_receive_to_broadcast` искажена артефактом replay | требует production-замера |
| Browser receive → отображение p95 ≤ 250 мс | вне охвата серверного бенча | требует browser-замера |
| Принятие ручного запроса p95 ≤ 500 мс без сети биржи | `data_sync.start()` — in-memory (job dict + broadcast), сети нет | требует замера через API на production-профиле |
| Видимая реакция кнопки ≤ 100 мс | UI | требует browser-замера |
| Закрытая свеча → обработка без backlog: H1 p95 ≤ 3 с, HTF p95 ≤ 5 с | локальная часть (persist) p95 ≈ 2.3 мс; полный путь включает расчёт движка (`calc_duration` в бенче ~0 — нет зон) | частично; полный путь — production-замер через `pipeline.calc_pending_wait_s` и `calc_duration` |
| API небольшого снимка p95 ≤ 300 мс при 10 инструментах | вне бенча; есть middleware-метрики `api_response_*` | требует production-замера |
| Полезный экран из сохранённой БД ≤ 2 с | UI | требует browser-замера |
| 30-с CPU-расчёт: котировки продолжают приниматься (AC02) | архитектурно: расчёт без охватывающей write-транзакции (`market_queue._process`), покрыто тестами этапа 2 | покрыто тестами; нагрузочный production-замер отдельно |
| 0 повторных полных расчётов при неизменных свечах/зависимостях (AC05) | счётчик `calc_skipped_unchanged`; тесты `test_incremental_skip.py`, `test_calc_queue.py` | покрыто тестами |

Не достигнутые/непроверимые локально цели перечислены выше явно — это
ограничения локальной приёмки, а не отклонения от спеки (§17: «Не достигнутый
target фиксируется в отчёте»).

## Намеренно НЕ изменено (с причинами)

- `worker.py:1340` `_htf_unchanged` и `worker.py:1371` `_store_htf_fingerprints`:
  отпечаток AC05 покрывает **весь** потреблённый закрытый хвост; ограничение
  окна ослабило бы проверку глубоких правок истории (семантика AC05). Это
  подлинные full-history чтения (как replay).
- Движок/replay: `engine/scanner.py:99,643,819`, `engine/replay.py:166`,
  `engine/ltf/engine.py:276,449,1901,2533` — построение структуры/replay по
  всей истории окна; область движка не трогаем.
- Request-scoped UI-чтения (`web/api.py:324,1059`, `web/ltf_api.py:121`,
  `services/presentation.py:929`, `notify/chart_series.py:32` и др.) — не
  горячие циклы; большинство уже ограничены `start_ms/end_ms/limit`.
- PRAGMA: ничего не менялось (см. аудит); `busy_timeout=0` на loop-соединении
  — контракт параллельного storage-воркстрима, задокументирован как finding.
- Индексы не добавлялись: медленных запросов вне покрытых PK
  `candle(instrument_id, timeframe, open_time)` замеры не показали (§12:
  индексы — только для измеренных медленных запросов; EXPLAIN QUERY PLAN
  ограниченного чтения — `SEARCH candle USING INDEX`, покрыто тестом).
