# Техническое задание на стабилизацию LevelFrame

Дата: 12 октября 2026 года. Основание: [обширный аудит текущей рабочей копии](audit/LevelFrame_Comprehensive_Audit_RU_2026_10_12.md). Базовый commit: `8e736517e17659fe2bace20a5f17b180529cb8d3`; фактическое состояние исходников зафиксировано в [манифесте](audit/2026-10-12/source-manifest.json).

Цель — обеспечить сохранность принятых рыночных данных, согласованность расчёта и интерфейса, предсказуемое применение настроек и восстановление после отказа. Завершением работы считается прохождение критериев ниже на фиксированном окружении и нагрузке. Наличие кода, счётчика ошибок или успешного HTTP-ответа само по себе не подтверждает выполнение требования.

## Границы поставки

В поставку входят runtime ownership, SQLite, очередь тиков, задания пересчёта, REST/WS-синхронизация, outbox, API, авторизация, frontend-состояния, метрики, тесты, сборка и восстановление. Существующие правила HTF/LTF и работающие каналы Binance, Bybit, Hyperliquid, ALT, Events и Telegram должны сохранять совместимость.

Новая торговая стратегия, изменение порогов детекторов, автоматическое включение ALT v0.4, переход на другую СУБД и горизонтальное масштабирование не являются условиями этой поставки. Версионирование и проверка ALT v0.4 входят как подготовительная задача; включение новой логики производится по отдельной приёмке соответствующего ALT ТЗ.

Это инженерное дополнение к [ТЗ производительности](Service_Performance_Optimization_Spec_RU_2026_10_12.md) и [ТЗ синхронизации свечей](Candle_Synchronization_Spec_RU_2026_10_12.md). При конфликте производительности с сохранностью сначала выполняются требования сохранности. Старые замечания, уже исправленные в коде, не реализовывать повторно.

## Обязательные инварианты

1. Принятый сервисом тик имеет durable-запись работы или уже завершённый durable-результат. Подтверждение приёма не предшествует commit.
2. Тик не исчезает при исключении, отмене, переполнении, аварийном завершении или рестарте. Необрабатываемый тик получает видимый статус ошибки и возможность восстановления.
3. Повторная доставка одного входа не создаёт повторных рыночных событий, визитов и notification packets. Система допускает повтор обработки входа, сохраняя идемпотентный результат.
4. Транзакция одного запроса не может быть зафиксирована или отменена другим запросом. Читатель видит опубликованное состояние одной версии.
5. Данные одной карточки и соответствующих слоёв графика относятся к совместимой версии состояния и профиля. Несогласованный ответ не заменяет последний согласованный снимок.
6. Различаются время источника, приёма, сохранения и обработки. При отсутствии времени источника хранится null, а не подставленное время ответа.
7. Исторический replay не использует будущие свечи и не превращает исторические события в новые live-уведомления. Коррекция OHLC имеет явную ревизию.
8. Изменение настроек либо публикует законченную новую версию, либо оставляет рабочей прежнюю. Ошибка задания не оставляет смешанный профиль.
9. При потере права владельца процесс прекращает новые записи соответствующей роли. PID не считается достаточным подтверждением права записи.
10. Отключение инструмента имеет определённую точку вступления в силу. После подтверждения операции новые callbacks не создают по нему live-события.
11. Неопределённый результат внешней доставки сохраняет статус uncertain; автоматический повтор не выдаётся за гарантию отсутствия дубля Telegram.
12. Ошибки и отставание видны в диагностике и UI; подключённый WebSocket не означает свежесть цены и завершённость расчёта.

## Целевая организация обработки

Сохранить один сервис с явно управляемыми ролями HTTP, расчёт, получение данных и доставка. Внутри процесса все задачи принадлежат общему supervisor. Для каждой роли хранить instance ID и generation владения; только действующий владелец выполняет защищённые изменения.

Вход проходит общую нормализацию и durable intake, после чего допускается публикация принятой цены. Движок обрабатывает запись с устойчивым idempotency key. Изменения рынка, отметка обработки и намерение публикации связываются транзакционно либо восстанавливаемым журналом, который гарантированно находит непоставленные публикации. Сетевой вызов Telegram выполняется после commit.

SQL-доступ должен иметь явное владение соединением на всю транзакцию. Допустим выделенный writer с очередью команд и отдельные read-соединения. Альтернатива допустима после доказательства изоляции и задержек. Держать обычный `threading.Lock` через `await` и блокировать event loop ожиданием длительного replay запрещено. Глобальный calc-lock не подменяет транзакционную изоляцию.

## TZ01 Безопасное владение процессами

Приоритет P0. Закрывает A00, A08. Область: `services/runtime.py`, `main.py`, `worker.py`, диагностика.

Заменить `os.kill(pid, 0)` как универсальный health probe. На Windows использовать безопасное чтение состояния процесса либо исключить зависимость ownership от PID. Никакая проверка существования процесса не должна посылать ему завершающий сигнал.

Хранить `role`, `instance_id`, `owner_generation`, `claimed_at`, `heartbeat_at`, `expires_at`; host/container identity использовать только как дополнительную диагностику. Claim и takeover выполнять атомарно. Обновление heartbeat и защищённые записи должны проверять instance и generation. Старый владелец после takeover не может продолжить работу. Отдельно применять механизм к calc и Telegram polling.

Критерии приёмки:

- AC01: конкурентный запуск двух экземпляров на одной временной БД даёт ровно одного владельца каждой роли.
- AC02: на Windows безопасная проверка собственного тестового дочернего процесса не изменяет его состояние и exit code; отдельно проверить отсутствующий и недоступный PID.
- AC03: одинаковые PID разных instance не считаются одним владельцем; устаревшая generation не проходит проверку записи.
- AC04: после аварийной остановки takeover возможен по истечении lease; до истечения второй экземпляр остаётся наблюдателем с явной диагностикой.

## TZ02 Изоляция записей и согласованные снимки

Приоритет P0. Закрывает A01. Область: `db.py`, все прямые `db.conn`-записи, replay, outbox, API-мутации.

Инвентаризировать все пути `execute/commit/rollback`, включая outbox и служебные миграции. Ввести unit of work с владельцем транзакции; убрать общепроцессный `_batch_depth` как способ присоединения независимых операций. Ограничить прямой доступ к внутреннему соединению. Для вложенных операций определить одну семантику: присоединение к транзакции того же владельца или savepoint.

Read model и `state_seq` публиковать после согласованного commit. Кэш не должен сохранять объекты отменённого изменения; инвалидировать его только в определённых местах commit/rollback. Существующие идентификаторы зон, событий, разметка и связи не должны исчезнуть при смене реализации репозитория.

Критерии приёмки:

- AC05: оба сценария из `transaction_isolation` в audit probe меняют результат на корректный: чужая подтверждённая запись сохраняется, отменённый replay отсутствует.
- AC06: параллельные quote ingest, review, outbox и replay не видят чужих незавершённых изменений и не вызывают чужой commit.
- AC07: HTTP current/chart/candles с общей версией не содержат промежуточного batch-состояния; отмена batch не меняет опубликованную версию.
- AC08: fault injection между отдельными SQL-операциями оставляет либо полный результат unit of work, либо прежнее состояние; `PRAGMA integrity_check` проходит на тестовой копии.

## TZ03 Сохранная очередь и своевременная доставка

Приоритет P0 для сохранности, P1 для задержек. Закрывает A02, A03, A04. Область: `market_queue.py`, quote ingest, scanner, outbox, schema.

Рекомендуемый контракт записи входа: `id`, `instrument_id`, `source`, `source_seq`, `event_at`, `received_at`, `persisted_at`, `payload`, `status`, `attempts`, `next_attempt_at`, `last_error`, `processed_at`, `owner_generation`. Конкретную схему можно упростить, сохранив все гарантии и наблюдаемость. Монотонные часы использовать для длительностей процесса; они не должны сохраняться как переносимые между рестартами timestamps.

Сначала сохранять pending-работу, затем подтверждать intake и публиковать принятую цену. Память используется как ускоритель. После ошибки не удалять вход и не снимать degraded. Выполнять ограниченные повторы с backoff; после лимита помещать в quarantine с причиной и ручным восстановлением. Нельзя молча пропускать ошибочный тик и объявлять последующее состояние полным: дальнейшее продвижение инструмента допускается только по явной политике неполных данных либо после replay.

Обрабатывать bounded batches по числу записей и временному бюджету. Создание событий и публикаций не должно ждать полного опустошения очереди. Порядок значимых тиков одного инструмента сохраняется; latest-price для UI можно объединять, но входы детектора и переходы состояния объединять запрещено. Одна медленная задача не должна блокировать intake всех инструментов.

Критерии приёмки:

- AC09: исключение детектора оставляет тик pending/retry/quarantine, сохраняет причину и делает канал degraded; аудитный сценарий `queue_failure` больше не теряет строку.
- AC10: принудительное завершение процесса после durable intake, в середине расчёта и после commit результата не теряет входы; после рестарта нет дублей событий.
- AC11: непрерывный поток, при котором очередь никогда не пуста, регулярно публикует законченные партии; размер локального списка событий ограничен.
- AC12: overflow и disk-full имеют различимые статусы; при невозможности durable записи новый тик не считается успешно принятым.
- AC13: после crash между событием и outbox восстанавливается намерение публикации; uncertain-доставки не отправляются повторно автоматически.
- AC14: короткое касание и выход из зоны внутри одного интервала REST, переданные через последовательность WS-тиков, сохраняются в тех же событиях, что и эталонная последовательная обработка.

## TZ04 Версионированные настройки и задания пересчёта

Приоритет P1. Закрывает A05, A06, A10, A11, A12. Область: `config.py`, settings API, worker, frontend settings.

Все ENV-поля читать при создании Settings после dotenv, а не при объявлении класса. Зафиксировать существующий порядок детектора: defaults → ENV → сохранённый профиль. Для секретов оставить отдельный ENV-only путь. Defaults, ENV, JSON и API должны проходить один валидатор типов, диапазонов и межполевых зависимостей.

Сохранение профиля принимает `expected_config_version`. Конкурентное изменение возвращает 409 без побочных эффектов. Новый кандидат проходит validation, получает job ID и requested version. Длительный пересчёт возвращает 202 с адресом задания. HTTP timeout не завершает и не теряет само задание. Каждый job имеет владельца и терминальное состояние ready/failed/cancelled/interrupted; running без работающего владельца недопустим.

Профиль рассчитывать под тем же механизмом сериализации, что и live-расчёты. Публиковать effective version вместе с законченным результатом. Если выбран staging по generation, API читает только активную generation. Если используется транзакционная перестройка, доказать допустимые задержки и отсутствие промежуточных чтений. Откат обязан включать рыночное состояние, а не только JSON и поля объекта.

Применение `scan_timeframes` и отключения инструментов должно работать при realtime on/off. Для файла использовать уникальное временное имя и atomic replace после согласованной операции; конкурентные сохранения не делят один `.tmp`.

Критерии приёмки:

- AC15: свежий subprocess, загрузивший тестовый `.env`, получает ожидаемые port, poll_seconds и quote_poll_seconds; реальные ENV сохраняют приоритет над dotenv.
- AC16: массив вместо JSON-объекта, отрицательные окна, дробный integer и несовместимые поля отвергаются одинаково через файл/ENV/API с адресной ошибкой; рабочий профиль не меняется.
- AC17: job дольше HTTP timeout достигает ready либо failed с `finished_at`; UI показывает конечный результат без перезапуска.
- AC18: два параллельных сохранения не приводят к потерянному обновлению, ошибке общего tmp-файла или откату чужого успешного профиля.
- AC19: отказ пересчёта после частичного прогресса оставляет активной предыдущую согласованную версию и её расчётное состояние.
- AC20: изменение scan_timeframes применяет один effective набор к REST, WS, freshness и UI; проверяется отдельно при `realtime_enabled=false`.

## TZ05 Общий запуск и завершение сервиса

Приоритет P1. Закрывает A07. Область: `main.py`, worker loops, realtime background tasks, outbox, Telegram.

Создать supervisor с явными task handles. Нормальная остановка HTTP или сигнал ОС запускают общий shutdown: readiness=false; прекращение intake; остановка подписок и polling; сохранение pending; завершение текущих транзакций в пределах бюджета; остановка delivery; закрытие сетевых клиентов и БД. Задачи `worker._ws_background` обязательно входят в этот порядок.

У бесконечных loops должен быть stop-сигнал. Исключение обязательного цикла отражается в диагностике и запускает определённую политику перезапуска/остановки. Не закрывать БД под ещё работающим Python-потоком: отмена await сама по себе не останавливает поток.

Критерии приёмки:

- AC21: SIGTERM в контейнере и штатная остановка на Windows завершают весь процесс в согласованный срок, а не только HTTP.
- AC22: shutdown во время WS recovery, закрытия H1, settings job и отправки уведомления не вызывает обращения к закрытой БД и не теряет accepted intake.
- AC23: после завершения нет принадлежащих сервису незавершённых asyncio tasks; interrupted jobs и uncertain deliveries восстанавливаются предсказуемо.

## TZ06 Немедленное управление источниками и подписками

Приоритет P1. Закрывает A09, A10. Область: instruments API, worker, BinanceRealtime, DataSync.

Команды enable/disable и изменения таймфреймов должны поступать в runtime непосредственно после commit конфигурации. Основной HTF-цикл остаётся сверкой, а не единственным механизмом применения. Callback проверяет актуальную generation подписки; поздние сообщения старой подписки не исполняются после барьера отключения.

При reconnect сохранять разделение «соединение установлено», «цена свежая», «история непрерывна», «курсор расчёта догнал». Recovery имеет отдельное состояние; факт подключения не делает пропуски восстановленными. Повторное закрытие свечи и REST/WS-ревизии обрабатываются идемпотентно.

Критерии приёмки:

- AC24: после успешного disable не создаются новые live-события; запоздавший callback старой generation игнорируется и учитывается диагностикой.
- AC25: enable/disable и смена ТФ применяются не позднее 2 с при доступном локальном scheduler; принятую pending-работу завершить или отменить по документированной политике.
- AC26: reconnect с пропуском H1, повтором closed kline и запоздавшим forming snapshot сохраняет причинность, терминальность закрытия и один экземпляр события.

## TZ07 Общая валидация входных данных

Приоритет P1. Закрывает A13. Область: adapters, модели входа, ingest, instruments/manual zone/review API.

Для всех источников проверять конечность и положительность цен, `low <= open/close <= high`, порядок времён, допустимый ТФ, соответствие instrument/source и строгий boolean closed. Проверять сеточную привязку времени с учётом календаря источника; не навязывать UTC Monday источнику с другим документированным календарём. Ошибка нормализации должна оставлять диагностическую запись без включения повреждённой свечи в расчёт.

Для instrument API разрешать только реализованные venue и market_type, валидный symbol и ограниченную precision. Для ручных зон и корректировок проверять положительные конечные границы, допустимый якорь и лимиты текстов. Не заменять ручную разметку автоматически новой догадкой алгоритма.

Критерии приёмки:

- AC27: NaN, Infinity, high<low, отрицательная цена, неверный closed и неправильные времена не попадают в рабочую таблицу свечей ни через REST, ни через WS.
- AC28: неизвестная площадка, неподдерживаемый market_type и некорректная ручная цена возвращают 422/400 с полями ошибок и без записи в БД.
- AC29: валидные Binance/Bybit/Hyperliquid fixtures сохраняют значения, source и календарь; повторная ревизия не создаёт дубликат revision.

## TZ08 Доступ без постоянного токена в ссылках

Приоритет P1. Закрывает A14 и часть A21. Область: auth, common.js, внутренние ссылки, Telegram buttons, reverse proxy configuration.

Постоянный токен обменивать на ограниченную серверную сессию. Для браузера использовать защищённую HttpOnly-сессию с подходящими Secure/SameSite и CSRF/Origin гарантиями; для локального HTTP отдельно определить режим разработки. Ссылки на актив или график должны содержать только идентификатор объекта и параметры вида. Пользователь без сессии проходит вход, после которого возвращается к исходному адресу.

WS авторизовать через сессию либо одноразовый короткоживущий ticket; постоянный owner token исключить из query. Старый URL-токен при миграции допускается только в явно ограниченном сценарии обмена, после чего удаляется из URL и больше не распространяется. Не логировать credentials. CDN-скрипт графика включить в сборку либо закрепить ресурс с проверкой целостности и совместимой политикой CSP.

Критерии приёмки:

- AC30: переходы между HTF/LTF/ALT, копирование ссылки и Telegram-кнопка не содержат owner token; после входа открывается нужный объект.
- AC31: logout/revocation прекращает доступ HTTP и WS; 4401 приводит к входу, 4403 — к понятной ошибке без бесконечного reconnect.
- AC32: отрицательные тесты токена, Origin/CSRF, истёкшей сессии и ticket проходят; query/access logs не содержат постоянных секретов.
- AC33: защищённый небраузерный API-клиент сохраняет документированный способ доступа; неверная авторизация возвращает отказ, не 500.

## TZ09 Правдивая готовность и метрики

Приоритет P1/P2. Закрывает A15, A17. Область: health API, metrics, realtime health, frontend freshness.

Разделить liveness процесса, readiness расчёта и состояние внешних источников. Проверять calc lease, heartbeat циклов, фазу restore, pending/quarantine, обработанные курсоры. Публичный liveness возвращает минимум информации; подробности остаются в защищённой диагностике. Кратковременная недоступность биржи не должна создавать restart loop.

Исправить interval lag, возраст худшего обязательного канала и семантику RSS. Нормализовать HTTP methods и причины в конечные множества, ввести верхнюю границу числа time series. Отдельно публиковать intake lag, pending count, oldest pending age, processed cursor, failures, retry/quarantine, discarded stale generation и outbox pending/uncertain/exhausted.

Критерии приёмки:

- AC34: HTTP доступен, но calc не владелец/остановлен — readiness не объявляет сервис готовым; отсутствие истории обозначается pending.
- AC35: одна задержка event loop после восстановления не навсегда завышает следующие измерения.
- AC36: при одном свежем и одном зависшем инструменте aggregate не показывает оба здоровыми; диагностика указывает проблемный канал.
- AC37: 10 000 произвольных значений HTTP method или reason не создают неограниченное число series; текущая и пиковая память различаются по названию.

## TZ10 Ограниченные очереди UI и запросы истории

Приоритет P1/P2. Закрывает A16, A18. Область: WsHub, REST candles, WS closed path, repository reads.

У каждого WS-клиента должна быть ограниченная очередь, send timeout и контролируемое отключение при отставании. Заменяемые price-снимки объединять до последней версии. Значимые события восстанавливать из durable-журнала по cursor; после разрыва клиент получает согласованный snapshot. Уточнить порядок state_seq при конкурентных broadcasts.

Добавить запрос хвоста свечей на SQL-уровне с LIMIT и обратным порядком для доставки клиенту. Закрытую WS-свечу сравнивать с необходимым диапазоном и обработанным курсором, а не всей историей. Оптимизировать по плану запроса и измерениям; не менять causal replay ради скорости.

Критерии приёмки:

- AC38: один искусственно медленный WS-клиент не увеличивает задержку остальных и не создаёт неограниченные tasks; memory возвращается к устойчивому уровню после отключения клиента.
- AC39: при цене 100 сообщений/с клиент получает последнюю версию, а все значимые события доступны после восстановления по cursor.
- AC40: запрос последних 300 свечей не десериализует всю историю; на 100 000 и 1 000 000 строк план использует индекс и ограниченный хвост.
- AC41: оптимизированный replay даёт те же состояния и события, что эталонный, за исключением заранее описанных и отдельно принятых исправлений дефектов.

## TZ11 Воспроизводимый релиз и восстановление

Приоритет P1/P2. Закрывает A19, A22. Область: packaging, Docker, CI, tools, эксплуатационная документация.

Закрепить проверенную Python-версию и lock/constraints транзитивных зависимостей. Собрать wheel и контейнер из чистого checkout; явно включить schema и static assets. Запуск контейнера выполнять без root после подготовки прав persistent volume. Проверить bind host и порт для целевой платформы, не полагаться на локальные defaults.

На Linux использовать production-профиль; на Windows обязательно проверить ownership, пути и shutdown. - AC45: restore возвращает настройки, зоны, ревью, курсоры, pending/uncertain-доставки и согласованные версии; результат проверяется автоматически.

## Нагрузочный протокол и целевые показатели

Числа ниже — стартовые цели приёмки, а не результаты текущего аудита. Перед оптимизацией сохранить baseline на одном стенде: ОС, CPU, RAM, Python, lock, режим SQLite, размер БД и хеш входного replay. Сравнивать одинаковые данные до/после. Сетевое время внешних бирж и Telegram измерять отдельно от внутреннего времени сервиса.

| Сценарий | Цель |
|---|---|
| 10 инструментов, суммарно 100 тиков/с, 30 минут | Нет потерянного accepted intake; нет дублей событий |
| Burst 500 тиков/с в течение 60 секунд | Backlog видим, память ограничена; после burst очередь догоняет без потерь |
| Intake → durable persist | p95 ≤100 мс при штатной нагрузке |
| Получение → доступность новой цены для обычного WS-клиента | p95 ≤500 мс при штатной нагрузке |
| Возраст старейшего pending в устойчивом режиме | p95 ≤2 с; превышение отражается как отставание |
| Готовое событие → durable намерение доставки | p95 ≤1 с; не зависит от опустошения всей очереди |
| Event loop lag | p95 ≤100 мс; устойчивое превышение выявляется диагностикой |
| Чтение 300 свечей при 1 млн строк истории | p95 ≤300 мс на согласованном стенде, с индексным запросом |
| Shutdown | ≤30 с; по истечении бюджета pending остаётся восстановимым |
| 24-часовой soak | Нет монотонного роста незавершённых задач/series/очередей после стабилизации нагрузки |

Если baseline показывает недостижимость цели на согласованном оборудовании, представить профиль затрат и уточнённую конфигурацию стенда. Не повышать порог молча и не удалять рыночные входы ради отчётной задержки. Глобальная сериализация тяжёлого расчёта допустима, пока выполняются цели и intake остаётся независимым.

## Матрица обязательных отказов

| Отказ | Ожидаемое поведение |
|---|---|
| REST timeout или Retry-After | Ограниченный retry, сохранённая причина, другие инструменты продолжают работу |
| WS разрыв и повтор сообщений | Recovery, дедуп и один результат закрытия свечи |
| Исключение детектора | Durable retry/quarantine, видимое неполное состояние |
| SQLite busy | Ограниченное ожидание вне event loop; нет ложного подтверждения записи |
| Disk full | Intake не подтверждён; явный degraded и уведомление эксплуатации |
| Kill после intake | Pending восстанавливается |
| Kill после события до outbox | Намерение доставки восстанавливается без дубля события |
| Telegram принял, ответ потерялся | Uncertain, без слепого автоповтора |
| Второй процесс или lease takeover | Один действующий writer; старый fencing token отвергнут |
| Settings timeout и поздняя ошибка | Job получает failed; предыдущая effective version остаётся рабочей |
| Медленный браузер | Ограниченная очередь/отключение; остальные клиенты не страдают |
| Поздняя задача при shutdown | Не получает закрытую БД; pending корректно переносится на восстановление |

## Миграция и выпуск

Перед миграцией создать проверяемую резервную копию на остановленном writer либо штатным согласованным backup API. Зафиксировать версии схемы, профиля и приложения. Новые поля добавлять совместимо; новые pending-записи не должны пропасть при откате. Миграция не изменяет пользовательские review и ручные границы.

Сначала выполнить replay и fault injection на копии. Затем провести ограниченный запуск с диагностикой и контролем backlog; для уведомлений использовать тестового sender до сверки результатов. Критерии возврата: потеря входов, дубли событий, нарушение причинности, некорректный takeover, зависший shutdown или смешение config versions. Возврат версии приложения разрешён только при подтверждённой совместимости схемы; иначе применять процедуру восстановления копии.

Поставка включает код, миграции, lock, CI, полный test report, нагрузочные результаты, browser screenshots, backup/restore протокол и обновлённый индекс контрактов. Каждый AC имеет статус passed/failed/not run и ссылку на доказательство. `Not run` не считается выполнением. Все P0 и P1 закрываются до выпуска; отложенные P2 перечисляются с последствиями и ответственным решением о переносе.
