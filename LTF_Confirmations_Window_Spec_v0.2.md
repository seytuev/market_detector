# LTF Confirmations — отдельное окно в приложении HTF Zones

**Версия 0.2 · 18 сентября 2026 года.** Полная актуальная редакция LTF-ТЗ для реализации в существующем приложении. Заменяет LTF_Confirmations_Spec_v0.1.md. Источник торговых требований — ответы пользователя и предоставленные схемы, включая IMG_5535.png. HTF-состояния наследуются из HTF_Zones_Spec_v0.3.md. Это спецификация, не отчёт о готовом коде или проверенной прибыльности.

Последнее уточнение: если OB/FVG хотя бы частично подходит по Premium/Discount, уведомление отправляется при первом допустимом касании **любой части полного исходного диапазона зоны**.

## 1. Задача и границы реализации

Добавить в существующее приложение отдельный раздел/окно **«LTF Confirmations»**: наблюдение структуры H1 после достижения HTF-зоны, обнаружение BOS и SMS, построение Premium/Discount, поиск Entry Zones, уведомления и отмена сценариев. Использовать существующие авторизацию, инструменты, котировки, фоновые задачи, график, настройки Telegram и размещение Railway, если они уже реализованы. Проверить фактический код перед выбором библиотек и API; названия сущностей/методов ниже — проект контракта.

Только H1: структура, FVG, OB, BSL/SSL и закрытия. H4/M15/M5 и автоматическое исполнение сделок в эту редакцию не входят. Entry Zone означает место для внимания пользователя, а не автоматически открытую позицию. Формулы стопа, целей, RR и размера позиции не заданы и не вычисляются произвольно.

HTF-модуль остаётся источником старших зон. LTF не создаёт конкурирующую версию их границ и валидности. Исходные активы и источник наследуются из списка приложения; нельзя смешивать Binance BTCUSDT, BTCUSDC и данные другого рынка в одном сценарии.

## 2. Согласованные торговые правила

| Вопрос | Актуальное правило |
| --- | --- |
| Таймфрейм | Только H1 |
| Подтверждения | BOS и самостоятельный SMS; обязательной комбинации BOS+SMS нет |
| Первичный/вторичный BOS | Первичный запускает поиск; вторичный не является обязательным условием входных зон |
| Фиксация слома | Закрытие H1 строго за соответствующим структурным уровнем |
| Медвежий контекст | HTF Bear → Bear BOS/SMS → FVG/OB/BSL в Premium |
| Бычий контекст | HTF Bull → Bull BOS/SMS → FVG/OB/SSL в Discount |
| Диапазон | Последняя связанная пара LH→LL для bear; HL→HH для bull |
| Подтверждение новой границы диапазона | Три закрытые свечи справа |
| Пересчёт | После подтверждения нового экстремума; до этого сохраняется предыдущий диапазон |
| Происхождение Entry Zones | Только движение, приведшее к конкретному BOS/SMS |
| Попадание OB/FVG в половину | Достаточно частичного пересечения; исходные границы не обрезать |
| Касание подходящего OB/FVG | Любая часть полного диапазона зоны |
| Количество Entry Zones | Все подходящие, без выбора одной «лучшей» |
| Уже протестированная H1-зона | Исключается, в том числе если тест был за время ожидания экстремума |
| BSL/SSL | Уровень снимается и та же H1-свеча закрывается обратно на исходной стороне |
| BOS/SMS есть, зон нет | Сообщить о сломе отдельно, показать ожидание зон/диапазона |
| Обратный слом | Отмена текущего сценария, уведомление, ожидание нового сценария по исходному HTF-направлению |
| Слом после выхода из HTF | Допускается после предшествующего достижения этой HTF-зоны |
| Срок наблюдения снаружи HTF | Не определён пользователем; автоматические «24 часа» не вводить |
| Judas Swing | Пока без автоматического фильтра или изменения сигналов |

Инженерные решения ниже — предложения реализации, а не новые условия торговой модели. Открытые трактовки собраны в §16; они не скрываются за произвольными коэффициентами.

## 3. Окно LTF: интерфейс

### 3.1. Навигация

Добавить пункт **LTF** в основную навигацию. Это отдельная страница/вкладка внутри приложения, не отдельная регистрация и не обязательное всплывающее окно браузера. В карточке HTF-зоны — действие «Открыть LTF»: переход к связанному наблюдению. При нескольких сценариях показывать их историю.

### 3.2. Компоновка для компьютера

- Верхняя панель: актив/биржа, выбранная HTF-зона, «H1», состояние потока, время последней цены и последней закрытой H1-свечи.
- Слева: список наблюдений с активом, HTF-направлением и статусом: ожидание слома / ожидание диапазона / Entry Zones / цена в зоне / отменён.
- В центре: H1-график. Отобразить HTF-диапазон, подтверждённые HH/HL/LH/LL, линии BOS/SMS, текущие границы расчётного диапазона, 50%, Premium/Discount и Entry Zones.
- Справа: список Entry Zones выбранного сценария, причины включения и текущее состояние; ниже журнал событий.
- Отдельные вкладки «Активные», «История», «Все»; фильтры актив, HTF D1/W1, направление, BOS/SMS, тип Entry Zone.

Не требовать входа в карточку каждой зоны для просмотра цены. Данные обновляются потоком без перезагрузки страницы. Состояние «нет подходящих зон» отличается от «нет данных».

### 3.3. Карточка сценария

Поля: инструмент/биржа/рынок; родительские zone_id, тип, TF, направление и границы; время достижения HTF; BOS/SMS и этап; уровень слома и время закрытия; исходные экстремумы с датами; диапазон [R_low;R_high], середина; состояние наблюдения; количество свежих Entry Zones; последняя отмена/причина; качество данных.

Не писать «внутри HTF», если слом произошёл после выхода. Вместо этого: «после касания HTF-зоны». Если точное пространственное положение внутри пробойной свечи не установлено, использовать нейтральное «в контексте HTF-зоны».

### 3.4. Таблица Entry Zones

Колонки: тип; направление; полный диапазон/уровень; середина OB/FVG; время подтверждения; Premium/Discount; «частично» при частичном пересечении; расстояние от цены; статус; событие первого касания; ссылка на исходные свечи.

Выбор строки подсвечивает соответствующую зону на графике. Действия: «Показать на графике», «TradingView», «История». Нет кнопки автоматической покупки/продажи. Состояние «снятие ожидает закрытия H1» заметно отличается от «снятие подтверждено».

Для расстояния до диапазона [L;U] при P>0: dist_abs=max(L−P,0,P−U), dist_pct=100×dist_abs/P. Для уровня K: dist_abs=abs(P−K). Это показатель интерфейса, не фильтр допуска.

### 3.5. График и мобильная версия

На графике различать дату экстремума и время его подтверждения. Неподтверждённые точки можно показывать пунктиром с подписью «кандидат», но не использовать в сигналах. Линия BOS/SMS заканчивается на свече фактического закрытия за уровнем; в подсказке — когда событие стало доступно алгоритму.

Premium/Discount показывать лёгкой заливкой; сами Entry Zones не теряют полные края. На мобильном: карточка HTF-контекста → график → список зон → журнал. Список сценариев открывается отдельной панелью. Ключевые действия доступны без горизонтальной прокрутки таблицы.

Интерфейс не выводит наружу технические поля вроде schema_version; они доступны только в диагностике.

## 4. Связь с HTF и запуск наблюдения

Основной согласованный сценарий — подтверждённый валидный OB D1/W1. В HTF-карточке визуально можно выбирать родителя. Поддержку других типов предусмотреть в контракте, но не включать автоматически для всех: применимость конкретных стартовых событий FVG/PRB/Breaker/SSL/BSL для LTF требуется уточнить.

Наблюдение открывается после фактического достижения соответствующего HTF-OB. Подгрузить историю H1 до касания, чтобы понимать предшествующую структуру. Исторические точки до касания допустимы как контекст, но BOS/SMS, уже завершившийся до касания, не выдавать как новый сигнал от него. Предложение консервативной политики: такой случай только в истории; точная политика ретроактивации не согласована.

HTF-событие поступает независимо от доставки Telegram. Пятидневное подавление повторного HTF-сообщения не блокирует создание/продолжение наблюдения и не является TTL LTF.

Согласно актуальному HTF-ТЗ, OB D1/W1 остаётся валидным после глубоких тестов, включая 90%, до подтверждённого пробоя в обратную сторону. Поэтому max_depth>=0.9 не закрывает LTF-наблюдение. Отдельный запрет образования Breaker также не означает невалидность OB.

**Предлагаемая политика жизненного цикла:** при достоверной инвалидации родителя прекратить поиск новых Entry Zones и закрыть активный сценарий с причиной HTF_INVALIDATED. При преобразовании в Breaker не менять молча направление старого сценария: новый тип/цикл — отдельный родительский контекст. При недостатке данных показывать paused_data, не объявлять торговую отмену.

После ухода из HTF продолжать наблюдение до обратного слома текущего сценария, инвалидации родителя или ручного завершения; отсутствие автоматического таймера — явное техническое решение до ответа пользователя о сроке. Обратный слом отменяет сценарий, но оставляет наблюдение валидного родителя в ожидании нового подтверждения нужного направления.

## 5. Экстремумы, роли и доступность данных

### 5.1. Локальные экстремумы

Для свечи i при l свечах слева и r справа:

`pivot_high(i) = High_i > max(High_j), j∈[i−l,i−1]∪[i+1,i+r]`

`pivot_low(i) = Low_i < min(Low_j), j∈[i−l,i−1]∪[i+1,i+r]`

Используются только закрытые H1-свечи. Pivot известен после закрытия i+r, а не в момент открытия i. Хранить pivot_at и confirmed_at отдельно.

Для структуры ранее согласованы настройки 3–5 слева/справа. Предложение default — 3+3. Для **новых границ Premium/Discount** последнее уточнение требует именно три закрытые свечи справа; в текущем профиле использовать 3+3 для этих опор. Если структурный профиль изменён на 4/5, структурные и диапазонные подтверждения хранятся отдельно, не заявлять структурный pivot подтверждённым раньше его собственного правила. Настройки должны явно показывать это различие.

Равные пики/дно: в базовой строгой реализации не образуют новый подтверждённый pivot; правила plateau отдельно не согласованы. Для неоднозначной свечи, которая одновременно является high- и low-pivot, не выдумывать порядок внутри: младшие данные или ambiguous.

### 5.2. Структурные роли

Последовательность HH/HL — восходящая; LH/LL — нисходящая. Локальный pivot и его структурная роль — разные сущности. Опорный HL — минимум отката, после которого сформировался следующий HH. Если вместо HH сформирован более низкий максимум, внутренний минимум участвует в SMS. Зеркально для нисходящей структуры.

Хранить связи role_assigned_at, preceding/opposite_pivot, promoted_by_pivot. При пересмотре роли сохранять историю. Предложение выбора среди нескольких однотипных кандидатов до противоположного свинга: более крайний high/low; равные значения не разрешать произвольно. Эта инженерная политика должна быть явной в rule_version и проверена на размеченных примерах.

## 6. BOS и SMS: формальные условия

Названия используются по методике пользователя. Общие условия: подтверждённые необходимые опоры, closed=true и строгое закрытие за уровнем. Тень, текущая незакрытая свеча и Close=level сломом не являются.

`bear_break(level,t) = closed(H1_t) AND Close_t < level`

`bull_break(level,t) = closed(H1_t) AND Close_t > level`

Не создавать повторное событие на каждом следующем закрытии за уже пробитым уровнем. Один структурный уровень/этап в данном сценарии имеет одно событие слома.

### 6.1. Медвежий BOS

Исходно HH/HL. H_peak — последний HH; L_ref — предшествующий опорный HL.

1. Закрытие H1 ниже L_ref — первичный BOS; поиск Entry Zones запускается сразу.
2. Формируется L_first ниже L_ref.
3. Формируется откат H_pullback < H_peak.
4. После отката закрытие ниже L_first — вторичный BOS. Это дополнительное подтверждение в том же сценарии, не обязательный допуск поиска входа.

Непрерывное падение через несколько уровней без промежуточного отката не является двумя этапами по этой модели. H_pullback не обязан быть ниже L_ref: такой дополнительный фильтр не согласован.

### 6.2. Бычий BOS

Зеркально: исходно LH/LL; L_bottom — последний LL, H_ref — предшествующий опорный LH. Close>H_ref — первичный BOS; далее H_first, откат L_pullback>L_bottom, затем Close>H_first — вторичный BOS. Поиск входных зон начинается с первичного.

### 6.3. Медвежий SMS

На восходящей структуре после H_peak появляется внутренний минимум L_internal выше опорного L_ref, затем H_pullback<H_peak. Закрытие H1 ниже L_internal фиксирует SMS; на показанном эталоне опорный L_ref ещё не пробит. SMS самостоятелен, ожидание BOS не требуется.

Схематические отношения: L_ref<L_internal, H_pullback<H_peak; пробивается внутренний L_internal. Позднейший выход ниже L_ref возможен и не стирает предыдущий SMS.

### 6.4. Бычий SMS

Зеркальный профиль для реализации: в нисходящей структуре после L_bottom появляется внутренний H_internal ниже опорного H_ref, затем L_pullback>L_bottom; закрытие выше H_internal при ещё не пробитом H_ref фиксирует bullish SMS. Зеркальный поиск согласован пользователем; отдельного реального свечного эталона bullish SMS пока нет, его необходимо получить при приёмке.

### 6.5. События на одной свече и отмена

Если одна свеча пересекает внутренний и внешний структурные уровни, сохранить оба доказательства. Предложение отображения: одно уведомление с обоими фактами, без двух копий Entry Zones; основной тип BOS, SMS — сопутствующий факт, если условия обоих выполнены. Это политика устранения дублей, не новое подтверждение «двойной силы».

Противоположный подтверждённый структурный слом отменяет активный сценарий: отмена не ждёт второго этапа. По широкому ответу пользователя предлагается применять это к обратному BOS и самостоятельному SMS; поскольку ранее подробно подтверждался именно обратный BOS, вид отменяющего паттерна сохранять явно и проверить обратный SMS отдельным эталоном. На тех же данных не публиковать вход от уже отменённого сценария.

Отмена медвежьего LTF в медвежьем HTF не создаёт самостоятельный long-сигнал. Родительское наблюдение возвращается в ожидание нового bear BOS/SMS. Позднейшие LH/LL или HH/HL в том же направлении — продолжение, а не поток новых независимых сигналов.

## 7. Диапазон Premium / Discount

Для bear: последняя связанная пара подтверждённых LH→LL выбранного движения. На IMG_5535.png — последняя красная верхняя точка и следующая за ней красная нижняя, а не глобальный зелёный HH.

Для bull: зеркальная пара HL→HH.

`R_low = low_price выбранной пары`

`R_high = high_price выбранной пары`

`M = (R_high + R_low)/2`

`Discount = [R_low; M]`, `Premium = [M; R_high]`.

При R_high<=R_low диапазон не строится. Последний LH одновременно является кандидатом BSL для медвежьего входа; последний HL — SSL для бычьего. Область Premium/Discount относится к LTF-диапазону, а не к середине родительского HTF-OB.

Новый LL/HH до трёх закрытых правых свечей — кандидат; действующий диапазон не меняется. После подтверждения пересчитать обе половины, применимость всех зон и сохранить range_version. Старое уведомление и его диапазон не переписываются задним числом.

**Первичный BOS без готовой пары:** отправить BOS, запустить поиск, показать range_pending. Не подменять отсутствующий LH глобальным HH молча и не выдавать неподтверждённый минимум за LL. Конкретный запасной якорь для такого раннего случая пользователь не определил; до появления допустимой пары нет готового фильтра Premium/Discount. Это ожидание геометрии, а не обязательное требование вторичного BOS.

При продолжении движения новая подтверждённая опора может изменить диапазон текущего сценария. Зоны сохраняют исходные цены; меняется результат пространственного фильтра. Зона вне нужной половины получает out_of_range, а не market_invalid. При возвращении в подходящую половину она может снова рассматриваться только если всё ещё не тестировалась и относится к исходному причинному движению.

## 8. Обнаружение Entry Zones и происхождение

После BOS **или** SMS сразу запускать поиск. При готовой паре фильтровать по половине. Список включает все свежие подходящие зоны; не ранжировать и не скрывать по выдуманному score.

### 8.1. Привязка к движению

Нужны movement_id, start_pivot_id, start_at, break_event_id, end_pivot_id, end_at, confirmed_at и source_candle_ids. Entry Zone должна быть сформирована движением, приведшим к данному BOS/SMS; ранее существовавшие посторонние зоны не добавлять только из-за нахождения в Premium/Discount.

Для выбранного bear LH→LL или bull HL→HH состав движения восстанавливается по связанным структурным опорам и свечам, а не по ближайшей к цене зоне. OB-основание у начальной опоры и его подтверждающий импульс составляют одну причинную цепочку; нельзя отбрасывать основание только потому, что часть его свечей предшествует pivot_at.

Точная нижняя временная граница многосвечной базы и тройки FVG на стыке движения требует эталонов. Базовая проверка: подтверждающее движение/FVG принадлежит выбранной структурной ноге; включение исходных свечей сохраняется в доказательствах. После более позднего продолжения структуры пересчитать Premium/Discount, но не добавлять автоматически любые новые зоны последующих движений без связи с исходным сломом. Расширение причинного движения — отдельное открытое решение, §16.

### 8.2. FVG H1

Три закрытые последовательные свечи:

- Bull: `High_1 < Low_3`, диапазон `[High_1; Low_3]`.
- Bear: `Low_1 > High_3`, диапазон `[High_3; Low_1]`.

Подтверждение после закрытия третьей. Использовать прежние правила HTF для геометрии, но отдельный жизненный цикл Entry H1: первое последующее касание потребляет зону для этого поиска. Не требовать 50% заполнения, чтобы убрать H1 Entry Zone. Формирующие три свечи не считать её ретестом; иначе третья всегда ошибочно «тестирует» собственный край.

### 8.3. OB H1

Применять согласованную геометрию OB: противоположная свеча либо связанная консолидация перед импульсом с внешним FVG; оба цвета допустимы в единой базе без самостоятельного импульса внутри. Включать соответствующую тень импульсной свечи, расширяющую экстремум основания. Сохранять базу, отдельные якоря границ и подтверждающий FVG.

Пока OB не подтверждён, он кандидат, не готовая Entry Zone. Направление OB должно совпадать с направлением LTF-сценария. Общий алгоритм детектора переиспользовать из HTF с H1-свечами; ранее открытые критерии выделения базы не заменять новыми произвольными ATR/процентными фильтрами.

### 8.4. BSL/SSL H1

Уровень — экстремум по тени. Для bear — BSL в Premium, включая верхний LH выбранной пары; для bull — SSL в Discount, включая нижний HL. Уровень должен относиться к движению сценария. Рождение самого экстремума не является его последующим снятием.

Входное условие у уровня — не просто касание: снятие и возврат закрытия той же H1-свечи на исходную сторону, §10.

### 8.5. Частичное попадание и полный диапазон касания

Для зоны Z=[Lz;Uz], целевой половины T=[Lt;Ut]:

`eligible_overlap = max(Lz,Lt) <= min(Uz,Ut)`.

Для уровня K: `Lt<=K<=Ut`. Обе половины включают M; предложение реализации границы — равенство считается попаданием. Это граничный случай для приёмки, а не скрытый процент пересечения.

При частичном попадании не обрезать Z до пересечения. Касание проверяется по полному Z:

`touch_price = Lz<=P<=Uz`

`touch_bar = High>=Lz AND Low<=Uz`.

**Согласованный пример:** Premium начинается на 100, OB=[98;102]. Зона подходит; при движении снизу уведомить уже на 98, не ждать 100. Одновременно показать «частично в Premium».

При подтверждённом гэпе через всю зону без цен внутри не утверждать фактическое касание только по отрезку между двумя котировками. Исторический OHLC без последовательности не позволяет восстановить все внутрисвечные события.

## 9. Свежесть и ожидание трёх свечей

Сохранять first_test_at по всей доступной истории после рыночного подтверждения самой Entry Zone, а не только после появления её карточки.

`fresh_at(T) = нет допустимого последующего касания/снятия или пробоя до момента T`.

Если во время ожидания трёх правых свечей экстремума OB/FVG уже протестирован, его не включать в готовый список и не отправлять запоздалое сообщение как о новой возможности. Для BSL/SSL уже снятый до готовности уровень исключается. Равное касание уровня без снятия — отдельный пограничный случай; предложение консервативного режима свежести — считать протестированным, не выдумывая нового ликвидностного события.

После публикации свежей Entry Zone первое касание:

- OB/FVG: зафиксировать touch, поставить уведомление в очередь, вывести из списка свежих; сохранить в истории. Не скрывать карточку события мгновенно — показать «касание зафиксировано».
- BSL/SSL: уведомить о достижении один раз, перевести в ожидание исхода текущей H1-свечи; убрать из свежих кандидатов, но продолжить проверку уже начатого события до закрытия (§10).

Отказ Telegram не отменяет факт касания; повторять доставку того же события, не создавать новый тест. Удаление Entry Zone из свежих не отменяет весь LTF-сценарий или актуальность HTF-родителя. Другие Entry Zones продолжают отслеживаться.

## 10. Снятие BSL/SSL и закрытие той же свечи

Для уровня K и закрытой H1-свечи s:

`BSL_sweep_confirmed = High_s > K AND Close_s < K`

`SSL_sweep_confirmed = Low_s < K AND Close_s > K`.

Это формализация согласованного возврата под BSL/над SSL. Close=K не является строгим возвратом; обозначить как неподтверждённый исход, проверить в приёмке. Одной тени до закрытия недостаточно для утверждения подтверждённого условия входа.

Если High>K, а Close>K для BSL — возврата нет. Для SSL зеркально. Не ждать ещё несколько свечей и не объявлять поздний возврат подтверждением той исходной свечи. При обратном структурном сломе дополнительно отменить сценарий по §6.5.

Если было только равное касание K, а превышения не было, событие достижения допустимо, подтверждённого снятия нет. Начальный подход, первое касание и текущая свеча должны быть записаны, чтобы не использовать ранее снятый уровень повторно.

Предложение доставки: отдельное сообщение «BSL/SSL снят, H1 закрылась обратно» как продолжение события касания. Это не сообщение об исполненной сделке. Если пользователь не хочет дополнительный Telegram, состояние всё равно обязательно в интерфейсе; тип доставки можно отключить в настройках.

## 11. Уведомления

Использовать существующий Telegram-канал доставки владельцу и внутренний журнал. Содержание строится из реальных полей, без выдуманных цен. Время и источник обязательны; прикладывать график с той же версией диапазона и ссылку TradingView выбранного инструмента.

### 11.1. BOS/SMS с зонами

> [Инструмент] · H1
> Произошёл [Bearish/Bullish] [BOS/SMS] [внутри / после касания] HTF [тип] [D1/W1] [направление].
> Возможности входа:
> FVG H1: [L–U]
> OB H1: [L–U]
> BSL/SSL H1: [K]
> [Premium/Discount]: [границы], 50%: [M].

Отображать все зоны, а не по одной каждого типа. При большом списке разбивать сообщение или давать полный список в карточке; не пропускать зоны незаметно. Для OB/FVG основная цена — диапазон, середина дополнительна.

### 11.2. Слом есть, диапазон или зоны ещё не готовы

> Произошёл [направление] [BOS/SMS] H1 в контексте HTF [зона].
> [Ожидаем подтверждения LL/HH тремя свечами / Подходящих свежих Entry Zones пока нет].

После готовности — одно дополнение с новыми Entry Zones того же сценария. Если на закрытии слома все данные уже доступны, отправить одно объединённое сообщение вместо двух.

### 11.3. Достижение Entry Zone

> [Инструмент]: цена пришла к Entry Zone — [FVG/OB/BSL/SSL] LTF H1.
> Зона: [L–U или K]. Цена события: [P].
> Сценарий: [направление] [BOS/SMS], HTF [тип/TF/направление].

Для ликвидностного уровня: «Ожидаем закрытия текущей H1 для проверки снятия без закрепления». Не писать подтверждение входного условия до её закрытия.

### 11.4. Отмена

> [Инструмент]: [направление] LTF-сценарий отменён.
> Причина: [обратный BOS/SMS H1 / инвалидация HTF / ручное завершение].
> [Если HTF ещё валиден: ожидаем новое подтверждение по направлению этой HTF-зоны].

Структурная отмена не означает закрытие реальной позиции — данных о позиции нет.

### 11.5. Подавление дублей

Ключи по смыслу: scenario_id + structure_event_id; entry_zone_id + lifecycle_id + touch; level_id + sweep_candle_id; scenario_id + cancellation_event_id. Ключ касания не включает range_version: пересчёт диапазона не должен оживить уже использованную зону или повторно отправить её касание.

Новый подтверждённый LL/HH сам по себе не создаёт повтор BOS. Изменения диапазона обновляют интерфейс. Telegram-дополнение требуется при появлении ещё не сообщённых подходящих свежих зон, а не при каждом изменении M. Общая H1-зона нескольких родительских контекстов может давать одно сгруппированное сообщение со всеми ссылками, сохраняя независимые сценарии.

## 12. Состояния и данные

Разделить наблюдение HTF, направленный LTF-сценарий, диапазон, Entry Zone и доставку.

## 13. Интеграция, обработка и восстановление

Переиспользовать потоки цены и закрытий H1, не опрашивать каждую карточку отдельным запросом. Изолировать модуль LTF в существующем backend; отдельный микросервис не обязателен. Фактический транспорт адаптировать к проекту.

Предлагаемый контракт HTF: event_id, instrument, venue, market_type, symbol, zone_id/version/cycle, type, TF, direction, lower/upper, confirmed_at, is_valid, occurred_at, event_kind, data_quality. Нужны snapshot и события с курсором восстановления. Визуальное объединение HTF не уничтожает идентичность родителя.

Предлагаемый API окна: список наблюдений; карточка/графические слои; зоны входа; журнал; настройки; ручное завершение; поток обновлений SSE/WebSocket. Эти адреса не считать существующими до проверки проекта.

Обработка при закрытии H1 в одной согласованной транзакции/последовательности:

1. Проверить полноту и окончательность свечи.
2. Учесть касания опубликованных Entry Zones; закрыть ожидающие liquidity-тесты.
3. Подтвердить pivots, классифицировать структурные события и отмены.
4. При отмене не публиковать новый входной сигнал от отменённого сценария. Внутрисвечные ранее доставленные касания остаются в истории.
5. Обновить подтверждённый диапазон, обнаружить/проверить происхождение зон, воспроизвести их свежесть до текущего момента.
6. Сохранить итоговые состояния и события, поставить допустимые сообщения в очередь.

Если снятие и отмена приходятся на одно закрытие, журнал хранит оба факта; приоритет пользовательского сообщения — отмена, без противоположного «готов вход».

Live/replay используют один детерминированный движок. После перезапуска восстановить сценарии, range_version, первые тесты и доставки. Не отправлять массовые исторические касания как текущие. Восстановленные события сохраняют исходное время и метку задержки; политика их Telegram-доставки отдельна от обнаружения.

Миграция со старого LTF-проекта: отключить H4 в новом профиле, не удаляя историю; убрать обязательное ожидание второго BOS; не наследовать старую инвалидацию HTF-OB на 90%; не применять скрытый таймер 24 часа; не назначать старым записям новые Entry Zones без replay. Менять rule_version, а не переписывать старые доказательства.

## 14. Настройки окна

- Включить/выключить LTF-мониторинг; выбранные активы из существующего списка.
- Структурные pivots: 3–5 слева/справа, default 3+3 как предложение; опоры диапазона — три правые свечи согласно последнему уточнению, явно показано в интерфейсе.
- Типы отображаемых Entry Zones: FVG, OB, BSL/SSL; по умолчанию все.
- Доставка: BOS/SMS, готовые Entry Zones, касание, исход liquidity-теста, отмена; выключение доставки не меняет рыночный анализ.
- Отображение: родительская HTF, pivots, BOS/SMS, Premium/Discount, свежие/исторические Entry Zones.
- Нет обязательного H4, фильтра Judas Swing, автоматического стопа/тейка или неподтверждённого TTL.

## 15. Приёмка

1. Всё обнаружение и подтверждение текущего профиля работает на H1; H4 не требуется.
2. Тень за структурным уровнем не даёт BOS/SMS, закрытие строго за уровнем даёт при наличии нужных опор; равенство и незакрытая свеча не дают.
3. SMS самостоятельно запускает поиск; первичный BOS не ждёт вторичного.
4. Схемы BOS и SMS различаются по опорному/внутреннему уровню. Непрерывный импульс не создаёт два этапа BOS без отката.
5. Диапазон bear строится от последнего связанного LH к LL, bull — HL к HH. Глобальный максимум не подставляется вместо LH без отдельного правила.
6. До третьей закрытой правой свечи диапазон не обновляется. Исторический сигнал не переносится на время самого экстремума.
7. Новая подтверждённая опора создаёт range_version; старые события сохраняют прежнюю геометрию.
8. Premium от 100, OB 98–102: подходит, касание 98 отправляет сообщение; зона не обрезается до 100–102. Полностью неподходящая зона не включается.
9. Все подходящие FVG/OB/уровни показаны, независимо от количества; неподходящий по направлению или происхождению объект исключён с объяснением.
10. Зона, протестированная за время ожидания трёх свечей, не появляется как свежая и не даёт запоздалый новый вход.
11. Формирующие свечи FVG/OB не являются их последующим тестом. Доказательства границ совпадают с исходными OHLC.
12. Касание FVG/OB отправляет одно событие и убирает зону из свежих; повтор через пять дней не возникает для этой H1 Entry Zone.
13. BSL High>K, Close<K — подтверждение снятия на закрытии той же свечи; SSL зеркально. High=K, незакрытая свеча, Close=K и Close за уровнем не дают этого подтверждения.
14. Первый touch уровня не прекращает обработку его уже начатой H1-свечи. Последующее закрытие создаёт исход теста, не оживляя уровень для нового входа.
15. Обратный слом отменяет сценарий и уведомляет; при валидном родителе остаётся ожидание нового события нужного направления. Новые контр-HTF входы не создаются.
16. BOS/SMS после выхода из HTF допустим после её достижения; в сообщении нет ложного «внутри». Скрытого TTL 24 часа нет.
17. HTF OB с тестом 90% остаётся доступным LTF при is_valid=true. Запрет Breaker не закрывает его наблюдение.
18. BOS без диапазона/зон даёт отдельное сообщение; готовность зон — дополнение; одновременная готовность даёт одно объединённое сообщение.
19. Отмена и потенциальный вход на одном закрытии разрешаются последовательно без противоречивой новой рекомендации; история событий не стирается.
20. Повторные HTF-события, свечи, range-update и перезапуск не дублируют наблюдения/уведомления и не возвращают протестированные зоны в свежие.
21. График/таблица/Telegram используют одну версию данных и один источник. Stale/gap/ambiguous явно видны; фон работает при закрытой странице.
22. Положительные и отрицательные эталоны имеют точный symbol/venue/timeframe, OHLC и ожидаемые события; примеры без свечей проверяют логику схемы, но не доказывают точность рыночного детектора.

## 16. Открытые решения и пределы готовности

ТЗ достаточно для разработки окна, событий, Premium/Discount, свежести и уведомлений. Следующие вопросы не заполнять выдуманными торговыми условиями:

1. Политика времени наблюдения после ухода из HTF: пока автоматического ограничения нет; ручное завершение доступно.
2. Ранний первичный BOS без пары LH→LL/HL→HH: нет согласованного запасного якоря. Сообщение BOS есть, диапазон ожидается; нужен реальный пример выбора якоря, чтобы ускорить готовность Entry Zones без второго слома.
3. Границы причинного движения для многосвечной базы, тройки FVG на стыке и зон дальнейшего продолжения после первоначального BOS/SMS. Требуются эталоны, а не фиксированное «последние N свечей».
4. Применимость запуска к другим HTF-типам, кроме разобранного OB; не считать одинаковыми касание диапазона и снятие уровня.
5. Строгая обработка плато и пары pivots внутри одной свечи; предложенная консервативная политика не утверждена как авторское торговое правило.
6. Обратный SMS как причина отмены, совпадение BOS+SMS на одном закрытии, равенство середине/уровню — явно описанные инженерные политики для проверки на примерах.
7. Точный алгоритм автоматического выбора консолидации OB наследует открытые вопросы HTF; красивый интерфейс не доказывает правильность этого детектора.

Реальный ранее присланный пример был уточнён как BTCUSDC H4; он иллюстрирует последовательность, но не служит свечным тестом текущего H1-профиля. IMG_5535.png — схема без точных времён/OHLC. Для финальной приёмки нужны H1-примеры с источником и датами, особенно первый BOS до готовности диапазона и зеркальный bullish SMS.

## 18. Контекстный допуск FVG вне Premium (SSL sweep + тест 50% HTF FVG)

Сценарий: медвежий BOS; причинное движение сформировало FVG, не попавший в Premium диапазона (reason `outside_pd`), при этом обновление лоя движения было снятием SSL с одновременным тестом 50% бычьей D1 FVG. Такой вход допускается; факт «вне Premium» всегда отображается, но не блокирует. Bull — зеркально (хай, BSL, медвежья D1 FVG).

Детекция контекста (оба факта обязательны):

1. Снятие контр-уровня: подтверждённый low-pivot (для bear; high-pivot для bull), известный к моменту триггера сценария (confirmed_at не позже триггера), по которому закрытая H1 после триггера дала зеркальный исход §10: для SSL Low < K и Close > K. Экстремум, сформировавшийся в самом движении, прежней ликвидностью не является.
2. Тест 50% D1 FVG: среди активных/weakened D1 FVG противоположного направления — зона, чья середина достигнута экстремумом движения (для bear: минимум Low от триггера <= mid). Приоритет — зона с зафиксированным HTF-событием DEPTH_50/FVG_WEAKENED; запасной вариант — чистая геометрия.

Условия допуска: контекст полон (оба факта) И тип зоны FVG И reason == "outside_pd". Остальные отказы (type_disabled, tested_too_deep, invalid, swept_level, origin_unresolved) контекст не отменяет; уровни BSL/SSL и OB вне половины диапазона не допускаются. Границы зоны не обрезаются; строка ltf_scenario_entry сохраняет исходные reason/state — допуск происходит только при выборе кандидатов, ветка истории не переписывается.

Аннотации: в payload зоны (bos/sms/entries_ready/touch) — `half` (premium/discount/none) всегда; при контекстном допуске — `outside_premium: true` и краткий `context`. В Telegram: «⚠️ Зона вне Premium — не критично для этого сценария» и «Контекст: обновление лоя = снятие SSL + тест 50% D1 FVG». В вебе: бейдж «вне Premium» у зоны и блок контекста в карточке сценария.

Событие `context_update`: каждый новый факт контекста (снятый уровень, тест 50% D1 FVG) — отдельное событие журнала с дедуп-ключом по уровню/зоне (§11.5); replay и перезапуск не дублируют. Отдельно в Telegram не доставляется (группы в настройке доставки нет); смысл показывается аннотациями выше. Контекст читается агрегацией событий сценария — схема БД не меняется.
