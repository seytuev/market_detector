# ТЗ v2: HTF Zones — рабочее место наблюдения и проверки сценариев

Дата: 6 октября 2026 года. Статус: предложение к реализации, а не описание уже выполненной переработки.

## 1. Вывод и цель

Рекомендую кардинально изменить организацию приложения: сделать основным объектом работы **ситуацию по активу и следующее действие пользователя**. Зоны, структура и события остаются доказательствами этой ситуации. Пользователь открывает приложение, чтобы понять, где нужно внимание, проверить разметку и настроить наблюдение.

Сейчас приложение показывает много предметной информации, но пользователь сам связывает HTF-зону, контекст, H1-сценарий, диапазон, пригодность зон и доставку. Это особенно заметно при нескольких противоположных контекстах и проблемах данных. Расширение числа индикаторов без изменения этой организации усилит перегрузку.

Цель новой версии: за 10 секунд определить состояние выбранного актива, доступность данных, причину вывода и следующее действие. Проверка одного кандидата должна проходить в одном рабочем контексте. Переход из уведомления должен открывать точное событие и его объекты.

Первая очередь — достоверность наблюдения и доставки. Переработка экранов опирается на согласованные данные, поэтому исправления логики выпускаются раньше нового интерфейса.

Проект — Python/FastAPI + SQLite, два фронтенда на HTML/CSS/JS, отдельные циклы HTF/LTF и Telegram-бот в одном процессе. Уже есть значительная предметная основа:

Полная замена детектора или базы данных не является предпосылкой редизайна. Сначала завершить консистентность существующей модели, затем менять оболочку и пользовательские потоки.

Обозначения: **воспроизведено** — наблюдалось в отдельном эксперименте; **по коду** — подтверждён путь реализации, но последствия на production не измерялись; **UI** — наблюдение в браузере.

### 4.1. Воспроизведение A01

Использована существующая синтетическая серия `SERIES_H_HL` и setup из `tests/test_ltf_engine.py`. Свечи подавались последовательно до BOS; менялся только момент обработки относительно закрытия каждой свечи. Отправитель — `RecSender` из тестов.

## 5. Новая продуктовая организация

### 5.1. Навигация

Верхний уровень: **«Сейчас»**, **«Проверка»**, **«Журнал»**, **«Настройки»**.

«Сейчас» — рабочее место по активу. HTF и H1 становятся режимами одного графика и анализа: «Контекст D1/W1» и «Структура H1». Переключение сохраняет актив, выбранный контекст, сценарий и зону. Таймфрейм свечей и набор слоёв — разные настройки с разными подписями.

«Проверка» — устойчивый список задач с тем же графическим компонентом и инспектором. «Журнал» объединяет рыночные события, пользовательские решения и доставку, сохраняя фильтры по виду. «Настройки» содержит один редактор правил; второй независимый редактор LTF убрать после переноса его функций.

### 5.2. Основные сценарии

| Сценарий | Последовательность | Результат |
|---|---|---|
| Ежедневный просмотр | «Сейчас» → группа внимания → актив | Понятны состояние, свежесть и следующее действие |
| Проверка разметки | Задача → свечи формирования → решение/правка | Задача закрыта устойчиво; предметный статус зоны показан отдельно |
| Разбор H1 | Актив → контекст → причинное событие → пригодные зоны | Видны основания допуска и условия отмены |
| Наблюдение | Актив/сценарий → типы событий → включить наблюдение | Ясно, что отслеживается и какие уведомления придут |
| Переход из Telegram | Ссылка события → событие и версия → текущее состояние | Нет потери исходного контекста, даже если сценарий завершён |
| Разбор истории | Сценарий → момент времени → шаг по закрытиям | Показано только то, что было известно на выбранный момент |

### 5.3. Компоновка

На большом экране: слева активы, в центре график, справа краткий вывод и детали выбора, снизу сворачиваемые зоны/события. В верхней строке — актив, площадка/рынок, настоящая котировка и её возраст. Состояние обработки раскрывается рядом.

```text
Сейчас | Проверка | Журнал                         Настройки
BTCUSDT · Binance · spot     Цена / возраст     Качество данных
┌──────────────┬───────────────────────────┬─────────────────────┐
│ Активы       │ Контекст D1/W1 | H1       │ Что происходит      │
│ Внимание     │ График выбранного объекта │ Почему              │
│ Избранное    │                           │ Чего ждём           │
│ Поиск        │                           │ Условие отмены      │
│              │                           │ Наблюдать / Детали  │
├──────────────┴───────────────────────────┴─────────────────────┤
│ Подходящие зоны | События | Исключённые | История              │
└──────────────────────────────────────────────────────────────┘
```

На телефоне: актив → краткий вывод и свежесть → график → зоны/события. Выбор актива, слои и подробные доказательства открываются в панелях. Решения проверки закрепляются снизу над навигацией. Список кандидатов открывается отдельно, чтобы не отнимать высоту графика.

## 6. Требования к логике и данным

### F01. Разделить обычную задержку обработки и восстановление — P0

Заменить смысл одного `delayed` явными полями происхождения события: `processing_mode=live|catchup|replay`, `occurred_at`, `detected_at`, `detection_lag_ms`. При необходимости сохранить legacy-поле для совместимости, но не использовать сравнение двух времён как единственный запрет доставки.

Live-обработка с нормальной задержкой опроса создаёт доставляемое событие. Catchup/replay подавляет поток исторических сигналов. Допустимый возраст для доставки задаётся политикой по виду события, отдельно от определения режима обработки. После долгого сбоя показывать сводку восстановления и актуальное состояние.

**Приёмка:** серия A01 при задержках 1 с и 60 с отправляет BOS ровно один раз; replay той же серии не отправляет исторические BOS. Проверить также 5-минутный опрос, рестарт, повтор обработки и касание с последующей отменой.

### F02. Разделить каналы текущей цены и свечного анализа — P0

Выделить независимый цикл котировок. Предлагаемый стартовый интервал — 5–15 с для наблюдаемых активов, с ограничением частоты по возможностям адаптера, backoff и учётом квот. HTF-свечи обрабатывать после закрытий D1/W1; H1 — после закрытия H1 с контролируемой задержкой. Ошибка одного инструмента не задерживает все остальные.

Для intrabar-касания использовать доступный поток цен либо явно указать разрешение наблюдения. После пропуска наблюдения закрытая OHLC доказывает пересечение, но не точный порядок движения внутри свечи. Не выдавать восстановленное время касания за точно наблюдённое.

**Приёмка:** изменение котировки обновляет рабочее место независимо от обновления D1/W1. Для поступивших тиков касание фиксируется один раз. При polling интерфейс показывает его ограничение; короткий заход между опросами не объявляется доказанно отсутствовавшим.

### F03. Единый контракт качества данных — P0

Возвращать каналы: quote, H1/D1/W1 history, continuity, processing, replay. Для каждого — статус, последнее доступное время, возраст/порог и причина. Требуемые каналы зависят от действия: показ последней известной геометрии возможен без свежего тика, утверждение «цена сейчас внутри» требует свежей котировки, решение о пригодности требует завершённого расчёта по нужным свечам.

Сравнение курсоров обработки и свечей выполнять в одной семантике: `processed_close_time` с `latest_closed_close_time`. Условие своевременной обработки и количество пропущенных свечей выводить на сервере. Проверять разрывы ряда, а не только возраст последней свечи.

UI, `/status`, health и доставка используют одну функцию качества/допуска действия. Возраст на клиенте увеличивается по таймеру и переходит в stale даже при отсутствии новых WS-сообщений. Проблема данных получает отдельный заметный признак вне рыночной сортировки.

**Приёмка:** при свежей котировке и необработанной H1 карточка показывает «Расчёт отстаёт», новые сообщения о пригодности блокируются; после обработки статус восстанавливается. Разрыв в середине истории виден при свежем хвосте. HTF и H1 учитывают собственные пороги.

### F04. Согласованный снимок рабочего места — P0

Добавить серверную сборку `WorkspaceSnapshot`: выбранный контекст/сценарий, вывод, quality, текущая версия диапазона, строки зон и слои графика читаются из одной согласованной версии. Свечная история может загружаться отдельно по `data_revision`; ответ явно связывается со снимком.

Версия включает instrument/context, последовательность состояния и версии расчёта/данных. Изменения публикуются после завершения предметной операции. WS сообщает, какая область изменилась; клиент объединяет частые сообщения, перечитывает согласованный снимок и отклоняет устаревший ответ. Reconnect всегда синхронизирует снимок.

**Приёмка:** искусственная смена range между запросами не создаёт карточку v2 с зонами v1. Быстрое переключение BTC→ETH→BTC сохраняет правильный актив. Пересчёт не публикует промежуточный набор зон. Проверки охватывают несколько вкладок.

### F05. Настройки и пересчёт как управляемая операция — P0

Единая валидация API/файла/ENV: конечные числовые значения, целые числа без усечения дробей, нормализация перечислений, зависимости порогов. Некорректный конфиг при старте даёт ясную диагностику и явно выбранное последнее корректное состояние.

Редактор показывает значения до/после и затронутые активы. Аналитические параметры сохраняются как новая неизменяемая версия. Пересчёт выполняется фоновым заданием: queued → running → ready → published либо failed/cancelled. Старое согласованное состояние доступно с отметкой «Пересчитывается». Новая версия публикуется атомарно после готовности. Ошибка диска или вычисления не меняет действующую версию.

Настройки отображения применяются сразу, доставки — независимо от пересчёта. Предметные параметры меняются по одному общему пути; ручная строка `rule_version` не служит заменой версии конфигурации.

**Приёмка:** `ltf_structure_left=3.9` возвращает ошибку поля. Сбой записи/пересчёта сохраняет старое состояние и историю. После рестарта задание восстанавливается либо безопасно завершается с ошибкой. Старый BOS открывается со своими опорами.

### F06. Завершить единый отбор пригодных зон — P1

Сохранить `evaluate_final` как предметное правило. Убрать самостоятельные вариации отбора: либо материализовать окончательные решения в общей проекции, либо генерировать SQL-условия из того же формального правила и проверять эквивалентность.

Текущая версия range определяется одинаково во всех представлениях. Отсутствие зон текущей версии не заменяется молча предыдущей непустой версией. Старые зоны доступны в истории с подписью версии.

Решение содержит `eligible_now`, основание допуска, причины блокировки, момент оценки, версии правил/конфига/range и статус данных. Отдельно хранить геометрию, рыночную актуальность и отношение пользователя к объекту. Ручное подтверждение геометрии не оживляет завершённую зону.

**Приёмка:** множества ID в счётчике, таблице, графике и новом уведомлении совпадают на одном снимке для обычного допуска, контекстного исключения, теста ровно 90%, отключённого типа и смены range. Legacy-строки проверяются отдельно.

### F07. Доставка с ясными исходами и ограничением возраста — P1

Рыночное событие и попытка доставки — разные записи. Ввести delivery/outbox со статусами pending, sending, delivered, suppressed, expired, failed; хранить причину, число попыток, следующую попытку, идентификатор сообщения. Перед повтором проверять актуальность сообщения: после отмены сценария не отправлять старое «зоны готовы» без пояснения исторического контекста.

При нескольких частях сообщения хранить результат по части либо использовать одно сообщение, чтобы сбой на второй части не повторял уже отправленную первую. После отправки и сбоя до записи результата остаётся окно возможного дубля: не обещать exactly-once транспорт, отдельно документировать механизм защиты от повторов.

Уведомление отвечает: актив/рынок, что изменилось, время события и задержка, что ждём, ссылка на точное событие. Действия: открыть событие, временно отключить уведомления этого сценария, открыть текущее состояние.

**Приёмка:** недоступность Telegram не меняет состояние сценария; повтор не создаёт новый рыночный факт. Устаревшее сообщение получает expired/suppressed с причиной. Отключённая группа не остаётся непонятной вечной очередью pending.

### F08. Устойчивые задачи проверки — P1

Создать ReviewTask со ссылкой на объект и версию границ/правила. Статусы: требуется, в работе, решено, отложено. Отдельные исходы: геометрия верна, исправлена, неверна, недостаточно контекста. Прежние review/assessment остаются историей доказательств.

Повторная задача возникает при изменении материала проверки, а не после перезагрузки браузера. «Нет контекста» переносит в отложенные с причиной; «сейчас неактуально» не подменяет оценку геометрии. Отмена решения создаёт компенсирующую запись и не удаляет рыночную историю.

**Приёмка:** десять проверенных кандидатов сохраняют решения после refresh и на другом устройстве; исправление границ создаёт новую версию и её задачу по заданной политике. Повторный запрос решения идемпотентен; конфликт версии возвращает 409 с понятным предложением обновить данные.

### F09. Явные режимы наблюдения и конфликт контекстов — P1

Развести включение инструмента для загрузки, анализ до касания HTF, наблюдение после касания и доставку. Для пользователя дать явные команды «Анализировать до касания», «Наблюдать после касания», «Уведомлять о …». Отключение доставки не завершает сценарий; завершение сценария не выключает загрузку актива.

Ручной выбор контекста сохраняется и объясняется. Альтернативы видны компактным списком; противоположные направления — конфликт с возможностью сравнить две карточки. Навигационный приоритет не превращается в оценку вероятности успеха.

**Приёмка:** переключение котировки не заменяет вручную выбранный контекст; после его завершения видно основание нового выбора. Все сочетания анализа/наблюдения/доставки описаны таблицей поведения и проверены.

### F10. История «как было известно тогда» — P2

Добавить режим разбора по закрытиям H1 с явным `as_of`. Отдельно различать время формирования, доступности/подтверждения и обнаружения. Сохранённые версии границ, расчёта и исходные доказательства позволяют воспроизвести объяснение.

**Приёмка:** добавление будущих свечей/зон не меняет исторический результат. Новая конфигурация не переписывает старую карточку. Неопределённый порядок внутри OHLC обозначается как неопределённый. Исторический просмотр не создаёт live-уведомления.

## 7. Требования к интерфейсу и пользованию

### U01. Экран внимания и общее рабочее место — P1

Список активов показывает одну строку на instrument: тикер, площадка/рынок, короткое состояние, количество подходящих зон и quality. Группы: «Нужно проверить», «Цена в зоне», «Сценарий готов», «Ожидание». Проблемы данных видны отдельно и не скрываются из-за рыночного приоритета.

Добавить избранное, поиск, сохранённые фильтры и профили рабочего места. Сортировка стабильна во время взаимодействия; новая информация появляется без перемещения выбранной строки. Размеры панелей, режим, слои и масштаб сохраняются. Одна структура маршрута открывает asset/context/scenario/zone/event/mode без секретов.

**Приёмка:** HTF↔H1, «Назад», refresh и ссылка сохраняют выбранный объект. При отсутствии данных отображаются причина и доступное действие, а не обобщённое «нет зон».

### U02. Вывод до технических подробностей — P1

Вверху карточки четыре коротких ответа: «Что происходит», «Почему», «Чего ждём», «Что отменит». Основное действие одно и зависит от состояния: проверить разметку, наблюдать, показать событие или проверить данные.

Пример: «Сценарий снижения. H1 закрылся ниже опорного уровня. Ждём возврат к двум подходящим зонам. Отмена — закрытие H1 выше …». Цены и условия берутся из той же серверной проекции, что расчёт; фронтенд не выводит свои условия отмены.

Термины BOS/SMS/FVG доступны с короткими пояснениями. Сырые JSON-ключи, внутренние ID, версии и миллисекунды — в «Доказательствах»/«Технических подробностях». Проверенные четыре вопроса из текущего интерфейса сохранить, сократив основной текст и повысив его видимость.

**Приёмка:** без раскрытия деталей видно состояние и следующий шаг. Каждое доказательство ведёт к своей свече/зоне. Текст не обрезается на контрольных размерах.

### U03. График с приоритетом выбранного сценария — P1

По умолчанию показывать выбранную HTF-зону, действующий range, причинный BOS/SMS и пригодные зоны. Остальная структура, исключённые зоны и история раскрываются слоями. Выбранный объект заметнее остальных; подписи не перекрывают цены и друг друга.

Клик по зоне/строке синхронно выделяет объект и открывает инспектор. Для наложившихся объектов — список выбора. «Формирование» показывает исходные свечи, «Сейчас» возвращает к свежей цене, «Весь контекст» расширяет масштаб. Обновления не сбрасывают ручной масштаб.

История — приглушённая, предварительные объекты — пунктир и явный текст, недостоверная свежесть — подпись. Все цены форматируются по точности инструмента; расстояние/позиция рассчитываются только по свежей котировке. Закрытие последней свечи подписывается именно как закрытие свечи.

**Приёмка:** на плотном наборе зон выбранный объект распознаётся; переключение слоёв не меняет расчёт пригодности; неподтверждённый диапазон не похож на подтверждённый.

### U04. Проверка как последовательная работа — P1

В списке задач — актив, тип/ТФ, возраст, причина проверки и рабочий статус. Поиск/фильтры по активу, ТФ, типу, причине и отложенным. Основное объяснение — человеческий текст: какая база выбрана, где подтверждающая FVG, чего не хватает.

График фокусируется на свечах формирования с достаточным контекстом. Исправление границ — перетаскивание с точным вводом, выбор якоря и предпросмотр. После успешного ответа показываются результат и следующая задача. Ошибка оставляет текущую задачу и введённые значения. Горячие клавиши сохраняются для desktop, не срабатывают в поле ввода.

**Приёмка:** десять кандидатов проверяются без перехода в «Обзор», включая хотя бы одну правку и одно откладывание. При неуспешной записи прогресс не увеличивается. Решение можно отменить с сохранением аудита.

### U05. Мобильный сценарий и доступность — P1

На телефоне основное состояние доступно до большого графика; краткая карточка остаётся компактной. График может раскрываться на весь экран. Таблицы заменяются карточками с теми же действиями. Слои — одно меню. Общая навигация доступна также на H1-экране.

Цели: области касания не меньше 44×44 px, читаемый основной текст, видимый focus, смысл статуса через текст/форму помимо цвета. Диалоги управляют фокусом, Escape и восстановлением фокуса; Tab не уходит под модальное окно. Элементы таблиц/списков доступны клавиатуре.

**Приёмка:** сценарии просмотра, выбора контекста, чтения события и проверки доступны при 390×844 без горизонтального скролла всей страницы. Проверить также 360 px, 1024×768, 1280×720, 1440×900 и масштаб 200%. Панель слоёв/вкладки не обрезаются графиком.

### U06. Журнал, поиск причин и восстановление — P1

Один журнал с фильтрами: актив, сценарий, зона, период, вид события, действие пользователя, доставка. По каждой строке доступны событие, доказательства, снимок того момента и состояние сейчас. Показывать время события и обнаружения раздельно, когда есть задержка.

Пустые состояния различают: нет подходящих зон, ещё нет диапазона, анализ выключен, данные отсутствуют, расчёт отстаёт, всё отфильтровано. Состояния загрузки/ошибки принадлежат конкретной панели; доступно «Повторить». Возврат после ошибки сохраняет выбор и формы.

**Приёмка:** по сообщению из Telegram найдено точное событие и причина доставки/недоставки. Отменённый сценарий открывается как исторический с кнопкой «К текущему состоянию».

### U07. Единый редактор настроек и первый запуск — P2

Разделы: инструменты/наблюдение, уведомления, отображение, правила анализа, состояние сервиса. Экспертные и экспериментальные правила раскрываются отдельно с указанием влияния. Устаревшие поля доступны только в диагностике миграции.

Для каждого изменения указать единицы измерения, диапазон, влияние и необходимость пересчёта. Показывать несохранённые изменения, ошибки по полям и ход задания. Преднастройки сохраняют конкретные значения и версию, а не неявно меняют торговые правила.

Первый запуск: выбрать источники и инструменты → загрузить историю с прогрессом → включить нужный режим наблюдения → проверить доставку по запросу пользователя. До завершения загрузки не утверждать, что сценариев нет.

## 8. Архитектурные границы реализации

Предлагаемая последовательность слоёв:

```text
Адаптеры → исходные свечи/котировки → движок + версия конфигурации
         → предметные события/решения → общая проекция рабочего места
         → Web API / Telegram / журнал / доставка
```

Движок не зависит от фронтенда и транспорта. API и бот используют общую проекцию. `app/services/overview.py` — подходящая исходная точка, но требует общего контракта снимка и качества данных.

Для фронтенда выделить модули: route/store, загрузка снимков, websocket, chart/layers, workspace, review, journal, settings. Первая версия может остаться без нового фреймворка. Переход на другой стек оценивается после определения контракта и компонента графика; сам по себе он не решит расхождения данных.

SQLite можно сохранить для личного сервиса. Разделить границы чтения/записи, задать завершённые предметные транзакции и не держать общий lock во время сетевого ожидания. Тяжёлые пересчёты — через очередь заданий. Разделение web/worker/delivery на процессы выполнять при подтверждённой потребности в изоляции или масштабе.

### 8.1. Предлагаемые изменения модели

| Сущность/контракт | Назначение |
|---|---|
| WorkspaceSnapshot | Согласованные карточка, зоны, слои и качество данных |
| DataQuality / DataRevision | Свежесть, полнота и происхождение требуемых данных |
| ConfigVersion + CalculationJob | Воспроизводимость, безопасный пересчёт и публикация |
| FinalDecision projection | Общий отбор пригодности с объяснением и версиями |
| ReviewTask | Устойчивый рабочий статус проверки конкретной версии объекта |
| DeliveryAttempt / Outbox | Ясные исходы, ретраи, возраст и подавление сообщений |
| WorkspacePreferences | Избранное, фильтры, панели, слои, последний выбор |

Новые таблицы добавлять только там, где существующая схема не может выразить контракт. `Review`, `ReviewAssessment`, версии range и pivots переиспользовать, сохраняя ссылки и историю.

### 8.2. Доступ и ссылки

Убрать постоянный токен владельца из внутренних ссылок и событий Telegram. Предпочтительно обменять первоначальное подтверждение доступа на серверную сессию с HttpOnly-cookie; при публичном HTTPS — Secure и подходящий SameSite с сохранением проверки Origin. Для входа с другого устройства использовать короткоживущий одноразовый механизм либо обычный вход. URL выбранного объекта не содержит credentials.

При миграции старые ссылки продолжают разрешать объект через совместимый путь входа; секрет удаляется из адреса и не входит в журналы/новые ссылки. Сохранить защиту запуска с `dev-token` на внешнем host.

## 9. План выполнения и границы выпусков

| Этап | Объём | Условие завершения |
|---|---|---|
| 1. Надёжность | F01–F05, минимальные индикаторы quality | Корректная доставка live, отдельная цена, согласованный снимок, безопасные изменения настроек |
| 2. Общая модель | F06–F09, устойчивые ссылки и задачи | Одинаковые наборы зон, ясные режимы наблюдения, проверка и доставка с историей исходов |
| 3. Новое рабочее место | U01–U06 | Основные потоки работают на desktop/mobile, старые URL разрешаются |
| 4. Разбор и доводка | F10, U07, сохранённые профили | Воспроизводимая история, удобная настройка и измеренные пользовательские сценарии |

Первые два этапа можно выпускать в существующей оболочке. Новое рабочее место внедрять по флагу с сохранением доступа к старому до выполнения приёмки. Сроки оценивать после декомпозиции и определения численности команды; без этого календарные обещания не обоснованы.

### 9.1. Миграция

1. Сделать проверяемую резервную копию SQLite и конфигурации; проверить восстановление в отдельной среде.
2. Добавить новые поля/таблицы идемпотентно. Существующие ID зон, сценариев, диапазонов и событий сохраняются.
3. Для legacy delayed-событий, происхождение которых нельзя доказать, поставить явно неизвестный режим; не отправлять массово старые сигналы.
4. Перенести существующие решения проверки в задачи по явной политике; геометрию и актуальность не объединять.
5. Строить новую проекцию рядом со старой и сравнивать наборы объектов на эталонах. Расхождения объяснить до переключения.
6. Включить новую оболочку, проверить старые deep links, refresh, Telegram и мобильные потоки.
7. Сохранить откат приложения и совместимость чтения прежних данных; миграция и replay не инициируют историческую рассылку.

## 10. Измеримая приёмка всего проекта

Целевые показатели — требования к новой версии, а не измеренная текущая производительность.

- На одном снимке карточка, счётчик, таблица, график и новое уведомление совпадают по eligible IDs и range version.
- Утверждения о текущей цене и пригодности не делаются при недостаточном качестве нужного канала.
- Live-события не подавляются из-за обычной задержки опроса; историческое восстановление не создаёт поток live-сигналов.
- Все действующие 499 тестов сохраняют смысл. Дополнительно нужны проверки задержки закрытия, gaps, отставания processing, сбоев записи конфига, смешанных версий, нескольких вкладок и stale-ретраев.
- Web E2E: ежедневный просмотр, переход HTF→H1, смена контекста, исправление зоны, перезагрузка очереди, старое событие из Telegram, отказ API, reconnect.
- На фиксированном локальном стенде с 20 активами, 30 днями H1 и 1000 зонами на актив: p95 получения снимка ≤500 мс, обычный переход к активу ≤1,5 с. Измерять отдельно cold/warm и фиксировать CPU/RAM; оптимизация не снижает корректность снимка.
- Обновление интерфейса после поступления события на сервер — p95 ≤2 с при доступной сети. Отдельно измерять задержку от источника, детекции и доставки; не смешивать эти показатели.
- Пользователь определяет текущее состояние, качество данных и следующий шаг ≤10 с; выбор актива и причинного события — максимум три осмысленных действия. Проверить на заранее заданных задачах с владельцем.
- Проверка десяти кандидатов не требует перехода в другой раздел; результаты не исчезают после refresh. Операции с ошибкой не выглядят успешными.
- Контрольные разрешения и клавиатурная навигация из U05 проходят без недоступных основных действий и обрезанных контролов.
- В ссылках/новых сообщениях отсутствует постоянный токен владельца.

Метрики сервиса: возраст котировки, пропуски свечей, processing lag, время расчёта, длительность/исход задания, задержка доставки, pending/expired/failed, ошибки адаптера. Пользователю показывать объяснение и действие; подробные метрики доступны в диагностике.

## 11. Дополнительное улучшение качества детектора — отдельный этап

Использовать накопленные labels и оценки как набор для проверки геометрии и объяснений. Сначала проверить полноту и согласованность разметки. Разделить примеры по периодам/активам и сохранять закрытый набор регрессии; не подгонять пороги по всем уже увиденным примерам.

Сравнивать версии по совпадению границ, причинам отклонения, лишним/пропущенным объектам, стабильности при replay и доле неопределённых случаев. Это измерение качества разметки. Оценка торговой результативности требует отдельной методики с правилами исполнения и затратами и не подменяется этими показателями.

Если предлагается менять 90%, подтверждение pivots или правила контекстного исключения, оформить отдельный вариант правила, эталоны до/после и новое решение владельца. В рамках переработки приложения сначала устранить инфраструктурные и пользовательские расхождения при действующей методике.
