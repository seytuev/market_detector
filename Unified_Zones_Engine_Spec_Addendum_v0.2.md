# Дополнение к спецификации: единый движок зон HTF/LTF (rule_version 0.2)

Источник: ТЗ «Единый движок зон HTF/LTF» от 22.09.2026. Имеет приоритет над
противоречащими правилами HTF_Zones_Spec_v0.1.md и LTF_Confirmations_Window_Spec_v0.2.md.
Не меняет: BOS/SMS, Premium/Discount, направление сценария и условия его отмены.

## 1. Единый движок (ТЗ §2)

Поиск, геометрия, подтверждение, тестирование и отрисовка одного типа зоны —
одна реализация на любом таймфрейме. HTF/LTF — роль зоны в сценарии, а не
разные определения. Удалённые скрытые ветки прежних версий:

- «H1: первое касание завершает зону» (бывшее §9.8, `_track_h1`) — удалено;
  H1-зоны живут по общему lifecycle;
- «DEPTH_90 завершает OB» (worked_90) — удалено для OB; сохранено для PRB;
- запрет первой же протестированной H1-зоны — удалён.

Закрытие для подтверждения/пробоя берётся на таймфрейме самой зоны.

## 2. Актуальность OB отдельно от пригодности для входа (ТЗ §3)

Раздельные свойства зоны (колонки `zone`):

- `market_validity` (active/invalid): актуален ли OB по рыночной истории.
  Бычий OB теряет актуальность при закрытии свечи его ТФ СТРОГО ниже нижней
  границы; медвежий — строго выше верхней. Выход тенью без такого закрытия —
  не пробой. Равенство Close границе — не пробой.
- `max_test_depth` / `has_tests` / `test_extreme`: максимальная глубина
  самостоятельных тестов за ВСЮ историю действующего OB (консервативная
  формализация: мелкий поздний тест не стирает более глубокий прежний).
  Для нетестированной зоны max_test_depth=0 и has_tests=false.
- `entry_eligible = (market_validity == active) AND (max_test_depth < 0.90)`,
  порог — настройка `entry_reuse_max_depth` (0.9). Ровно 90% — недопустимо.
  Сравнения — точная десятичная арифметика по экстремуму теста
  (P90 = U−0.9W / L+0.9W), без epsilon.
- При d ≥ 0.90 OB отображается актуальным, но недоступным для нового входа.

## 3. Формулы и последовательность тестирования (ТЗ §4)

Пересечение диапазона свечи с зоной: `High >= L AND Low <= U`; без пересечения
тест не присваивается по формуле глубины.

Глубина самостоятельного визита: бычий OB `d=(U−min(Low))/W`,
медвежий `d=(max(High)−L)/W`; `d_raw` и экстремум сохраняются в визите.

Последовательность: база → направленный выход из базы → самостоятельный
возврат (тест, возможен до и после подтверждения FVG) → подтверждение.
Свечи базы и первоначальный проход импульса тестами не являются (фаза
`forming`/`departed` в evidence зоны). Ранние тесты кандидата пишутся в
историю (визиты, max_test_depth) без событий и уведомлений; при подтверждении
не обнуляются и учитываются в entry_eligible и запрете Breaker (>50%).
Свеча «выход+возврат в одном OHLC» помечается неопределённой
(`pre_departure_overlap_unknown`), последовательность не выдумывается.

## 4. Внутренние уровни ликвидности (ТЗ §5)

Экстремум самостоятельного теста OB образует внутренний уровень: минимум
теста бычьего OB → SSL, максимум теста медвежьего → BSL. Подтверждение —
строгое правило 3+3 (`inner_level_pivot_left/right`) на ТФ уровня;
`confirmed_at` — закрытие i+3; до подтверждения — кандидат (пунктир на
графике), при обновлении экстремума кандидат пересчитывается. D1- и
H1-экстремумы внутри D1 OB — раздельные записи. Поля: parent_ob_id,
timeframe, pivot_time, confirmed_at, price, source_test_id, история снятия.
Экстремум вне диапазона OB не создаёт уровень. Снятие уровня не отменяет
родительский OB; снятые остаются в истории.

## 5. Остальные типы (ТЗ §6)

- FVG: трёхсвечная геометрия по теням (bull: High1<Low3; bear: Low1>High3),
  подтверждение закрытием третьей свечи, M=(L+U)/2. Ограничение <90% на FVG
  не переносится (50% → WEAKENED, 100% → FILLED — прежние правила).
- Breaker: образование из OB без предшествующих самостоятельных тестов >50%
  (включая ранние тесты до подтверждения FVG), импульсный пробой с новым FVG
  и закрытием за границей; собственный тест СТРОГО >50% после образования
  делает Breaker невалидным (ровно 50% допустимо). Правило реализовано в
  track_zone (ранее — только в документации).
- PRB: прежнее правило 90% → WORKED сохраняется.

## 6. Ручные зоны (ТЗ §7)

Начало ручной зоны — выбранная пользователем координата времени
(`anchor_time`/`display_from`), в т.ч. историческая; зона продолжается вправо,
автопродолжения влево нет. Раздельно: `created_at` (запись), `anchor_time`
(начало на графике), source candle times, `confirmed_at` (только алгоритмом —
при создании ручной зоны не проставляется). При рисовании сохраняются
`zone_type` (ob/fvg/…) и `source=manual`; ручная зона с zone_type=ob живёт по
правилам OB, включая пробой закрытием по истории.

## 7. Экспорт и миграция (ТЗ §10)

- Экспорт различает geometry_verdict / lifecycle_verdict / reason_code /
  comment / requires_clarification; lifecycle-замечание не превращается в
  отказ по геометрии. Исходные оценки неизменны; нормализация — полем
  `normalized` с объяснением. В записях — фактический rule_version.
- Миграция (tools/restore_unified_zones.py): восстанавливает OB, завершённые
  по worked_90 / h1_first_touch / ошибочному rejected, если нет последующего
  валидного пробоя закрытием; пересчитывает тесты, max_test_depth,
  entry_eligible и внутренние уровни replay-ем общего движка; история
  доставленных уведомлений не сбрасывается; повторный запуск идемпотентен;
  при нехватке свечей — needs_replay.
