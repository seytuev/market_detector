# Переход LevelFrame на PostgreSQL

`DATABASE_URL` выбирает PostgreSQL. `HTF_DB_PATH` остаётся путём исходной
SQLite-базы и определяет каталог графиков, меток и резервных копий. При ошибке
PostgreSQL приложение не переключается на SQLite. Пароль подключения не
попадает в журнал старта или представление Settings.

## Первый запуск на Railway

Сервис `market_detector` в проекте `melodious-magic` уже содержит переменную
`DATABASE_URL` и том `/data`. Нужно сохранить этот том и исходный путь БД.
Запускается один экземпляр приложения; старый процесс должен завершиться до
переноса. При остановке владельца расчёта его lease может истекать до двух минут.
На первый запуск предусмотрен healthcheck timeout 600 секунд.

До запуска API и воркера приложение:

1. Создаёт версионированную PostgreSQL-схему под advisory lock.
2. Проверяет, что целевые таблицы пусты, и ждёт завершения старых владельцев.
3. Блокирует поздних SQLite-писателей и делает согласованную копию SQLite.
4. Обновляет старую схему только на частной копии. Исходник сохраняется.
5. Переносит таблицы через `COPY`, сохраняя ID и исторические архивы
   `*_bak_ltfmig`, `*_bak_ltfv2`, `ltf_migration_log`.
6. Сверяет количество и SHA-256 всех строк, проверяет внешние ключи,
   восстанавливает identity sequences и фиксирует импорт одной транзакцией.
7. Освобождает старые leases, сохраняет receipt в PostgreSQL и отметку
   `htf_zones.db.postgres-migrated` на томе. Выполняет `ANALYZE`.

Ошибка до commit оставляет целевые таблицы пустыми. Неизвестные дополнительные
таблицы, отсутствующий исходник на Railway или непустая целевая БД останавливают
импорт. После receipt повторного переноса нет. Отметка на томе защищает от
случайного запуска новой версии приложения с устаревшей SQLite-базой.

Доставленные уведомления, pending/retry очереди, настройки, свечи, состояния
движков и журналы сохраняются. Старые структурные правила обновляются штатным
механизмом приложения. Транзакции используют отдельные соединения потоков,
вложенные savepoints и публикацию после commit. Владельцы процессов и принятие
котировок блокируют отдельные ключи; общей блокировки всех писателей нет.

## Проверки

На PostgreSQL 17 выполнены проверки импорта, полного rollback при нарушенной
связи, повторного импорта, identity, конкурентных claims, независимой записи
heartbeat, savepoints и восстановления резервной копии. Существующие тесты
уведомлений, событий, журнала, синхронизации и lifecycle также запускаются
через `tools.pytest_postgres` на отдельных схемах. Добавлена отдельная CI-задача
с PostgreSQL 17.

Репетиция на частной копии локальной БД размером около 490 МБ: **91 таблица,
7 078 549 строк, 153,42 секунды**. Все таблицы сверены; исходная рабочая БД
осталась неизменной. Это проверка локальной копии, а не подтверждение состояния
Railway. Отчёт репетиции находится в `tmp/postgres-real-data-verification.json`.

Повторить репетицию на отдельном тестовом сервере:

```powershell
$env:HTF_TEST_POSTGRES_URL='postgresql://postgres@localhost:55432/postgres'
python tools/verify_postgres_migration.py data/htf_zones.db --report tmp/postgres-import.json
python -m pytest tests/test_postgres.py -q
```

## Резервные копии и восстановление

Maintenance продолжает делать резервные копии на томе с прежним интервалом.
Для PostgreSQL используется единый repeatable-read снимок, потоковый `COPY`
и gzip по таблицам. Архивы миграций также сохраняются. `manifest.json` содержит
схему, столбцы и SHA-256; наличие manifest означает завершённую копию.
Файлы графиков и меток сохраняются отдельно. Это не копирование файла БД.

Восстановление выполняется только в пустую PostgreSQL-базу:

```bash
DATABASE_URL='postgresql://...' python tools/restore_postgres_backup.py /data/backups/<backup>
```

Контрольные суммы, внешние ключи и весь restore проверяются в одной транзакции.
Команда доступна в Docker-образе; дополнительные pg_dump-бинарники не нужны.
Отдельные Railway backups и PITR можно использовать дополнительно.

После переключения PostgreSQL является источником истины. Простой откат
старого образа к сохранённому SQLite-файлу не переносит новые записи обратно.
Для восстановления после начала работы PostgreSQL следует использовать
актуальную PostgreSQL-копию, а не удалять marker или receipt.

## Ограничение подключений после переноса

14 октября в production запросы API стали возвращать 500 с PostgreSQL
`FATAL: sorry, too many clients already`. Соединения сохранялись за каждым
рабочим потоком до остановки приложения, включая завершившиеся потоки.

Теперь один экземпляр приложения использует пул `psycopg_pool` с максимумом
16 соединений. Отдельный запрос возвращает соединение после выполнения;
транзакция, вложенные savepoints, read snapshot, импорт и резервное копирование
удерживают одно соединение до завершения всей операции. Неактивные соединения
сверх минимального одного сокращаются через 60 секунд. Проверка соединений
и замена оборванных подключений выполняются пулом.

Регрессионная проверка создаёт 48 параллельных запросов и затем 120 новых
рабочих потоков на пуле из четырёх соединений. Проверяются ограничение пула,
буферизация результатов, вложенный rollback, read snapshot, возврат соединений
после ошибки и восстановление после разрыва подключения.
