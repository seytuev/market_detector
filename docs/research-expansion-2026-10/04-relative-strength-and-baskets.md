# ТЗ 04. Относительная сила и исследовательские корзины

Дата: 15.10.2026. Версия: research-strength-1.0 / research-baskets-1.0. Статус: запланировано. Общие требования — [README](README.md). Информационные поля из [01](01-asset-information-context.md) и [02](02-catalyst-calendar.md) опциональны и не блокируют численные расчёты.

## 1. Цель

Дополнить структурный скринер сопоставимыми показателями: как актив ведёт себя относительно BTC и выбранной тематической корзины, насколько он коррелирован с другими активами и как меняется результат сохранённой корзины.

Два самостоятельных подэтапа: A — относительная сила в текущем скринере; B — версионные корзины и их индексы. Готовность B не требуется для выпуска A. Автоматическая ротация, рекомендации по размеру реальных позиций и биржевое исполнение не входят.

## 2. Текущая база

Market Researcher: app/alt/*, app/services/alt_overview.py, app/web/alt_api.py, alt.html/alt.js/alt_chart.js; существующий engine_version и структурные диапазоны сохраняются. Новые показатели не меняют eligible, lifecycle, ручные границы и канал ALT-уведомлений.

Цены и история берутся из существующих адаптеров/data_sync; повторный параллельный сбор тех же свечей запрещён. При недостатке истории ставится ограниченное фоновое задание догрузки с низким приоритетом.

stvterminal: services/baskets/index-model.ts и index-repository.ts; backtest/rules/relative-strength.ts; portfolio/analytics.ts. Переиспользовать формулу процентного индекса и явную неполноту при отсутствии цены. Параметры beta из ручных портфельных моделей не считать рассчитанными статистическими показателями. [Модель индекса](https://github.com/seytuev/stvterminal/blob/af1b0b3a74f28b61b8c44b423a895610af92c418/site/services/baskets/index-model.ts).

## 3. Сценарии

1. Пользователь видит прежнюю структурную таблицу и включает колонки «К BTC 7д», «К BTC 30д», «Корреляция 60д», «Волатильность 20д».
2. Фильтрует активы, опережающие BTC; открывает объяснение метрики с периодом, источником, формулой и покрытием.
3. Сохраняет тематическую корзину с весами, описанием гипотезы и источниками. Свободная доля остаётся Cash.
4. Нажимает «Начать наблюдение»: система фиксирует реальные базовые цены и старт 100 после готовности всех участников.
5. Меняет состав: создаёт новую версию и новый сегмент наблюдения; прошлый результат доступен отдельно.
6. Одна цена пропала: общий индекс текущего момента неполон; система не заменяет отсутствие нулевой доходностью и не перераспределяет веса.

## 4. Область данных и выбор инструментов

MVP — crypto spot USDT с BTCUSDT как benchmark. Perpetual, акции, DEX и валютные преобразования добавляются отдельными методиками. Торговые инструменты разных рынков не склеивать в одну ценовую серию из-за общего asset_uid.

Для каждого asset_uid хранить выбранный расчётный instrument_id и период действия выбора. Автовыбор допустим только по фиксированной политике поддерживаемых площадок и рынка; решение показывается. При отсутствии спота показатель spot-RS отсутствует. Смена источника не склеивает историю незаметно.

Используются закрытые D1 в UTC, единый источник и одинаковые границы баров. Это отличается от календарной статистики МСК из app/events/calendar.py; показатели явно подписываются «Дни UTC». Свеча D1 доступна с её exclusive close boundary. Свечи с разрывом/некорректной OHLC дают incomplete, а не интерполируются.

## 5. Численные контракты

Методика rs-utc-1.0. Все проценты в API — процентные пункты представления: 5 означает 5%, корреляция/beta — безразмерные числа. Исходные цены и веса сохраняются без округления UI; вычисления конечны, деление на ноль возвращает unavailable с причиной.

| Показатель | Определение |
|---|---|
| Return N | (P[t] / P[t−N] − 1) × 100%; N=7/30/90 закрытых календарных дней |
| Excess BTC N | Return актива N − Return BTC N; единица — п.п. |
| RS ratio N | ((P[t]/P[t−N]) / (B[t]/B[t−N]) − 1) × 100% |
| Daily return | r[t]=P[t]/P[t−1]−1; доходности соседних дней |
| Correlation 60 | Pearson(r_asset,r_BTC) на 60 одинаковых дневных интервалах |
| Beta 60 | SampleCov(r_asset,r_BTC) / SampleVar(r_BTC) на том же наборе |
| Volatility 20 | SampleStd дневных simple returns за 20 дней × sqrt(365) × 100% |
| Drawdown 30 | (P[t] / max(P[t−29..t]) − 1) × 100%; по закрытиям |

Excess и RS ratio — разные значения с разными подписями. В первой таблице основная колонка «К BTC» означает Excess BTC, а RS ratio доступен в подробностях. Это устраняет неоднозначность названия relative strength.

Для Return N нужны N+1 последовательных закрытий. Для Correlation/Beta 60 — 61 последовательное общее закрытие; MVP не снижает размер выборки до произвольного минимума. Для Volatility 20 — 21 последовательное закрытие. Недавно листингованный актив показывает доступные короткие показатели и отсутствие длинных. Нулевой variance даёт null/constant_series, а не 0 или 1.

Расчёт всех активов одного snapshot использует общий t: последний день с доступным закрытием benchmark. Опаздывающий актив не сравнивается на своей более старой дате без пометки и исключается из текущего ранжирования. Межбиржевые отличия источника выводятся как metadata.

Попарная матрица корреляций первой версии — максимум 30 выбранных активов, 60 одинаковых интервалов на пару, с n/from/to/quality. Нельзя выдавать всю матрицу за рассчитанную на одной выборке, если покрытия различаются. При крупной группе задание асинхронное.

## 6. Модель метрик

research_strength_snapshot: id, as_of, available_at, benchmark_instrument_id, method_version, source_revision_hash, calculation_job_id, quality. research_strength_metric: snapshot_id, asset_uid, instrument_id, metric, window, value, sample_n, from_at, to_at, quality, reason_codes. UNIQUE(snapshot_id, instrument_id, metric, window).

Для неизменного набора исходных свечей повторный расчёт возвращает тот же payload_hash. Исправление свечи создаёт новый snapshot с причиной revised_input, не переписывает сохранённый результат эксперимента. Не хранить только последний float без входного fingerprint и периода.

## 7. Корзины

research_basket: id, title, thesis, status (draft/observing/paused/closed/archived), current_revision_id, created_at, linked_idea_id. research_basket_revision: id, basket_id, available_at, source_refs, members, benchmark, rebalance_policy, reason, method_version. Каждый member: asset_uid, instrument_id, weight_pct, role/sector; один инструмент на актив в версии.

Веса конечны и положительны, сумма ≤100%; шаг ввода до 0,01 п.п., сервер проверяет decimal, без float-epsilon скрывающего превышение. Cash=100−сумма весов. Пустая корзина остаётся draft; наблюдение требует хотя бы один актив. В MVP Cash — условный USDT по постоянной единице; нет процентов, кредитного риска и моделирования отвязки. Это явно подписано.

research_basket_segment: id, basket_revision_id, status (pending_baseline/active/paused/closed), requested_at, started_at, baseline_snapshot_id, previous_segment_id. research_basket_baseline хранит для каждого участника цену, время, источник, quote currency и качество.

Запуск фиксируется на общем закрытии UTC H1 не раньше запроса. Максимальное ожидание полного набора — 2 часа; после него baseline_failed с перечнем отсутствующего, без частичного старта. Все цены взяты на одной границе, закрыты и доступны. Нельзя фиксировать одну базу сегодня, другую завтра и называть это одним стартом.

Формула buy-and-hold: I[t] = Cash% + Σ(weight_pct[i] × P[i,t] / P[i,0]). I[0]=100; return_pct=I−100. Вклад позиции в доходность = weight_pct[i] × (P[i,t]/P[i,0]−1). Текущий вес = (weight_pct[i] × P[i,t]/P[i,0]) / I[t] ×100%. Это дрейфующие доли; ежедневной ребалансировки нет.

Пример приёмки: 50% актива +20%, 30% актива −10%, Cash 20% → индекс 107, доходность +7%, вклады +10/−3 п.п. и текущие доли 60/107 и 27/107 от индекса. Стартовые веса остаются 50/30/20.

research_basket_observation: segment_id, observed_at, available_at, input_prices, price_revision_hash, index_value nullable, coverage_weight_pct, quality, reason_codes. При отсутствии цены хотя бы одного участника полная оценка null; допустимы известные вклады и последнее полное наблюдение с его датой. Не нормировать оставшиеся веса до 100%.

Обновление — после закрытых H1; не повторять запись одной и той же версии цен. График «Наблюдение» содержит реально сохранённые полные наблюдения и разрывы. Исторический расчёт до started_at — отдельный режим «Реконструкция», со своими входами и без утверждения, что такой состав наблюдался тогда.

## 8. Изменение состава

Редактирование draft не начинает наблюдение. У наблюдаемой корзины изменение активов, весов, benchmark или расчётного инструмента создаёт новую revision и pending-сегмент. Старый сегмент остаётся активным до успешного старта нового; затем закрывается на общей доступной границе. При неудаче базовой фиксации новая версия остаётся ожидающей, прежний сегмент не теряет историю.

Новый сегмент стартует с 100. В MVP графики сегментов показываются отдельно; склеивание в непрерывный индекс и учёт turnover/издержек — отдельный этап. Архив не удаляет исторические составы, source_refs и наблюдения. Исключённый сегодня токен не исчезает из вчерашней корзины.

Pause приостанавливает автоматическое получение новых наблюдений, а не ликвидирует модельные позиции. Resume того же состава продолжает сегмент с прежними базовыми ценами и видимым пробелом в наблюдениях. При запросе восстановления пропуска исторические точки подписываются реконструкцией. Close завершает сегмент; повторный запуск закрытой корзины создаёт новый сегмент и новую базу. Нельзя скрыть просадку кнопкой pause и затем представить только выбранные наблюдения как непрерывную историю.

Сравнение с BTC: тот же started_at, валюта и фактические границы наблюдений. Доходность корзины и сравнение — описательные, без обозначения как реального P&L. Плановые target prices могут появиться позже как отдельный пользовательский сценарий, не прогноз системы.

## 9. Скринер и API

Новые локальные маршруты /api/research/v1:

| Метод и путь | Назначение |
|---|---|
| GET /strength | Snapshot; asset_uids либо instrument_ids, benchmark, metric, window, filters, sort, cursor |
| GET /assets/{uid}/strength | Метрики, качество, входные серии и методика |
| POST /strength/recalculate | 202 job_id; ограниченная область |
| POST /correlations | 202 job_id; до 30 активов, окно 60 |
| GET /correlations/{id} | Матрица и покрытие |
| GET/POST /baskets | Список / создание draft |
| GET/PATCH /baskets/{id} | Детали / новая версия, expected_revision |
| POST /baskets/{id}/start | Pending baseline, Idempotency-Key |
| POST /baskets/{id}/transition | pause/resume/close/archive с причиной |
| GET /baskets/{id}/history | Версии, сегменты и составы |
| GET /baskets/{id}/observations | segment_id, from/to, cursor, quality |

В текущую ALT-таблицу метрики добавляются через batch-запрос по набору instrument_id с явным snapshot_id. Не выполнять N запросов на N строк. Фильтры/сортировка по новым числам серверные; pagination выполняется после полного join/filter/sort. Несколько страниц не должны сортироваться каждая отдельно.

Параметры фильтров: excess_min/max с обязательным window, correlation_min/max, volatility_min/max, quality; допустимые sort перечислены сервером. Один запрос содержит максимум 200 instrument_ids, строки сверх limit выдаются по cursor. Одновременное указание asset_uids и instrument_ids возвращает 400. Неоднозначный выбор расчётного инструмента у asset_uid возвращает unresolved в строке, а не случайный рынок.

Новые колонки выключены по умолчанию и включаются пользователем. Сортировка: value, затем стабильный instrument_id; null всегда в конце, причина доступна. Не вводить общий непрозрачный рейтинг «качества монеты». Существующая structural rank сохраняется отдельно.

В детали метрики: «К BTC 30д: +8 п.п.», фактический период, coverage, площадка, UTC и ссылка «Как считается». В корзине: индекс, доходность, Cash, вклад/дрейф весов, benchmark, состав версии, качество и последние полные данные. В мобильном виде колонки выбираются, детали доступны без горизонтальной стены таблицы.

## 10. Производительность и флаги

RESEARCH_STRENGTH_ENABLED и RESEARCH_BASKETS_ENABLED независимы. Рассчитывать дневные метрики после закрытия D1 и подтверждения истории; ручной refresh не делает повторный backfill всего рынка. Исправление данных инвалидирует только затронутые активы/периоды. Вычисления корреляций выполняются вне web request.

Стенд: 200 активов × 3 года D1, 100 корзин до 30 активов, 100 000 наблюдений. Цель чтения таблицы 100 строк p95 ≤ 750 мс, карточки корзины ≤ 500 мс; запись вычислений пакетная. Сначала измерить фактический прогон; не создавать миллион парных расчётов ради нескольких пользовательских корзин.

## 11. Поставки

1. S1: Return/Excess BTC 7/30/90, метаданные качества и batch API; колонки/фильтры скринера.
2. S2: корреляция/beta/волатильность/просадка и объяснения; матрица выбранных активов.
3. B1: draft корзины, запуск на общей H1, индекс/вклады и честные разрывы истории.
4. B2: версии состава, сегменты, benchmark, связь с идеей и информационные индикаторы.
5. B3: реконструкция истории и формальная ребалансировка только в лаборатории 06 после отдельной методики издержек.

## 12. Критерии приёмки

- S01: ручные контрольные ряды дают правильные Return, Excess и RS ratio; названия/единицы различаются.
- S02: BTC сравнивается сам с собой: Excess=0, RS ratio=0; корреляция=1 только при ненулевой дисперсии.
- S03: constant series, разрыв, новый листинг и несвежий актив дают null с причиной, а не фиктивное число.
- S04: 60 интервалов корреляции требуют 61 общего закрытия; день UTC не смешан с днём МСК.
- S05: сортировка/фильтры стабильны между страницами; текущие ALT eligibility, диапазоны и уведомления не меняются.
- B01: формула примера 50/30/20 даёт 107; Cash и вклад позиций сходятся с общей доходностью.
- B02: 100,01% не сохраняется; неизвестная цена не подменяется нулём и не меняет веса.
- B03: все базовые цены имеют одну границу H1 не раньше старта; недостающая цена не создаёт частичный старт.
- B04: новая версия состава не наследует придуманную старую доходность; старый сегмент сохраняется при ошибке нового.
- B05: наблюдение и реконструкция раздельны; revised candle создаёт новую расчётную версию.
- B06: benchmark использует те же времена/валюту; архивирование не удаляет составы и исходные цены.
- S06/B07: выполнены нагрузки, миграции обоих backend, auth/Origin и UI-проверки из общей программы.

Обязательные fixtures: независимые и одинаковые ряды, постоянный BTC, отрицательная корреляция, один пропуск, новый листинг, correction свечи, два инструмента актива, неполная корзина, Cash-only draft, неудачный rollover сегмента. Проверки сравниваются с ручными вычислениями и независимыми эталонными численными значениями.
