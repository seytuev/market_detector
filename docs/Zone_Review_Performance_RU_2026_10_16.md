# Ускорение ручной проверки зон

Сохранение проверки задерживает синхронное воспроизведение истории инструмента. В Railway 16 октября 2026 года три последовательных решения сохранялись 16–20 секунд. Чтобы получить стабильный переход к следующей зоне за секунду, нужно заранее готовить рыночное состояние и сохранять решение короткой транзакцией. Первые локальные исправления уменьшают SQL-нагрузку и убирают обнаруженный конфликт записи свечей; целевая скорость на production ещё требует проверки после внедрения.

## Измерения на Railway

Наблюдение в Chrome: очередь проверки инструмента S / USDT; при сохранении кнопки блокируются, появляется сообщение «первая проверка зоны может занять до минуты». Горячие клавиши и автоматический переход уже реализованы.

HTTP-журнал приложения за 16 октября, время МСК:

| Завершение запроса | Зона | Результат | Длительность |
| --- | --- | --- | --- |
| 17:39:57 | 2777 | HTTP 200 | 20,328 с |
| 17:40:30 | 2778 | HTTP 200 | 19,537 с |
| 17:41:30 | 2779 | HTTP 200 | 16,312 с |
| 17:41:51 | 2780 | HTTP 500 | В runtime-журнале зафиксирован lock timeout |

В том же интервале загрузка карточки зоны занимала 21–57 мс, запросы свечей рядом с открытием кандидатов — 13–47 мс. Это длительности серверных запросов из прокси-журнала, без времени визуального анализа человеком.

Стек ошибки зоны 2780: `review_zone → replay_instrument → on_closed_candle → insert_candles → psycopg.executemany`. PostgreSQL сообщил `LockNotAvailable: canceling statement due to lock timeout`, контекст — вставка индексной записи в `candle`. На соединениях настроен `lock_timeout='15s'`. Какой именно конкурентный запрос удерживал блокировку, этот стек не устанавливает.

Источники: Railway production проекта `melodious-magic`, HTTP и runtime logs; вкладка [Проверка зон](https://stv-mr.up.railway.app/?instrument=9#review). При исследовании новые решения в production не отправлялись.

## Причины задержки в коде

1. `app/web/api.py`, `review_zone`: каждый POST запускает новый `Scanner.replay_instrument` от даты появления зоны с запасом 10 свечей. Расчёт ограничен таймфреймом, но обрабатывает зоны всего инструмента на этом ТФ.
2. `app/engine/scanner.py`: на каждой исторической свече заново обнаруживаются FVG, базы и pivots, проверяются переходы, уровни и визиты. Идемпотентность предотвращает дубликаты, но сохраняет вычисления и SQL-запросы.
3. До исправления replay повторно вызывал `insert_candles` для уже прочитанной свечи. PostgreSQL выполнял `ON CONFLICT DO UPDATE` даже для одинаковых OHLC, захватывая блокировки строк.
4. `refresh_liquidity_anchors` читал H1 отдельно для каждого уровня D1/W1, а replay вызывал его на каждой свече. Например, короткое окно W1 на 15 свечах породило 1061 вызов `get_candles`, из них 1060 относились к H1-привязкам уровней.
5. `app/web/static/app.js`, `submitReviewDecision`: после успешного ответа добавляется пауза 400 мс, затем ожидается обновление очереди и отдельно загружается следующая карточка со свечами.

Общий `Worker` уже умеет пропускать неизменившиеся закрытые свечи через курсоры и отпечатки. HTTP-обработчик ревью этим механизмом не пользуется и создаёт отдельный Scanner.

## Подготовленные локальные исправления

Replay больше не перезаписывает прочитанные свечи. Обычная обработка новой закрытой свечи сохраняет прежнюю запись в БД.

H1 для привязки экстремумов загружается одним снимком на replay. Для каждого уровня из отсортированного снимка выбирается его точное окно через бинарный поиск. В обычном вызове вне replay все уровни используют один общий запрос. Проверки полноты H1, первого равного экстремума и группового якоря сохранены.

Сравнение исходного кода из HEAD и исправленного кода на независимых копиях локальной SQLite-базы:

| Случай | Свечей replay | SELECT до → после | Время с профилировщиком до → после |
| --- | --- | --- | --- |
| ZEC W1, зона 5727981 | 15 | 2390 → 1316 | 0,575 → 0,428 с |
| ZEC D1, зона 5727976 | 22 | 7482 → 5767 | 2,476 → 2,065 с |

Содержимое `zone`, `zone_relation`, `visit`, `event`, `inner_level`, `candle` совпало для обеих пар прогонов; служебные времена `created_at` и `detected_at` исключены из сравнения. Локальная база содержит другие инструменты и историю, поэтому эти времена не являются прогнозом задержки Railway. Сырые результаты находятся в `docs/audit/zone-review-speed-2026-10-16.json`.

Отдельный тест PostgreSQL удерживает строку исторической свечи через `SELECT FOR UPDATE` в другом соединении. Replay завершается с локальным `lock_timeout=250ms`: он больше не пытается записать эту строку.

Проверки SQLite прошли двумя наборами: 73 теста replay, якорей, ревью, первого пробоя, канонического состояния и инкрементальной обработки; 50 тестов replay, якорей, приёмки, правил ревью, нормализации и ручных границ. Наборы частично пересекаются. Тест миграции старого SQLite-файла запускается на SQLite: PostgreSQL-подмена репозитория не переносит созданный им файл и для этого теста неприменима.

На локальном PostgreSQL 17.11 прошли 39 применимых тестов replay, якорей и решений ревью, а также отдельный тест удержания строки свечи другим соединением. Изменения в Railway не развёрнуты.

## Следующий этап для проверки за несколько секунд

### Заранее подготовленное рыночное состояние

Использовать единый расчёт Worker для подготовки очереди. Хранить подтверждение успешного расчёта по инструменту и таймфрейму: обработанное закрытие, версию закрытой истории с учётом ревизий и заполнения дыр, отпечаток правил и версию геометрии зоны. Одного времени последней свечи недостаточно: старая свеча может быть исправлена без нового закрытия.

Перед показом текущей и следующих двух задач получать подготовленную карточку. Если состояние отстаёт, ставить одно объединяемое задание расчёта на инструмент и ТФ. Расчёт не должен запускаться заново для каждой соседней зоны той же истории.

Не использовать глобальный `state_seq` как ключ такой подготовки: котировки и другие записи меняют его слишком часто. Существующий `_calc_deps_hash` включает глобальные счётчики review и тоже требует разделения зависимостей: обычная оценка геометрии одной зоны не должна отменять подготовку всей очереди.

### Короткая транзакция решения

Карточка передаёт версию подготовленного состояния. POST в короткой транзакции проверяет её актуальность, записывает review, assessment, правку и необходимые изменения выбранной зоны. Для согласования с Worker нужен общий порядок блокировки или атомарная проверка версии; отдельная проверка перед транзакцией оставляет гонку.

При несовпадении версий вернуть явный конфликт и сохранить черновик в интерфейсе; обновить подготовку, не подтверждая устаревшее состояние. `assessed_as_of` должен оставаться фактически обработанным срезом. Подтверждение завершённой зоны по-прежнему не возвращает её в active.

Исправление границ инвалидирует состояние изменённой зоны и зависимые расчёты. Если пересчёт ещё не окончен, интерфейс должен явно показывать ожидание оценки актуальности. Нельзя выдавать старый lifecycle за результат на новых границах.

Файловый экспорт меток и запуск зависимых LTF-расчётов следует вынести из ожидания клика через надёжную очередь после commit. Снимок решения необходимо сохранить в БД в той же транзакции, чтобы перезапуск не терял метки.

### Быстрый переход в интерфейсе

Предзагружать следующие две карточки, повторно использовать свечи одного инструмента и ТФ с проверкой версии истории. После подтверждённого commit сразу открывать следующую подготовленную задачу; обновление серверной очереди выполнять отдельно, убрав фиксированную паузу 400 мс. До commit задача остаётся непроверенной. Нужна защита от двойного отправления и повторов после потери ответа.

Подсвечивать свечи основания и сразу показывать участок формирования с переключением на текущую актуальность. Это уменьшит время на поиск контекста. Горячие клавиши 1, 2, 3 и переход уже есть; основной резерв сейчас находится на сервере.

## Критерии приёмки

Цель для подготовленной задачи: POST p95 не более 500 мс, переход от нажатия до готовности следующего графика p95 не более 1 с. Практический ориентир для простой визуальной проверки — 3–5 секунд на зону; неоднозначная разметка требует отдельного анализа.

Проверить минимум 30 решений на production-подобном PostgreSQL, включая старые D1/W1-зоны, активную фоновую загрузку, двойной клик, потерю ответа, новую закрытую свечу, ревизию истории и исправление границ. Отдельно измерять подготовку, ожидание блокировки, расчёт, запись решения и загрузку следующей карточки. Холодную подготовку учитывать отдельно от готовой очереди.

Сравнить рыночные состояния, визиты, события, подтверждающие FVG и оценки с эталонным replay. Стабильные секунды можно считать достигнутыми после этих измерений; первые локальные исправления сами по себе этого не доказывают.
