# ТЗ 01. Информационный контекст актива

Дата: 15.10.2026. Версия: research-context-1.0. Статус: запланировано; не реализовано этим документом. Общие контракты, доступ, время, миграции и качество — в [программе работ](README.md).

## 1. Назначение

Показывать рядом с технической картиной проверяемые изменения информационного контекста выбранного актива. За один просмотр пользователь должен понять, что нового, откуда это известно, что спорно и какие сведения требуют проверки.

Первая поставка: до 10 выбранных активов; серверный импорт готовых материалов и разборов из stvterminal; компактная карточка рабочего места; список первоисточников; ручная проверка неоднозначных привязок. Собственный сбор Telegram/X и новый LLM-конвейер в Market Researcher не требуются.

## 2. Текущая база и переиспользование

Market Researcher: app/services/asset_state.py — каноническая техническая проекция; app/web/ltf_api.py и app/web/static/now.js, app.js, h1_layers.js — существующие представления. Их контракты сохраняются; информационный блок загружается самостоятельным запросом по instrument_id и связанному asset_uid.

stvterminal: services/ticker_recap/hub.ts, registry.ts, mention-identity.ts, eligibility.ts; services/project-signals/model.ts и server.ts; src/live; services/telegram-feed. Hub хранит ссылки на входные ID, ограничивает свежую подборку и кэширует сводку. Эти решения переиспользовать через адаптер; прямые SQL-зависимости D1 не переносить в наш слой хранения.

Ссылка на [hub исходного снимка](https://github.com/seytuev/stvterminal/blob/af1b0b3a74f28b61b8c44b423a895610af92c418/site/services/ticker_recap/hub.ts). Пороговые значения исходника не объявляются проверенными для наших источников.

## 3. Пользовательские сценарии

1. Выбор BTCUSDT или другого инструмента → техническая карточка появляется обычным путём → независимо загружается информационный блок того же актива.
2. Пользователь раскрывает факт → видит исходную цитату, автора, публикацию, время получения и ссылку на оригинал.
3. Пользователь переключается между spot/perpetual одного подтверждённого актива → исследовательская информация общая, котировки и структура остаются инструментальными.
4. Неоднозначный тикер → вместо чужих новостей сообщение «Нужно сопоставить актив» и переход к проверке.
5. Источник недоступен → последняя сводка доступна с датой и признаком устаревания; технический график продолжает работать.
6. Из материала пользователь открывает катализатор или создаёт исследовательскую идею после внедрения 02/03. До появления функции кнопка скрыта, а не ведёт на заглушку.

## 4. Требования к материалам и разбору

### 4.1. Исходный материал

research_material: id, provider, external_id, source_kind (telegram/x/article/video/manual), source_id, author, canonical_url, original_text, original_language, published_at, first_available_at, current_revision_id, lifecycle (active/deleted/retracted), ingest_quality.

research_material_revision: material_id, revision_id, original_text, content_hash, source_observed_at, available_at, source_updated_at, media_refs, revision_reason. UNIQUE(provider, external_id, revision_id). Нативный ID сообщения приоритетнее URL. Media_refs содержат метаданные и безопасный адрес, не ключи доступа. В MVP допустимо не копировать медиа; доступность вложения показывается отдельно.

research_material_asset: material_revision_id, asset_uid, role (subject/mentioned/beneficiary_hypothesis), resolution, confidence_kind, evidence_quote, resolver_version. Автор-бот, название компании и токен — разные роли. beneficiary_hypothesis не включается в подтверждённые упоминания и подсчёт независимых источников без отдельного решения.

### 4.2. Анализ

research_analysis: id, material_revision_id, provider_analysis_id, model, prompt_version, schema_version, analyzed_at, available_at, status, payload_hash, payload. Payload включает summary, claims, opinions, risks, unknowns, catalyst_candidate_refs и source_refs. У каждого claim — текст, material_revision_id и точная цитата либо координаты фрагмента. Ссылка на существующий ID без поддержки текста не делает утверждение проверенным.

Различать:

- извлечённый факт: «проект опубликовал предложение»;
- мнение автора: «изменение полезно»;
- гипотезу аналитика о влиянии на токен;
- подтверждение исполнения изменения, если есть отдельное свидетельство.

Проверка на импорте: формат, существование ссылок, допустимый размер, конечность чисел, отсутствие будущего времени получения, цитата в нормализованном исходнике. Нормализация ограничена пробелами/переносами; не подменять отрицание и числа. Ошибочный claim исключается из проверенных фактов и получает причину; исходный материал сохраняется.

Внешние тексты не содержат доверенных инструкций модели. Если новый анализ появится в нашем сервисе, он обязан использовать schema validation, фиксированные задачи и ограниченные разрешения без выполнения инструкций публикации.

### 4.3. Сюжеты и источники

research_story: id, asset_uid, topic_key, current_stage, first_available_at, last_available_at. research_story_member связывает версии материалов с сюжетом и хранит основание склейки. Одинаковая ссылка/нативный ID — точный дубль; похожий текст — кандидат одной истории, не безусловное удаление.

Хранить origin_material_id при известном оригинале. Пересказы одного пресс-релиза не считаются независимыми подтверждениями. При неизвестном происхождении UI говорит «N источников обсуждают», а не «N независимых подтверждений». Изменение стадии proposal → announced → live сохраняется как новое развитие сюжета.

## 5. Проекция карточки

research_context_snapshot: id, asset_uid, as_of, generated_at, window_from, window_to, method_version, input_revision_ids, summary_revision_id, quality, payload_hash, payload.

По умолчанию информационное окно — последние 24 часа по published_at среди доступных на as_of версий. Лента допускает 7/30 дней и серверную пагинацию. Поздно полученная старая публикация маркируется отдельно. Катализаторы и риски с более долгим сроком выводятся отдельной выборкой, а не выдаются за новости суток.

Поля карточки:

| Блок | Контракт |
|---|---|
| Главное | До 3 кратких изменений с source_refs |
| Факты | До 5 подтверждённых извлечений; ссылка и стадия обязательны |
| Мнения | Направленность обсуждения с числом авторов и границами выборки |
| Риски | До 3 рисков с основанием; неизвестное не превращается в риск-факт |
| Что проверить | До 3 конкретных вопросов |
| Ближайшее | До 3 связанных событий из 02 при доступности |
| Свежесть | Время последней успешной синхронизации и возраст сводки |

MVP допускает отсутствие готовой сводки: тогда показываются сохранённые факты и материалы без синтетического headline. Новая версия материала делает ссылающуюся сводку superseded; до обновления она показывается как устаревшая и не считается актуальным разбором. Отозванный материал выводится из текущих оснований, история сохраняется.

Тональность — описание выбранных источников, не оценка будущей доходности. Она не меняет direction технической карточки. Единый «процент вероятности роста» из структуры и новостей не рассчитывается.

## 6. API Market Researcher

Все пути новые, под текущей авторизацией; общий envelope описан в README.

| Метод и путь | Назначение |
|---|---|
| GET /api/research/v1/instruments/{id}/context | asset_uid, compact snapshot, identity status, quality |
| GET /api/research/v1/assets/{uid}/materials | cursor, limit, kind, from, to; подтверждённые материалы |
| GET /api/research/v1/materials/{id} | Оригинал, версии, анализы, источник и связи |
| GET /api/research/v1/identity/candidates | Очередь неоднозначных сопоставлений |
| POST /api/research/v1/identity/candidates/{id}/resolve | Выбор кандидата/отклонение с expected_revision и причиной |
| GET /api/research/v1/integration/status | Возможности, лаг, очереди, ошибки, карантин |
| POST /api/research/v1/integration/sync | 202 job_id; один активный sync на область |

Контекст не найден при известном инструменте: HTTP 200 с identity=unresolved либо quality=unavailable; неизвестный instrument_id: 404. Успешная пустая лента: items=[], quality=ok. Ручной sync не запускает новый разбор всех публикаций и не пересчитывает HTF/H1.

Решение identity создаёт версию связи и задание перестроения затронутых проекций. Старая привязка остаётся в исторических снимках. При спорной идентичности нельзя «исправить» существующий asset_uid под другой проект.

## 7. Интерфейс

В рабочем месте после канонической технической карточки — блок «Информация по активу». До 3 строк в свёрнутом состоянии, действие «Источники и подробности». На мобильном подробности открываются панелью с возвратом к прежнему месту графика. В «Обзоре» первой версии допустим только индикатор свежих материалов, без массового LLM-расчёта.

Две временные подписи: «Срез информации» и «Источник обновлён». Для старого кэша — «Последние сохранённые данные, обновление недоступно». Для отсутствия публикаций — «В выбранных источниках новых материалов нет». Неподключённый источник не создаёт сообщение о спокойном рынке.

Оригинал открывается отдельным действием. Отображать опубликованную цитату без HTML из источника. Длинные материалы подгружаются в детали; список не передаёт полный текст всех записей. Объём ответа компактной карточки — целевой максимум 64 КиБ без медиа.

## 8. Обновление и эксплуатация

Импорт → проверка identity → сохранение версий → проверка claims → пометка затронутого asset_uid → локальная сборка карточки. Повторные события коалесцируются по активу и revision watermark. Проекция публикуется одной транзакцией и не смешивает половины разных обновлений.

Начальная политика: синхронизация раз в 5 минут, stale после 15 минут без успешной синхронизации; возраст сводки показывается отдельно. Эти интервалы конфигурируемые. Материал опубликован давно при здоровом канале — это старая публикация, а не отказ канала. Быстрое получение только одной страницы не обнуляет лаг оставшихся изменений.

При выключении RESEARCH_ENABLED скрываются действия запуска; существующая проекция может оставаться доступной с quality=disabled. Отдельный флаг RESEARCH_CONTEXT_UI_ENABLED управляет показом блока. Состояние информационного домена не блокирует /api/ready технического сервиса.

## 9. Этапы

1. C0: общая identity, 10 вручную проверенных активов, интеграционный экспорт, импорт и диагностика. UI проверки привязок входит в этот этап.
2. C1: только факты/материалы/качество в рабочем месте. Проверить цикл от новой реальной публикации до карточки.
3. C2: готовая сводка hub с проверяемыми ссылками, сюжеты и новые стадии. Разделение мнений/фактов обязательно.
4. C3: индикаторы в обзоре, связи с 02/03, опциональная дневная сводка по наблюдаемым активам. Дневная сводка отдельный snapshot со списком входов; push остаётся отдельным opt-in.

На C1 допускается выпуск без C2/C3. Нельзя заменять недоступный integration API парсингом DOM страниц терминала.

## 10. Критерии приёмки

- C01: один базовый актив на Binance/Bybit/другом рынке получает один информационный контекст при разных инструментальных котировках.
- C02: HOOD-акция и одноимённый DEX-токен не склеены; AIXBT-автор не создаёт автоматически упоминание AIXBT-токена.
- C03: факт раскрывает существующую версию материала и подтверждающую цитату; удалённый source ID не остаётся действующим основанием.
- C04: 3 пересказа одного релиза остаются доступными материалами одного сюжета; UI не называет их независимыми подтверждениями.
- C05: смена proposal на live создаёт развитие, прежнее состояние доступно в истории.
- C06: исправление материала инвалидирует актуальность старой сводки; её время не обновляется фиктивно.
- C07: импорт с одинаковыми timestamp, повтором, рестартом, 410 и tombstone соответствует G03/G04 общей программы.
- C08: старый кэш, нет новых материалов, нет подключения, auth_error и карантин различаются.
- C09: быстрые переключения активов и фоновый refresh не подменяют карточку и не сбрасывают график.
- C10: при выключенном модуле/недоступном терминале прежние технические вычисления и уведомления сохраняют семантику.
- C11: на стенде README достигнуты целевые задержки, проверены темы и 1440/900/390 px.

## 11. Проверки и данные для приёмки

Контрактные fixtures: два одноимённых актива; несколько рынков одного актива; автор-бот; оригинал с тремя пересказами; противоречащие публикации; исправление/отзыв; поздний импорт; пустая успешная лента; недоступное вложение.

Проверки: identity, импорт и cursor на обоих backend; claims/quote validation; исторический срез; API auth/Origin; изоляция сбоев; браузерная гонка ответов и состояние графика. Синтетические fixtures доказывают семантику. Отдельно нужен протокол реального обновления минимум по одному подключённому источнику с фактическими временами и без отправки новых сообщений пользователям.
