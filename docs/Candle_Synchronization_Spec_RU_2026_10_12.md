# ТЗ: актуальность свечей и принудительное обновление данных

Дата: 12.10.2026. Статус: готово к реализации.

## 1. Цель и границы

Устранить отставание графиков после смены периода, потери соединения и возврата во вкладку. Добавить ручное восстановление данных с биржи без перезапуска приложения.

Область первой реализации: основной рабочий экран, отдельная страница LTF, сводка «Сейчас»; свечи H1 и включённые в анализ D1/W1 всех включённых основных инструментов. H1 синхронизируется независимо от наличия LTF-наблюдений. Кнопка называется **«Обновить данные»**, пояснение: «Свечи и котировки всех включённых активов».

Отдельный дневной модуль альткоинов использует собственный job и не входит в эту операцию. В интерфейсе нельзя обещать обновление этого модуля общей кнопкой. Не менять расписание альткоинов, настройки анализа, историю ручных действий и торговые критерии.

## 2. Основания по текущему коду

| Наблюдение | Значение для задачи |
|---|---|
| `app/config.py`: значения по умолчанию HTF — 1800 с, LTF — 300 с, котировки — 10 с | Свечи и цены обновляются с разной частотой; фактические настройки могут отличаться |
| `app/worker.py`: циклы ожидают интервал после выполнения прохода | Время запросов и обработки увеличивает фактическую паузу |
| `_apply_price_to_forming()` обновляет существующий бар только внутри его периода | Котировка не создаёт новую свечу на границе периода; нужен запрос OHLC с источника |
| `app/web/static/app.js`: `connectWs()` не передаёт обработчик восстановления снимка | Основной экран может сохранить данные, пропущенные во время разрыва |
| `app/web/static/ltf.js`: обработчик reconnect уже существует | Сохранить его поведение и объединить с общим механизмом восстановления |
| `app/web/static/common.js`: возвращается первоначальный экземпляр WebSocket, последующие создаются внутри reconnect | Нельзя проверять актуальное соединение по сохранённому первоначальному объекту |
| `/api/candles` читает БД; резервный опрос рабочего экрана вызывает `loadDeskExtras()` | Перечитывание экрана не запускает загрузку свечей с биржи |

Это подтверждённые особенности кода, а не доказанная причина каждого пользовательского эпизода. Добавить диагностику, позволяющую отличить отставание источника, обработки и экрана.

## 3. Ручное обновление

Кнопка доступна в общей панели основного рабочего экрана и LTF. Обе точки запускают одну серверную операцию.

Последовательность:

1. Сервер фиксирует список включённых инструментов и нужных таймфреймов на момент старта.
2. Запрашивает свежую котировку и хвост OHLC каждого канала напрямую у соответствующего адаптера.
3. Заполняет пропуски, сохраняет текущий бар, сверяет недавние закрытые бары.
4. Последовательно обрабатывает новые закрытия и ревизии штатными механизмами HTF/LTF.
5. Публикует новую версию состояния и событие обновления после завершения соответствующей обработки.
6. Клиент перечитывает график, зоны, структуру, текущий сценарий и сводку.

Повторное нажатие во время операции возвращает существующее задание. Перезагрузка страницы и открытие второй вкладки не создают второй проход. Завершённая операция не запускает полный replay всей истории.

Во время выполнения кнопка показывает «Обновление…». Рядом отображаются прогресс по каналам и результат, например: «Обновлено 11 из 12 каналов; ETH H1 — источник недоступен». Данные остальных каналов остаются доступными.

После успешного завершения: «Данные обновлены в 14:32:08 МСК». При частичном результате: «Обновлено частично» и список ошибок. При недоступном исполнителе: «Обновление недоступно: обработчик данных не работает». Успех нельзя показывать только по факту принятия HTTP-запроса.

## 4. Синхронизация и целостность

- Начинать загрузку с предпоследней сохранённой закрытой свечи, чтобы повторно сверить минимум два закрытых бара. Если история отсутствует, использовать штатную первичную загрузку и показывать этап восстановления.
- Догружать диапазон до текущего времени с пагинацией адаптера. Отдельно проверять непрерывность последних 200 закрытых баров; найденные внутренние пропуски также заполнять. При необходимости более старой истории использовать существующий механизм восстановления, а не скрытый полный пересчёт по кнопке.
- Идентичный повторный ответ не создаёт новые свечи, события и уведомления. Ключ свечи: инструмент, таймфрейм, время открытия.
- Использовать биржевые OHLC. Не создавать новую часовую/дневную/недельную свечу из последней котировки. Существующее обновление текущего бара котировками сохранить как оперативное отображение между запросами OHLC.
- Определять границы периода штатными функциями проекта. Особенно учитывать недельную границу конкретного адаптера; часы сервера и МСК не должны менять состав биржевых свечей.
- Закрытые свечи обрабатывать по времени. Ревизии ранее обработанных свечей передавать существующему механизму ревизий; для H1 проверить достаточность восстановления структуры при изменении уже обработанного бара.
- Не считать канал полностью готовым, пока курсор обработки не достиг последнего полученного закрытия. Для H1 различать общую структуру и сценарии активных наблюдений.
- При восстановлении применять действующие правила delayed/historical и дедупликации уведомлений. Повторная синхронизация не должна повторно отправлять старые сигналы; новые актуальные события проходят обычные правила доставки.
- Ручной и фоновые проходы используют общий координатор. Для одного инструмента запись свечей, изменения структуры и сценариев сериализуются; обновление котировкой не должно перезаписать уже закрытый бар. Сетевые запросы не удерживают транзакцию БД.
- Ошибка одного инструмента не останавливает остальные. Не сбрасывать признак устаревания до подтверждённого восстановления.

## 5. Автоматическое получение свечей на границе периода

Сохранить обычный периодический опрос как резервный путь. Добавить отдельное планирование запросов возле закрытий H1/D1/W1, не зависящее от длительности полного прохода.

- Первый запрос — через 5 секунд после границы периода источника.
- Если ожидаемая закрытая свеча или текущий бар ещё отсутствуют, повторить запрос через 15, 30 и 60 секунд после первого запроса.
- Отсутствие ожидаемого закрытия после этих попыток отмечать как задержку данных; следующий периодический проход продолжает восстановление.
- Для сбоев сети и ограничения частоты соблюдать `Retry-After` и ограниченные повторные попытки адаптера. Не накладывать две независимые серии повторов друг на друга.
- При запуске или выходе сервера из длительной паузы сразу сверять ожидаемый последний закрытый период. Не ждать следующей часовой границы.
- Получение новой закрытой свечи запускает штатную обработку и обновление UI, даже если новых торговых событий нет.

При нормальном ответе источника новая свеча должна появляться вскоре после границы, а не через весь интервал LTF/HTF. Если биржа ещё не опубликовала данные, показывать ожидание; не подменять свечу вычисленным баром.

## 6. Восстановление клиентского экрана

Общий механизм для рабочего экрана, LTF и «Сейчас»:

- После reconnect получать свежий снимок из БД: свечи, слои графика, сценарий и сводку. Первое соединение не дублирует начальную загрузку.
- При `visibilitychange` в видимое состояние или восстановлении сети перечитывать снимок, если последнее успешное чтение старше 15 секунд. Одновременные триггеры объединять.
- Пока страница видима, резервно сверять выбранный инструмент раз в 30 секунд. Это работает и при формально подключённом, но переставшем доставлять сообщения WebSocket. Запросы не должны перекрываться.
- Сверка экрана читает БД и статусы, сама по себе не запускает общий биржевой проход. Автоматическую догрузку обеспечивает серверный планировщик.
- Сохранять выбранный инструмент, режим, таймфрейм, масштаб и видимый диапазон. Если график следовал за последней свечой, продолжать следование; просмотр прошлого не возвращать принудительно к текущему времени.
- Отбрасывать запоздалый ответ для ранее выбранного инструмента или более старой версии состояния. При несовпадении версий связанных частей повторить чтение снимка.
- Сообщения WS служат поводом обновить данные; пропущенное сообщение не должно навсегда оставлять экран устаревшим.
- `common.js` должен предоставлять актуальное состояние соединения независимо от замены экземпляров WebSocket. Проверки старого `state.ws.readyState` заменить этим источником состояния.

## 7. Статусы свежести

В общей панели показывать время последней полностью успешной синхронизации выбранного инструмента. Подробности по H1/D1/W1 и котировке доступны рядом, без необходимости открывать настройки.

Для каждого канала хранить отдельно:

- Последнюю попытку запроса и последний успешный ответ источника.
- Время последней закрытой свечи и ожидаемого последнего закрытия.
- Наличие текущего бара и пропусков проверенного хвоста.
- Последнее обработанное закрытие; для H1 — структуру и сценарии отдельно.
- Время последней ошибки и её понятную причину.

Успешный ответ источника без ожидаемого бара не означает актуальные данные. Недоступная биржа, отсутствующая свеча, незавершённая обработка и ошибка чтения UI должны иметь разные причины статуса. Индикатор WS продолжает показывать только соединение.

Возраст текущего бара нельзя определять по его времени открытия: часовой бар закономерно открыт давно. Свежесть текущего бара оценивать по последней синхронизации; наличие закрытий — по границам периода.

Пока выполняется догрузка/обработка, использовать штатное состояние восстановления и существующие ограничения пригодности сигналов. Для каждого статуса указывать инструмент и канал; не объявлять все данные актуальными при частичном успехе.

## 8. Серверный контракт

Предлагаемые маршруты, с существующей авторизацией приложения:

- `POST /api/data-sync` — создать задание для всех включённых основных инструментов или вернуть уже активное; HTTP 202, `job_id` и состояние задания.
- `GET /api/data-sync/{job_id}` — прогресс и результат задания.
- `GET /api/data-sync/status` — активное/последнее задание, доступность исполнителя и свежесть каналов. Статический маршрут зарегистрировать перед динамическим.

Состояния задания: `queued`, `running`, `succeeded`, `partial`, `failed`. Поля: `job_id`, `reason`, `requested_at`, `started_at`, `finished_at`, `channels_total`, `channels_completed`, результаты каналов и ошибки. Результат канала содержит инструмент, таймфрейм либо `quote`, число новых/исправленных баров, пропуски, ожидаемое/полученное/обработанное закрытие и состояние готовности.

Задание исполняет координатор рабочего процесса, использующий существующие адаптеры и движки. Не создавать второй независимый сканер внутри API. HTTP-запрос быстро возвращает ID; длительная работа продолжается в фоне.

Статус сохраняется в БД и доступен после перезагрузки страницы. После перезапуска процесса незавершённое задание помечается `failed` с причиной прерывания, либо возобновляется с сохранённым прогрессом при гарантии идемпотентности. Для первой реализации достаточно первого варианта и штатной автоматической догрузки при запуске.

События WS `data_sync` передают ID задания, состояние и прогресс. Клиент дополнительно опрашивает статус раз в 2 секунды во время задания; после завершения опрос прекращается. Недоступность WS не мешает получить результат.

Конкурентность запросов ограничить: по умолчанию до 2 запросов одновременно на биржу, с соблюдением лимитов адаптера. Повторные старты после завершения ограничить интервалом 15 секунд; ответ должен содержать время следующего разрешённого старта. Активное задание всегда возвращается без создания дубликата.

## 9. Диагностика и пределы ожидания

В структурированных логах сохранять причину запуска (`manual`, `boundary`, `startup`, `periodic`), ID задания, инструмент/канал, диапазон запроса, длительность запроса и обработки, число баров, курсоры до/после, ошибку и попытку повтора. Токены авторизации не логировать.

Операция не должна бесконечно оставаться в `running`: использовать конечные таймауты запросов адаптеров и общий предел задания 10 минут по умолчанию. По достижении предела завершать необработанные каналы ошибкой, сохраняя результаты завершённых. Координатор не освобождает владение инструментом, пока фактическая фоновая обработка не завершилась: таймаут ожидания потока не означает остановку потока.

Если обработка продолжается после предела задания, явно показывать это состояние канала и запрещать конфликтующий повтор до её завершения. Не сообщать о готовности по одному лишь завершению сетевых запросов.

## 10. Критерии приёмки

1. В БД отсутствуют три последние H1. Нажатие кнопки догружает их, заполняет хвост, доводит структуру/сценарии до последнего закрытия и обновляет график без перезагрузки страницы.
2. На границе часа текущая H1 появляется после ответа биржи через планировщик границ, без ожидания полного пятиминутного интервала. Аналогично проверены D1 и W1 с границами соответствующего адаптера.
3. Биржа отдаёт ожидаемый бар только при третьей попытке: до этого виден статус ожидания, затем канал становится актуальным.
4. Во время разрыва WS появились свечи и изменился сценарий. Reconnect обновляет и график, и сценарий. Проверить основной экран и отдельную страницу LTF.
5. После длительного пребывания в скрытой вкладке возврат обновляет снимок, сохраняя масштаб и просмотр прошлого.
6. При открытом WS, но отсутствии сообщений резервная сверка получает новые данные из БД в пределах 30 секунд плюс время ответа.
7. Двойное нажатие и запуск из двух вкладок возвращают один ID задания. Ручное обновление одновременно с фоновым проходом не дублирует закрытия, события и уведомления.
8. Один источник недоступен: доступные каналы обновляются, итог — `partial`; видны точная ошибка и устаревший канал.
9. Изменён недавний закрытый бар: применяется механизм ревизий, производное состояние соответствует исправленным OHLC. Отдельно проверить H1 и HTF.
10. Повторный ответ с идентичными барами не меняет число свечей/событий и не отправляет старые уведомления повторно.
11. Медленный ответ для старого инструмента приходит после смены выбора: новый график не перезаписывается.
12. Перезагрузка страницы во время задания показывает его прогресс; перезапуск сервера не оставляет вечный `running`.
13. Включённый инструмент без LTF-наблюдений получает H1 и общую структуру. Выключенные инструменты не включаются в новый проход.
14. Успешный ответ источника с отсутствующей ожидаемой свечой или отставшим курсором не получает статус «актуально».
15. Переподключение создаёт новый сокет; индикатор и резервный опрос используют его актуальное состояние.
16. Во время синхронизации пользовательская разметка, настройки и выбранный диапазон сохраняются. Дневной job альткоинов не запускается этой кнопкой.

Проверки выполнять на управляемых ответах адаптеров и управляемом времени. Добавить интеграционные проверки координатора/дедупликации и браузерные проверки reconnect, возврата во вкладку, прогресса и сохранения диапазона. Проверки не должны зависеть от доступности живой биржи.

## 11. Порядок реализации

1. Общий координатор записи/обработки, статусы свежести и диагностика.
2. API задания и ручная кнопка с прогрессом и частичными ошибками.
3. Восстановление клиента и исправление отслеживания текущего WebSocket.
4. Планировщик границ и повторные попытки появления баров.
5. Проверки по критериям приёмки и краткий отчёт с фактическими задержками.

Готовность определяется прохождением критериев, а не наличием кнопки. Результат реализации: актуальный график после восстановления связи, автоматическое получение новых периодов и проверяемая ручная синхронизация с источником.
