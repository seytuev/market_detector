# Техническое задание: ускорение получения данных, расчётов и интерфейса

Дата: 12 октября 2026 года. Проект: market_detector / htfdec.
Статус: спецификация для поэтапной реализации. Численные показатели ниже — цели приёмки, а не результаты замеров.

## 1. Цель

Сократить время от получения рыночного сообщения до отображения котировки, задержку обработки закрытых свечей, время запуска и открытия рабочего экрана. Сохранить правила HTF/LTF, монотонность времени, полноту событий, отсутствие повторных уведомлений и явную диагностику устаревших данных.

Успех определяется измерениями до и после изменения при одинаковой нагрузке. Подключённый WebSocket, HTTP 202 или свежий ответ API сами по себе не означают актуальность рыночных данных и завершение расчёта.

## 2. Исходное состояние

В `app/worker.py` существуют отдельные циклы HTF, LTF, котировок, altcoins и событий. `app/services/data_sync.py` координирует ручное обновление, периодическую сверку и восстановление свечей. Уже реализованы блокировки инструмента, общая блокировка расчёта LTF, ограничение HTTP-запросов и обработка Retry-After.

Котировки и обработка свечей используют владение инструментом, поэтому длительный расчёт способен задержать получение цены. Ручное обновление последовательно обрабатывает инструменты и каналы. В `app/db.py` уже существуют пакетные записи, версии состояния и кэши; их нельзя дублировать новой системой без измерения конкретного недостатка.

В интерфейсе `app.js`, `ltf.js`, `data_sync.js` реализованы обновление снимков и восстановление после reconnect. Полное обновление снимка может включать несколько API-запросов и перерисовку независимых разделов.

В последнем исправлении кнопка подключается до сетевой загрузки экрана, котировка запрашивается перед свечами инструмента, а статус показывается до перезагрузки графика. Эти свойства должны сохраниться.

Все перечисленные причины — установленные особенности кода. Их вклад в задержку production необходимо измерить; сетевые ошибки и стоимость расчёта нельзя объявлять причиной без диагностики.

## 3. Область реализации

Первый обязательный источник realtime — Binance Spot. REST Binance остаётся каналом истории, сверки и восстановления. Existing REST adapters Bybit и Hyperliquid сохраняют совместимость. Realtime Hyperliquid оформляется отдельным последующим этапом с собственной приёмкой.

Обязательны: метрики; Binance WebSocket; независимая публикация котировок; очередь расчётов; пропуск неизменившихся данных; ограниченная параллельность получения свечей; фоновый прогрев; точечные обновления UI; измеренная оптимизация SQLite; ручное обновление; восстановление и откат.

Изменение торговых правил, подмена spot перпами, автоматическое смешивание цен разных бирж, переход на другую БД и распределённые вычисления не входят в эту поставку.

## 4. Модель актуальности и времени

Для сообщения хранить `event_at` (время сделки или события источника), `received_at` (получение сервисом), `persisted_at`, `processed_at` и версию. Для длительностей использовать монотонные часы. Если источник не сообщает время сделки, `event_at = null`; время получения не подставлять вместо времени сделки.

Отдельно измерять возраст рыночной цены, транспортную задержку, ожидание очереди и время расчёта. Отрицательная задержка из-за рассогласования часов помечается как clock_skew; не превращать её в доказательство мгновенной доставки. Контроль синхронизации часов сервера обязателен.

Свежесть котировки, непрерывность истории, наличие текущей свечи и завершение расчёта — независимые состояния. UI должен уметь показывать «Цена актуальна, расчёт H1 догоняет».

Для малоликвидного инструмента отсутствие новой сделки не доказывает неисправность транспорта. Хранить здоровье соединения отдельно от возраста последней сделки. Не генерировать искусственные сделки ради зелёного статуса.

## 5. Целевая архитектура

Поток данных: источник → проверка сообщения → короткая запись котировки/свечи → публикация версии → очередь рыночной обработки → расчёт → транзакция результата и событий → доставка уведомлений и патч UI.

Получение сети и тяжёлый расчёт не выполняются под одной продолжительной блокировкой. Для каждого инструмента и таймфрейма сохраняется порядок применения свечей. Общая блокировка существующего LTF engine остаётся, пока подтверждено наличие общего изменяемого batch-состояния.

Сетевая конкурентность и конкурентность вычислений настраиваются независимо. Несколько Python threads не считать гарантией ускорения CPU-расчёта. Process pool возможен позднее только после профилирования, с неизменяемыми входными снимками и одним контролируемым писателем результата.

## 6. Метрики и профилирование

До функциональных изменений добавить измерения:

- REST duration, HTTP status, timeout, Retry-After, запросы и вес по venue/endpoint;
- WS connections, reconnects, последнее сообщение, последнее валидное сообщение, разрывы и ошибки parsing;
- quote source age, receive-to-persist, receive-to-broadcast;
- queue depth, oldest pending age, coalesced tasks, overload/resync counters;
- lock wait, lock hold, calculation duration по типу задачи;
- свечи received/inserted/revised/unchanged, processing cursor и lag;
- SQL duration, rows fetched, commit duration, busy/locked, WAL size;
- API duration, response bytes, cache hit/miss и время построения read model;
- event loop lag, CPU, RSS, file descriptors;
- UI request count, bytes, initial render, update duration и ошибки JS.

Собирать count и гистограммы p50/p95/p99 за одинаковые интервалы. Не использовать job_id, timestamp и произвольный symbol как неограниченные labels. Детали инструмента доступны через диагностический JSON и структурированные logs.

Диагностика защищена существующей авторизацией, не содержит токенов, ключей и URL с секретными query parameters. Метрики не должны создавать отдельную запись SQLite на каждый тик.

Baseline: минимум 30 минут обычной нагрузки и отдельные воспроизводимые тесты старта, всплеска и закрытия нескольких свечей. Production-замеры приложить при наличии доступа; локальные измерения прямо обозначить как локальные.

## 7. Binance WebSocket

Подключить публичный Spot stream для сделок и kline H1 плюс активных HTF. Предпочтительно `trade`; переход на `aggTrade` требует явного маппинга идентификатора и доказательства эквивалентности правил, зависящих от отдельных сделок.

Подписывать только включённые инструменты нужного venue. Изменения enabled и scan timeframe применять без перезапуска сервиса. Список желаемых подписок отличать от подтверждённого сервером. Ошибка одной подписки не прекращает остальные.

В trade отделять время сделки от времени события. В kline использовать open/close time, OHLC и признак закрытия источника. Проверять symbol, interval, конечность чисел, положительную цену и непротиворечивые OHLC. Неизвестный источник и неправильная структура сообщения отклоняются с метрикой.

Реализовать ping/pong средствами выбранного клиента, таймаут отсутствия активности, плановую ротацию соединения и reconnect с exponential backoff и jitter. При смене соединения дедупликация исключает двойную обработку перекрывающегося потока. Все лимиты, период жизни соединения и частота управляющих сообщений сверяются с актуальной документацией при реализации и задаются в одном месте.

REST polling котировок уменьшается только для здоровых подписок. При деградации включается ограниченный fallback. Восстановление WS не означает мгновенную готовность истории: сначала выполняется сверка пропущенного диапазона.

Контракт адаптера расширить capability `realtime_supported`, подпиской и нормализованными сообщениями. Отсутствие capability означает штатный REST режим, а не ошибку.

## 8. Быстрый путь котировки и сохранность сигналов

Разделить `_poll_quote` на получение тика, валидацию/дедупликацию, короткое сохранение и постановку рыночной обработки. REST и WS используют один путь применения. Получение новой цены не ждёт `_calculate` и instrument lock, удерживаемый обработкой истории.

Запись занимает короткую транзакцию. Перед обновлением повторно проверяется монотонность с учётом времени и идентификатора источника: старый REST-ответ не может затереть более новый WS-тик. Равное время нескольких разных сделок допустимо; timestamp не является единственным ключом дедупликации.

Разрешается объединять сообщения для визуального показа последней цены. Запрещается без доказанной эквивалентности оставлять только последний тик для scanner.on_price, касаний зон и LTF-переходов. Движение «вошёл в зону и вышел» между двумя UI-кадрами должно остаться событием.

Первая версия рыночной очереди сохраняет все необходимые trade-события в порядке источника. При перегрузке запрещено молча удалять их. Предусмотреть ограниченный durable spool либо сохранение существенных переходов с доказанной эквивалентностью; переполнение переводит канал сигналов в degraded, блокирует утверждение полноты и запускает восстановление. Если источник не позволяет восстановить все сделки, диагностировать невосстановимый интервал; свечи не считать полной заменой trade-пути.

Доставка уведомлений выполняется через существующий outbox вне критического пути цены. Идемпотентный ключ факта исключает повтор при WS reconnect, REST fallback и replay.

## 9. Очередь расчётов и инкрементальная обработка

Ключ задания: instrument_id, timeframe, task_kind. Для расчёта хранить input version, target cursor, earliest revised open и priority. Дубликаты объединять: максимальный target cursor и минимальная граница необходимого replay. Новые данные во время расчёта должны привести к следующему заданию, а не потеряться при завершении текущего.

Порядок приоритетов: непрерывные текущие сигналы и закрытие H1; ручная сверка свежего хвоста; текущий HTF; восстановление разрыва; полный исторический backfill. Добавить fairness и предел ожидания низкого приоритета. Повторяющаяся задача не создаёт неограниченную очередь.

Если закрытые OHLC и зависимости не изменились, повторный REST-ответ не запускает полный engine, уведомления и bump всех версий. Формирующаяся свеча обновляет график, но не запускает расчёт как закрытая.

Инвалидация включает не только OHLC, но и конфигурацию детектора, разрешённые типы зон, решения review, состояние родительских HTF-зон и восстановленные разрывы. Изменение конфигурации при тех же свечах должно вызвать нужный перерасчёт.

Закрытые свечи обрабатываются по возрастанию времени. Исправление свечи или вставка за курсором запускает replay с безопасной точки. При требуемом lookback перезагрузить нужное окно; нельзя использовать только последние две свечи, если этого недостаточно для pivot/FVG/структуры.

Курсор обработки и результаты фиксируются атомарно. Падение после записи свечи до расчёта оставляет задание восстанавливаемым. Версия результата проверяется перед публикацией; устаревший расчёт не публикуется поверх новой конфигурации.

## 10. Ограниченная параллельность и лимиты

Разрешить одновременное получение свечей разных инструментов. Начальная конкурентность REST — существующие 2 на venue; увеличивать после baseline и тестов, отдельно от расчётов. Одновременные запросы одного канала объединять в single-flight.

Добавить учёт веса endpoint, если текущий semaphore недостаточен для соблюдения лимитов. Управляющие WS-сообщения, reconnect и REST fallback имеют отдельные бюджеты, согласованные с лимитами источника. Retry-After учитывается общим для venue; запросы не обходят его через другую очередь.

Долгий запрос одного инструмента не должен остановить остальные. Каждый запрос имеет timeout, отмену и диагностический результат. Нельзя держать DB transaction во время сети, ожидания semaphore или backoff. 429 и временная ошибка используют ограниченные повторы; неправильный symbol не повторять бесконечно.

## 11. Запуск и восстановление

Разделить готовность web, получения котировок, истории и расчётов. После необходимых миграций, получения ownership и загрузки локальных инструментов запустить realtime и очереди; затем догружать историю в фоне.

При наличии сохранённой БД показывать предыдущий снимок с датой и состоянием прогрева. При пустой БД показывать понятный progress и запрашивать свежий хвост раньше полной истории. Каталог источника не должен блокировать работу уже известных валидных инструментов при временной сетевой ошибке.

Исторические задачи разбивать на ограниченные батчи с checkpoint. Восстановление после перезапуска продолжается от checkpoint и сверяет перекрывающийся участок. Пользовательская активность не меняет enabled/ltf_analyze.

Сохраняется единый владелец расчёта. При конфликте ownership UI получает конкретную причину. При shutdown прекратить подписки, зафиксировать незавершённые задачи, завершить или безопасно дождаться реально выполняющегося thread; освобождение lock до окончания thread запрещено.

## 12. SQLite и read model

Профилировать существующие методы прежде чем добавлять кэш. Чтение tail должно получать ограниченное окно SQL-запросом, а не читать всю историю и затем применять Python slice. Ограничение окна соответствует логике расчёта и проверке разрывов.

Объединять вставку батча свечей и необходимые метаданные через существующий transaction/batch механизм. Проверить rollback: ошибка батча не оставляет сдвинутые версии или курсоры. Один durable batch даёт согласованную версию.

Индексы добавляются для измеренных медленных запросов и проверяются EXPLAIN QUERY PLAN. Проверить уникальность candle key и индексы списков событий/наблюдений. Дубли индексов не добавлять.

Проверить текущий WAL, busy_timeout и checkpoint. Настройки менять только с тестом совместимости и резервного копирования. Shared SQLite connection не используется одновременно неконтролируемыми threads. Не снижать durability ради скорости без отдельного согласованного требования.

Точечная инвалидация кэша допустима по сущности и инструменту; сохранить существующую межпроцессную проверку state_seq. Кэш не может продлить жизнь устаревшей read model после изменения review или конфигурации.

## 13. API и версии

Сохранить `/api/data-sync`, `/api/data-sync/status`, `/api/data-sync/{job_id}` и обратную совместимость. Новые поля добавлять без удаления старых.

Ввести независимые версии quote, candles по timeframe, zones, scenario, history и configuration. Снимок возвращает свои версии, состояние каналов и расчётные курсоры. Quote update не требует инвалидировать всю историю событий.

Согласованный bundle содержит данные и соответствующую версию. Нельзя взять version после отдельного чтения, которое уже могло устареть. При ETag/304 соблюдать авторизацию, instrument и параметры запроса; приватные данные не кэшируются публичным прокси.

Предусмотреть защищённую диагностику pipeline: transport status, market age, requested/received/processed cursors, очереди, последнее исключение и восстановление. Добавить health/liveness и readiness; длительный backfill не делает web liveness ошибочным.

## 14. Точечные обновления интерфейса

Цена обновляет цену и информационные элементы. Изменение текущей свечи вызывает chart.update для соответствующего бара; закрытие нового бара добавляет его. Историческая правка и разрыв могут потребовать ограниченного снимка. Формирующаяся свеча не меняет статус закрытого сценария.

Объединять визуальные обновления через requestAnimationFrame или ограниченный cadence. Не выполнять полное reloadAll на каждый trade. Списки зон и карточки обновлять при изменении их версии. Журнал и невидимые разделы загружать при открытии или при значимом invalidation.

Сохранить положение графика, ручное масштабирование, выбранную зону, фильтры, вкладку и прокрутку. При переключении инструмента отменять старый запрос либо отклонять ответ по instrument/generation/version. Поздний ответ не возвращает старый актив.

WebSocket update содержит type, instrument, domain version и connection epoch/sequence. При пропуске сообщения, reconnect или неизвестном формате UI делает согласованный snapshot. Не путать server state_seq с порядком сообщений конкретного соединения.

В скрытой вкладке сократить визуальную работу, не останавливая серверные сигналы. Возврат вызывает один объединённый recovery. Резервный polling поддерживается при потере browser WS; падение отдельного виджета не блокирует кнопку, статус и reconnect.

## 15. Ручное обновление и свежесть

После клика немедленно показать «Запускаем обновление», затем job_id и этап. Первый полезный этап — независимое обновление котировок всех включённых инструментов; тяжёлый backfill одного актива не задерживает цену другого.

У задания показать этапы: котировки, свежие свечи, расчёт, восстановление истории. Различать completed, failed, waiting_source, waiting_calculation; не объявлять завершение на постановке в очередь. Повторный клик возвращает активное задание.

Фильтр выбранного актива не ограничивает глобальное задание. Детали свежести доступны даже без задач в истории. Ошибка API отображается текстом и временем последней успешной проверки, а не пустым блоком. Ошибка графика не стирает состояние задания.

После terminal job UI обновляет необходимые домены; ошибка такого обновления видна как проблема отображения, отдельно от результата серверной синхронизации. Таймаут с продолжающимся thread сообщает «Расчёт продолжается» и сохраняет владение.

## 16. Настройки и флаги

Предусмотреть validated настройки realtime enable по venue, WS URL, subscription batch, reconnect backoff, idle timeout, REST concurrency/weight budget, calculation concurrency, queue/spool capacity, UI publish cadence, history batch и feature flags для incremental/UI patches.

Значения задаются с консервативными defaults. Endpoint должен соответствовать venue и market type. Не выполнять пользовательский URL через неограниченный публичный API. Изменения flags записываются в диагностику и не смешивают активные поколения заданий.

## 17. Нагрузка и целевые показатели

Профили: 3, 10 и 30 enabled инструментов, H1/D1/W1. Зафиксировать CPU/RAM сервера, регион, версии Python/browser, размер БД и частоту сообщений. На replay использовать одинаковые записи источника и сценарии касания. Детерминированный стресс: 1000 trade-сообщений/с суммарно 60 секунд, включая повтор, перестановку и разрывы; результаты не обещают такую пропускную способность production заранее.

| Показатель | Цель после baseline |
|---|---|
| Receive → durable quote | p95 ≤ 250 мс при обычной нагрузке |
| Receive → server broadcast | p95 ≤ 500 мс |
| Browser receive → отображение цены | p95 ≤ 250 мс на согласованном устройстве |
| Принятие ручного запроса | p95 ≤ 500 мс без ожидания сети биржи |
| Видимая реакция кнопки | ≤ 100 мс |
| Полученная закрытая свеча → обработка без backlog | H1 p95 ≤ 3 с, HTF p95 ≤ 5 с |
| API небольшого сохранённого снимка | p95 ≤ 300 мс при 10 инструментах |
| Полезный экран из сохранённой БД | ≤ 2 с на согласованной сети |
| Долгий CPU-расчёт 30 с | котировки продолжают приниматься и публиковаться |
| Неизменившиеся закрытые свечи | 0 повторных полных расчётов при неизменных зависимостях |

Внешнюю задержку биржи и отсутствие сделок не включать в гарантию внутренней обработки. Отдельно публиковать event_at → received_at. Уменьшение REST запросов и CPU выражается процентом от baseline; целевые проценты утверждаются после измерений. Не достигнутый target фиксируется в отчёте и устраняется либо оформляется как явное ограничение.

## 18. Критерии приёмки

- AC01: сохранённая цена отображается при старте с указанием возраста; backfill не блокирует realtime.
- AC02: блокировка расчёта на 30 с не блокирует durable quote и broadcast; lag расчёта виден.
- AC03: краткое касание зоны между двумя UI-кадрами создаёт тот же факт, что последовательная эталонная обработка.
- AC04: старый REST-ответ не перезаписывает новый WS trade; равное timestamp разных сделок поддерживается.
- AC05: повторное closed kline не запускает engine и уведомление второй раз.
- AC06: исправленная свеча и hole за курсором вызывают replay; результат совпадает с полным эталонным расчётом.
- AC07: изменение review/configuration при тех же OHLC вызывает нужную инвалидацию.
- AC08: источник не отвечает по одному активу; остальные активы получают цены и закрытия.
- AC09: Retry-After соблюдается всеми REST очередями; нет retry storm.
- AC10: WS disconnect включает fallback, reconnect восстанавливает пропуски без дублей.
- AC11: overflow не скрывает потерю сигналов; degraded и interval recovery видны.
- AC12: плановая ротация WS не создаёт дублей trade/candle.
- AC13: ручная кнопка работает до загрузки графика и показывает ошибки API.
- AC14: manual job обновляет котировки всех инструментов до тяжёлой истории; single-flight сохраняется.
- AC15: поздние ответы не меняют выбранный актив; положение графика и фильтры сохраняются.
- AC16: quote update не запрашивает журнал, все зоны и историю свечей.
- AC17: скрытая вкладка и reconnect создают один recovery вместо параллельных полных reload.
- AC18: сбой транзакции не сдвигает processing cursor; рестарт восстанавливает задачи.
- AC19: общий LTF batch не используется конкурентно; lock удерживается до окончания реального thread.
- AC20: outbox не отправляет повторное уведомление после рестарта/replay.
- AC21: отключение realtime возвращает REST режим без миграции цен между venue.
- AC22: performance report содержит baseline, новые значения p50/p95/p99 и нагрузку.
- AC23: каждый timeframe показывает received/processed и возраст; WS connected не делает старую цену актуальной.
- AC24: API snapshot/version согласованы; cross-process cache invalidation сохраняется.

## 19. Тестирование

Unit: нормализация WS, dedupe, монотонность, планирование, priority/fairness, версии, shutdown. Integration: запись → расчёт → курсор → событие → outbox на реальной тестовой SQLite с детерминированным источником.

Replay: одна запись рынка проходит эталонную последовательную и новую pipeline; сравниваются зоны, касания, сценарии, события и курсоры. Сравнение допускает различие служебных timestamps, но не рыночных результатов.

Fault injection: timeout/429, delayed REST response, malformed WS, duplicate/out-of-order, network outage, transaction rollback, calculation exception, restart, ownership conflict и переполнение.

Browser acceptance: основной и LTF экраны, ошибка первоначального графика, ручное обновление, свежесть, смена инструмента, мобилка, hidden tab, reconnect и число сетевых запросов. Performance тесты выполняются на изолированной БД без отправки реальных уведомлений. Проверку внешних API выделить отдельно от детерминированных тестов.

## 20. Этапы поставки и откат

1. Метрики и baseline. Результат: измеренный список узких мест и согласованный профиль нагрузки.
2. Разделение quote ingestion и расчёта. Результат: сохранность касаний, независимая цена, bounded queues и AC02–04/11/19.
3. Binance WS и REST recovery. Результат: AC08–12/21/23, возможность выключить WS флагом.
4. Инкрементальные расчёты и fair scheduler. Результат: AC05–07/18/20 и replay equivalence.
5. Фоновый startup и параллельное получение. Результат: AC01/09/14, ограниченная память.
6. Точечный UI и версии. Результат: AC13/15–17/24 и browser acceptance.
7. Измеренная оптимизация SQLite и общая нагрузочная приёмка. Результат: AC22 и сравнение с baseline.

Каждый этап вводится флагом и небольшим коммитом с собственными проверками. Сначала тестовая среда и небольшой список активов, затем расширение. Несколько независимых писателей одного инструмента не включаются одновременно.

Перед изменением схемы создать проверяемый backup; миграции преимущественно добавочные и совместимы с отключёнными flags. Откат отключает новый ingestion/scheduler, останавливает его writers, восстанавливает REST путь и выполняет сверку хвоста. Не удалять production market data ради возврата старого кода.
